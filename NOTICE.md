### The headline features

- Vulkan 1.3 backend, with per-frame vertex arenas gated on fences so long sessions do not leak or
  develop black patches
- CRT post-processing from an integrated beam profile rather than point sampling: scanlines,
  slot/aperture/grille masks with per-pixel coverage, glass glow
- Three exclusive sync modes — fixed 57.5242 Hz arcade, exclusive VRR, borderless — with the
  statistics panel reporting which one the panel is actually honouring
- Decoupled multi-threaded audio: fractional per-frame sample generation, adaptive output latency,
  the sound board on its own thread
- Integer scaling derived from the panel's real resolution, with a live readout of the multiple in
  effect and what the next step would require
- A settings window that stays resident, so Esc returns to it instead of quitting the program
- Hot-plug gamepads on the SDL input systems
- Chinese and English interface, with the input tables translated in both directions

### How it was built

This fork was developed with AI assistance, used as a coding tool — the way one might use a very fast
pair programmer that never gets tired and has read a great deal of source code. That is worth stating
plainly rather than leaving for someone to guess at from the outside.

The division of labour was consistent:

| | |
|---|---|
| Written by the AI | probes, drafts, refactors, translations, documentation, first-pass fixes, and the analysis that produced them |
| Decided by the author | what to build, what to leave alone, which trade-offs were acceptable, and whether any of it was actually true |

The right-hand column is the one that took the time. Every change in this fork was run. Rendering
differences were compared against the previous build on the same hardware, at the same resolution,
with the same game paused on the same frame. Frame pacing was checked against the panel's own refresh
readout rather than against what the emulator believed it was doing. Input changes were tested by
attaching and detaching physical pads mid-session, not by reading the code and concluding it must
work.

That mattered more often than expected. Several bugs here were introduced by a fix that looked
correct in review and failed on the second attempt to launch a game:

- The hot-plug path sized the joystick cache before tearing it down — an out-of-bounds read on
  exactly the event it was written to handle
- A short-circuit in the poll loop skipped the device-count refresh whenever the change flag was
  already set, so hot-plug never actually did anything
- A static pointer to the input collection outlived the collection, but only for light-gun games,
  which is why it survived testing until one was tried
- A crash on exit after the renderers were already gone was only findable by adding one log line
  per teardown step

None of those look like bugs in a diff. They look like bugs when you press Esc and the program
disappears. So testing was not a formality at the end; it was the thing that turned a plausible
patch into a working one.

The same applies to what was deliberately *not* done: upstream's PRO-1000 machine support was left
out because merging it crosses six files this fork has rewritten, and upstream's `Audio.cpp` was left
out because taking it would delete the decoupled audio path. Both required reading the diff rather
than accepting it.
