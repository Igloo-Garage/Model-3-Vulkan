## 案例 1：新功能完全不可见，且**无任何报错**

**症状**：给合成管线加了一个新的纹理槽位（背景图），配置已开启、日志明确打印加载成功、**没有任何错误**，但画面上什么都看不到。

**先分层的定位思路**：这类"静默失效"最怕猜。加**一次性追踪日志**，把"功能应该生效"的链条逐段点亮：

```
Overlay trace: begin built.            ← UI 构建完成
Overlay trace: panel built, about to Render.
Overlay trace: Render done.
Overlay trace: draw data recorded (2028 vertices)   ← 几何确实提交了
```

链条全通却看不见 → 问题不在"有没有画"，而在"画出来的是什么"。

**根因**：一个数组长度写在**三个地方**：

| 位置 | 值 |
|---|---|
| 着色器 `uLayers[N]` | 改成 **4** |
| 描述符**写入** `descriptorCount` | 改成 **4** |
| 描述符**布局** `VkDescriptorSetLayoutBinding::descriptorCount` | **漏改，仍是 3** |

后果链：

1. 第 4 个描述符写入**超出该绑定声明的数量** → 被丢弃；
2. 着色器里 `uLayers[3]` **依然能编译、依然执行**；
3. 它读到的是**数组之外**的描述符，在该驱动上表现为一张**完全透明的纹理**；
4. 合成管线开着 alpha 混合（`SRC_ALPHA / ONE_MINUS_SRC_ALPHA`）→ 与"什么都没有"混合 → **画面毫无变化**。

所以三个现象同时成立：**draw 确实执行了、没有任何错误、却完全看不见**。

**修法**：把这个数字提成**一个命名常量**，三处都引用它：

```cpp
constexpr uint32_t kCompositeLayerCount = 4;
```

**验证层的价值**：这个 bug 有现成的 VUID（`VUID-VkWriteDescriptorSet-descriptorCount-00311`），**第一帧就会报出来**。但本机没装验证层，所以唯一的自动告警不存在 —— **没有验证层的 Vulkan 调试基本等于盲改**。装 Vulkan SDK 或 RenderDoc 的收益在这种时刻最明显。

**教训**：
- 同一个数字散落在 N 处，**漏改是时间问题**；提成常量成本几乎为零。
- **alpha 混合会掩盖错误**：越界/无效纹理在混合下表现为"什么都没发生"，而不是"画错了"。
- 判断"功能是否执行"要用追踪日志，判断"执行结果对不对"要靠**独立的数据**（见案例 12）。

> 项目内详见 `TECHLOG.md` 第 18.11 节。

## 案例 2：拷贝之后状态丢失，功能静默失效

**症状**：加载一个配置文件后，配置界面里**若干页变成空白** —— 语言切换、状态栏报告、ROM 目录判定全都正常，只有一部分控件消失。

**定位**：界面的控件是**遍历配置树、按分组名筛选**生成的：

```cpp
auto vRange = val->GetValueRange();
if (vRange) {                        // 范围为空 → 整项直接跳过，连报错都没有
    if (vRange->GetGroup() == group) { ...画控件... }
}
```

「这一项属于哪个页」这个信息**不在键名里**，而是挂在每个值上的元数据对象里。范围一丢，这些页就全空。所以问题是**数据丢了**，不是界面逻辑坏了。

**根因**：赋值 `config = merged;` 走的是深拷贝 → `MakeCopy()` → 拷贝构造函数，而那个拷贝构造**只初始化了类型，没复制基类的私有成员**：

```cpp
ValueInstance(const ValueInstance<T> &that)
  : GenericValue(std::type_index(typeid(T))),   // ← 只传了 type，基类不是拷贝构造
    m_data(that.m_data)
{
}                                              // ← 基类的 m_valueRange 从来没被复制
```

因为基类的成员是 `private`，而这里调的是「按类型初始化」的构造函数而非隐式拷贝构造，**每一次值的拷贝都会静默丢掉这部分状态**。

**为什么启动时正常、只有载入后不正常**：启动路径是**直接构造**目标节点，不经拷贝；而"恢复/覆盖"逻辑里那句赋值，是整个流程中**唯一**走拷贝的地方。

**修法**：在拷贝构造里显式带上（并补一个 `const` 重载，因为拷贝源的成员访问是 const 的）：

```cpp
std::shared_ptr<ValueRange> GetValueRange() const { return m_valueRange; }

ValueInstance(const ValueInstance<T> &that)
  : GenericValue(std::type_index(typeid(T))), m_data(that.m_data)
{
    SetValueRange(that.GetValueRange());
}
```

**教训**：
- 自定义拷贝构造要**显式处理所有基类/私有状态**；只初始化"自己的那部分"很容易漏。
- **"恢复"逻辑若被 `if (指针非空)` 保护，那么指针一旦丢失就再也恢复不了** —— 这类"补救代码"往往掩盖了真正的丢点。
- 排查"某功能在 A 路径正常、B 路径不正常"时，**先找出两条路径的差异**（本例唯一差异就是一句赋值），比通读代码快得多。

## 案例 3：启动时控制台黑框一闪而过

**症状**：GUI 程序启动时，一个黑色控制台窗口**一闪而过**。加了"隐藏控制台"的代码也无效。

**根因**：**不是隐藏得太慢，而是不可能隐藏掉**。链接时用的是控制台子系统（Windows 上 `/SUBSYSTEM:CONSOLE`），操作系统会在进程启动阶段、**在程序任何一行代码运行之前**分配并显示控制台。事后的 `ShowWindow(SW_HIDE)` 只能掩盖"已经显示过"的事实，是在赌"隐藏发生得足够快" —— 快机器上这个赌注会输。

**修法**：**改子系统，而不是事后隐藏**。

```
/SUBSYSTEM:CONSOLE  →  /SUBSYSTEM:WINDOWS
```

没有控制台子系统，就**没有东西可以出现**。

**附带代价与处理**：改完之后 `printf` / `std::cout` 没有去处了，而这通常正是程序用来输出的方式。要按场景分情况：

| 场景 | 处理 |
|---|---|
| 从终端/shell 启动 | `AttachConsole(ATTACH_PARENT_PROCESS)` **附着到父进程的控制台** —— 输出照旧出现在用户已经看着的窗口里，**不新建窗口** |
| 从文件管理器/快捷方式启动 | 没有父控制台可附着，什么也不做 → 无窗口 |
| 显式要求时（如 `--show-console`） | 先试附着父控制台，失败再 `AllocConsole()` 自建 |

**两个必须避开的坑**：

**① 不能隐藏别人的控制台。** 附着到父 shell 的控制台后，"取当前控制台窗口"的函数**不再返回空** —— 这时若执行"隐藏控制台"，被隐藏的是**用户自己的终端窗口**。要用一个所有权标志区分：

```cpp
static bool s_consoleIsOurs = false;   // 只有本进程 AllocConsole() 出来的才归我们
```

**② 不能吃掉输出重定向。** 附着父控制台后如果无条件把 `stdout` 重绑到控制台，那么

```
app.exe --list > out.txt
```

**会写出一个空文件** —— 调用方要求写到文件，程序却把流指向了控制台。要在**任何时候都可能创建控制台之前**先记录一次标准输出是否已经可用：

```cpp
HANDLE output = GetStdHandle(STD_OUTPUT_HANDLE);
s_stdoutProvided = (output != nullptr && output != INVALID_HANDLE_VALUE);
// 之后重绑时：if (s_stdoutProvided) return;
```

**验证方法**（重要）：不能靠"盯着屏幕看有没有闪" —— 一闪只有几百毫秒。要**枚举进程的顶层窗口，看有没有控制台类窗口**。并且**必须有阴性对照**（用确定带控制台的程序验证检测能力）—— 细节见案例 12。另外，**测试必须用用户的实际启动方式**（从文件管理器启动），从 shell 启动是测不出来的：shell 自己有控制台，程序附着上去就不会新建窗口，**无论代码怎么写**。

**教训**：
- **"事后隐藏"优于"事前不创建"的判断多半是错的** —— 凡是系统在启动阶段就创建的东西（控制台、窗口、句柄），只能从源头改。
- 改动一个默认行为时，要**列出它原本提供的所有好处**（这里是 CLI 输出），逐个补回来。

## 案例 4：裁剪误用 viewport，导致画面整体缩小

**症状**：给渲染加"裁剪掉边缘几像素"的修复后，**画面缩到中间去了**，四周多出一圈背景色。

**根因**：错在**把裁剪实现在矩形本身上** —— 把传进绘制函数的 `x/y/w/h` 缩小。

那个矩形在这段代码里是**视口（viewport）**，而绘制的四边形带的纹理坐标是 **0..1 全范围**：

```cpp
viewport.width  = (float)w;   // 同时决定纹理映射范围
viewport.height = (float)h;
```

所以把它改小的效果不是"裁掉边缘"，而是**把整张纹理压缩进更小的区域** → 画面缩小、四周露出底色。

**修法**：**裁剪必须用 scissor，不能动 viewport**。这也是 OpenGL 的做法：`glViewport` 管位置和缩放、`glScissor` 管裁剪，**两者互不影响**。

```cpp
// viewport：调用方给的原矩形，不动
VkViewport viewport = { ... x, y, w, h ... };

// scissor：裁剪后的矩形
int cx = x, cy = y, cw = w, ch = h;
/* 与可见区域求交 */
VkRect2D scissor = { { cx, cy }, { cw, ch } };
```

**为什么容易错**：裁剪和几何**都用"矩形"表达**，参数名也常常相似（`rect`、`area`、`region`）。但语义完全不同：

| 用途 | 改错的后果 |
|---|---|
| **几何**（viewport / 投影 / 矩阵） | 画面**被缩放/位移** |
| **裁剪**（scissor / clip rect / stencil） | 画面**被切掉一块** |

**教训**：
- **看到一个矩形参数，先确认它在这段代码里是"裁剪"还是"几何"** —— 这两者改错的症状完全不同，但都很容易被误判成"裁多了/裁少了"。
- **改渲染之后必须看画面**。本例中我**只验证了几何数据**（日志里的矩形数值完全正确），就宣布修好了 —— 而几何数值正确**不等于**画面对。这是最该避免的一类验证疏漏。

> 项目内详见 `TECHLOG.md` 第 18.4 节末尾的修正说明。

## 案例 5：脏标记提前清零 + 失败早退，导致数据永久丢失

**症状**：**偶发**的贴图变黑块 / 图案缺失。不是每次都出现，重写同一区域后才恢复。

**定位思路（这条最有价值）**：先确认"是不是我改出来的"。查文件修改时间：

```
10-10 11:21  TextureCache.cpp     ← 早于本次全部工作
10-12 12:51  Vulkan2D.cpp
```

**早于本次改动 → 是既有问题**，不是回归。这一步能立刻避免在错误方向上花时间。

然后顺着"纹理数据怎么到 GPU"读代码，找到两个问题叠在一起：

**问题 A：消费型状态提前清除。** 脏标记在**拷贝出来的同时就清零**了：

```cpp
{
    std::lock_guard<std::mutex> guard(m_dirtyMutex);
    dirty[0] = m_dirty[0];
    dirty[1] = m_dirty[1];
    m_dirty[0].reset();     // ← 已经清掉了
    m_dirty[1].reset();
}
```

**问题 B：失败早退，丢弃整批。** 上传时若分配失败，**直接退出整个函数**：

```cpp
if (!ring.Alloc(bytes, 4, offset, ptr))
{
    m_rawLayout[page] = TRANSFER_DST_OPTIMAL;
    return;                 // ← 退出整个函数
}
```

两者叠加的后果：**那批脏块永久丢失** —— 原始纹理页保持旧内容，而着色器直接采样它；游戏不重写同一区域就永远不会修正（对"加载时写一次"的数据就是永不）。

而且这个 `return` **放弃的不止一项**：另一页、以及本页剩余部分，全部一起被放弃。

**触发条件**：只在**短时间内大量写入**时才触发。而"从桌面切回全屏"正是这种时刻 —— 交换链重建、游戏暂停再恢复，积压的写入在少数几帧内集中处理。**这解释了为什么是"偶发"。**

**修法**（四点，缺一不可）：

1. 用一份**副本**逐个勾掉**已成功交出**的瓦片；
2. 失败时**不退出函数**，只跳出当前页的循环，**继续处理另一页**；
3. **无条件下发布局转换** —— 否则图像会卡在 `TRANSFER_DST`，而着色器当作 shader-read 采样，是未定义行为；
4. **未处理的放回**脏集合，下一帧继续；
5. 每次发生都**记日志**（配额本来给得宽裕，真发生就该看见频率）。

```cpp
std::bitset<...> pending = dirty[page];      // 副本
...
if (!ring.Alloc(...)) { ranOut = true; break; }   // 只跳出本页
...
for (int i = tx; i < run; i++) pending.reset(...);   // 已交出的才勾掉
...
CmdTransition(...);                          // 无条件
if (ranOut && pending.any()) { m_dirty[page] |= pending; InfoLog(...); }
```

**教训**：
- **消费型状态必须"成功后才清除"**。先清后做，中途失败就是永久丢失。
- **循环里的 `return` 放弃的是一整批，不是一项**。要想清楚"这一步失败后，其余部分该继续还是该放弃"。
- **收拾状态要无条件**（本例的布局转换），别让失败路径留下不一致的状态。
- 偶发问题的排查，先查**触发条件对应的时序**（"什么时候会集中发生"），而不是猜数据。

> 项目内详见 `TECHLOG.md` 第 18 章相关小节。

## 案例 6：刷新逻辑放错位置，导致状态转换永不触发

**症状**：做"实时调参数"功能时发现，参数改动**要重启才生效**；而且更奇怪的是，**从"全关"切到"开启"永远不生效**，从"已开启"再调却是好的。

**根因**：把"每帧回读参数"放进了那个**只在功能已开启时才会被调用**的函数里：

```
EndFrame():
    if (功能已开启) {
        ...
        DrawPostPass();      ← 刷新放在这里面
    } else {
        直接合成();           // ← 这条路根本不经过上面
    }
```

于是"开启"这个**状态转换本身**永远触发不了刷新 —— 因为只有已经开启才会执行刷新。这是个**自指的死结**：要改变条件，得先满足条件。

**修法**：把刷新移到**每帧必走的分支之前**：

```
EndFrame():
    刷新参数();               // ← 先刷新，再决定走哪条路
    if (现在开启了) { ... } else { ... }
```

**顺带发现的第二个问题**：如果功能**从未开启过**，它依赖的管线/资源**根本没有创建**。这时切到"开启"会绑定空句柄 —— 在图形 API 里这通常是**驱动错误而非可见失败**。所以刷新逻辑还要能**按需补建**资源（第一次需要时创建，而不是只在启动时创建）。

**教训**：
- **"只在条件满足时执行"的函数，不能承担"判断/改变该条件"的职责**。刷新、轮询、状态同步这类逻辑要放在**无条件执行**的位置。
- 做"运行时状态可切换"的功能时，要检查：**该状态从"关"变"开"时，需要的东西是否已经存在**。
- 症状"从 A 状态切到 B 状态无效、但从 B 再调有效"几乎总是指向**刷新位置错了**。

> 项目内详见 `TECHLOG.md` 第十八章的"参数每帧回读"部分。

## 案例 7：第三方后端与核心的版本配对

**症状**：想引入某个库的官方渲染后端，但取来最新版后编译报**一堆看似无关的错误**（成员不存在）：

```
error: 'X': is not a member of 'CoreStruct'
```

**定位方法**（这条很通用）：**开发中期的库，版本号不足以定位修订**（本例核心是 `1.92.6 WIP`，而该库的开发分支**也是** `1.92.6 WIP`）。要按**日期**对齐：

1. 读**核心**的变更日志，取最新一条的日期：

   ```
   - 2025/12/23 (1.92.6) - Fonts: ...
   ```

2. 用托管平台的 API 查**后端文件**在该日期之前最近的提交：

   ```
   api.github.com/repos/<owner>/<repo>/commits
       ?path=backends/<file>
       &until=2025-12-24T00:00:00Z
   ```

3. 取那一版：

   ```
   raw.githubusercontent.com/<owner>/<repo>/<sha>/backends/<file>
   ```

本例中后端文件在 12/17 之后没有改动，所以核心配的就是 **12/17 的那一版**；换上之后**一次编译通过**。

**验证方式**：**单独编译那个文件**，而不是等整个工程一起编。版本不匹配的错误会落在看起来无关的地方，混在几百个文件里非常难认。

**配套的配置项**：这类库通常提供"用哪个 Vulkan 加载器"的开关，而且**官方要求写在库的配置头里**（不能只放编译命令行）。本例：

```cpp
#define IMGUI_IMPL_VULKAN_USE_VOLK
#define IMGUI_IMPL_VULKAN_VOLK_FILENAME <volk/volk.h>   // 路径也要能配
```

**教训**：
- **开发中期的版本号不唯一标识修订**。要按日期或提交号锁定。
- 引入第三方代码时，**先用"单独编译"验证兼容性**，再集成进构建系统 —— 排查成本差一个数量级。
- 换掉手写实现改用官方实现时，**先验证"能否直接用"**，别因为"版本可能不匹配"这种**未验证的假设**就自己写。（本例我一开始就犯了：假设版本不匹配，验证后发现前提并不成立。）

> 项目内详见 `TECHLOG.md` 第十八章。

## 案例 8：多上下文库的空上下文解引用

**症状**：**访问违例**崩溃。日志停在某个函数**之前的**追踪行 —— 说明崩溃就在进入该函数的第一步。

**根因**：这类库（如 GUI 库）常支持**多个上下文**，每个线程有一个"当前上下文"。从一个上下文切到另一个时，如果在**没切换的情况下**读取上下文相关的数据：

```cpp
ImDrawData* drawData = ImGui::GetDrawData();   // ← 此时"当前上下文"是空的
```

而这里之所以是**空的**，是因为之前的上下文已经被销毁 —— 该类库在销毁上下文后会把"当前上下文"置空，而代码保存的"之前的上下文"正是那个已销毁的。

**修法**：**先切换，再取数据**：

```cpp
SetCurrentContext(g_context);
ImDrawData* drawData = GetDrawData();
...
SetCurrentContext(g_previousContext);
```

**定位技巧**：追踪日志的**"最后一条已打印"**就直接指向崩溃点。本例追踪到"构建完成 → 渲染调用完成"，而崩溃发生在**渲染之后的第一步**，于是范围瞬间缩到一个函数的前两行。

**教训**：
- 多上下文的库，**"进入前先切上下文"要成为固定习惯**，尤其在跨模块调用时。
- 保存"之前的上下文"时要注意它**可能是空**（首次使用、之前销毁过）。
- **在关键函数的首尾各加一条一次性追踪日志**，是定位崩溃最省事的手段 —— 比接调试器快得多。

> 项目内详见 `TECHLOG.md` 第十八章。

## 案例 9：抓屏：BitBlt 对现代 GPU 渲染无效

**症状**：需要验证屏幕上到底显示了什么，但截屏工具抓回来的是**全黑**。

**试过并失败的**（都返回黑）：
- 桌面 `BitBlt`
- 对该程序窗口做 `BitBlt` / 图形库的 `CopyFromScreen`

**有效的**：

```
PrintWindow(hwnd, hdc, PW_RENDERFULLCONTENT)   // 标志值 = 0x2
```

`PW_RENDERFULLCONTENT`（`0x2`）让窗口**把自己渲染进给定的设备上下文**，能拿到**合成后**的内容；普通的 `PrintWindow` 和 `BitBlt` 拿不到。

**注意事项**：
- `PrintWindow` 渲染的是**整个窗口**（含标题栏和边框），而取客户区尺寸返回的是**客户区**坐标 → 抓到的图**顶部会多出标题栏**，内容整体有偏移。分析像素时要留意，否则会把标题栏的亮色误读成画面内容。
- **独占全屏**（flip 模式的表面）**两种方法都拿不到** —— 那种情况下必须先切到窗口模式。
- 前提条件是窗口**可见且未被最小化**（客户区尺寸为 0 时无法抓取）。

**教训**：
- **"抓不到"要换方法，而不是放弃验证**。现代 GPU 合成（DWM）和翻转模型（flip model）表面需要**让窗口自绘**。
- 抓到的图**要核对坐标系与偏移**（标题栏、DPI、缩放），否则后续的像素分析全部建立在一个错误的基准上。

> 项目内详见 `TECHLOG.md` 第 18.10.1 节。

## 案例 10：输入注入不可靠

**症状**：用系统 API **合成按键**（`keybd_event` / `SendKeys`）送给一个游戏/全屏程序，程序**完全没有反应**。

**根因**（两层）：
1. **系统拒绝把窗口置前** —— 前台锁定等机制会让"设置前台窗口"失败，于是**程序从未获得焦点**；
2. 该程序的输入是**每帧轮询**的（而不是靠消息驱动），所以按键还必须**持续足够久**才能被某一帧看到。

两者叠加：按键既没送到正确窗口，即使送到了也可能因为太短而被漏掉。

**替代思路（更值得记）**：**绕过输入，而不是注入输入**。

本例需要验证的是"某个面板渲染是否正确"。与其费劲模拟"按开关打开面板"，不如**临时把面板的初始状态改成打开**：

```cpp
bool g_visible = true;   // TEMP: 强制打开用于渲染验证，之后还原
```

一次构建就能验证渲染、字体、布局，**完全不涉及输入**。验证完记得还原（并在文档里记下这次临时改动）。

**教训**：
- 自动化验证时，**先问"能不能绕过这个交互"**。能改成初始状态/配置项/命令行参数的，就不要再去做输入注入。
- 输入注入在**全屏、独占、前台锁定、轮询输入**这几种情况下都不可靠，而它们恰恰是游戏类程序最常见的情形。
- 临时改动要**明确标注 TEMP 并记入文档**，否则很容易遗留。

## 案例 11：几何用性质测试代替肉眼

**症状**：某几何计算（把画面之外的区域分成几块来填充）有 **off-by-one 错误**，但**在屏幕上完全看不出来** —— 表现是"背景图看着有点不对"，而不是明显的错。

**根因**：几何逻辑混在渲染代码里，**只能通过实际渲染来观察**。而这类错误的两种表现都很不显眼：

- 区域**重叠**几个像素 → 一块内容盖在另一块上；
- 区域**没铺满** → 留一条细缝。

**修法**：把几何**抽成纯函数**（不依赖任何图形 API 类型），然后**穷举断言不变量**：

```
对 输出尺寸 × 画面尺寸 × 偏移 × 修正量 做扫描：
  断言「各块区域与画面区恰好铺满整个输出」
       —— 不重叠、不留缝、每块非退化、不越界
```

实现上给输出打一个**粗网格计数**：每个格子记录"被几个矩形覆盖"，**必须恰好为 1**。这样一条断言同时覆盖重叠（>1）和留缝（=0），而且失败时能**指出具体像素**。

**实测规模**：12756 组用例（含 8 种真实分辨率 + 贫举扫描），**0 失败**。

**判定力必须反向验证**：故意把某一块改成错误形状，测试**立刻报出**

```
pixel (0,0) is owned by 2 rectangle(s), expected exactly 1
```

—— 它抓的是**重叠**，并且指到具体位置。

**教训**：
- **"恰好覆盖一次"远强于"看起来对"**。前者能在没有显示器、没有 GPU 的环境下穷举验证。
- **能抽成纯函数的几何，就抽出来**。留在渲染代码里就只能靠眼睛。
- **测试必须有判定力**：写完要**故意改错一处**，确认测试会失败。否则"一直通过"可能只是因为它什么都没检查。

> 项目内详见 `TECHLOG.md` 第 18.4 节。

## 案例 12：「假通过」的验证必须有阴性对照

这一条是**方法论**，因为本项目里它连续造成了三次误导，每次都**报告通过**。

**原则**：**断言"某物不存在"的检查，必须有阴性对照**证明它**能**发现该物存在。否则一个写错的比较会安静地报告成功。

### 三个具体的假通过

**① 字符编码编组错误 → 比较永远不匹配。**

用脚本语言调用宽字符 API（`GetClassNameW` 等）时，如果没显式声明**宽字符编组**，字符串缓冲区会被按 ANSI 读取：

```
class='S'        ← 每个类名只回来 1 个字符
class='t'
class='N'
```

于是 `-eq "ConsoleWindowClass"` **永远为假**，报告"0 个目标窗口"。**这个失败看起来和通过一模一样。**

修法：显式声明宽字符编组。**但更重要的是**：加一个**确定带该特征的进程**（如终端自身）做对照，验证检测能力。

**② 脚本语言的函数既输出到管道又返回值。**

```
$x = Report ...     # $x 变成"函数输出的所有字符串"的数组
if (-not $x)        # 判断的是一个数组，不是布尔值
```

于是条件判断**完全失真**。修法：**显示走"写主机"，返回值走"返回"**，两者不混。

**③ 测试方式与用户场景不符。**

用"从 shell 启动"来测"启动时有没有黑框"，**根本测不出来**：shell 自己有控制台，程序附着上去就不会新建窗口 —— **无论代码怎么写都会通过**。必须用**用户的实际启动方式**（从文件管理器启动）才能复现。

### 推论

- 检测"不存在"之前，先证明检测**能发现存在**。
- 复现问题要**匹配用户的真实场景**（启动方式、窗口模式、输入方式），否则测试只是在验证一个方便测的东西。
- 一旦发现一次假通过，**要回头重跑之前所有基于该检测的结论** —— 本项目里前两轮的"通过"结论都是这么被推翻的。

**教训**：**"报告通过"本身不可信，除非你见过它报告失败的样子。**

## 案例 13：结构体变长后，所有调用方都要推完整块

**症状**：给推送常量（push constant）结构体加了一个字段后，**部分路径的值变成垃圾**（而新功能本身工作正常）。

**根因**：推送时如果**只推一部分字节**，而结构体声明得更长：

```cpp
// 结构体：{ uint layer; float brightness; }   —— 8 字节
vkCmdPushConstants(..., sizeof(uint32_t), &layer);   // ← 只推了 4 字节
```

那么**剩下的 4 字节是未定义值**。

**修法**：**所有调用方都推完整的结构体**，不适用的字段填中性值：

```cpp
LayerPush push = { layer, 1.0f };        // 亮度中性值
vkCmdPushConstants(..., sizeof(push), &push);
```

**为什么容易漏**：加字段时只想着"新用途需要这个字段"，而**旧调用点看起来和自己的改动无关**，于是不会去动。

**教训**：
- 给共享的结构体/常量块加字段时，**要搜出所有推送点**，而不是只改新加的那个。
- 这类错误的表现是**"不该变的地方变了"**，比"新功能不工作"更难联想，因为它看起来像是无关代码被破坏了。
- 相关的一条实践：**在结构体定义处写明"每个调用方都必须推完整块"**，让下一个人看得见。

## 案例 14：可选资源缺失导致设备静默退化

**症状**：某款游戏**卡在硬件的自检画面上**，进不了游戏。而日志里**除了"找不到某文件"之外没有任何错误**，ROM 甚至报告 `ROM CHECK OK`。

**定位过程**（这条的价值在于它绕了两个弯）：

**第一层：确认不是常规问题。** ROM 载入零错误、无缺失父集、网络板自检明确显示 `NETWORK CHECK OK`。所以不是"缺文件"这么简单。

**第二层：找到"设备是否挂载"的判定条件。** 关键是一个 `&&`：

```cpp
if (game.driveboard_type == Game::DRIVE_BOARD_WHEEL && rom_set.get_rom("driveboard_program").size)
{
    DriveBoard = new CWheelBoard(m_config);      // 真实现
}
else if (... && rom_set.get_rom("driveboard_program").size)
{
    ...
}
else
{
    // 兜底：一个"未挂载"的空实现
    DriveBoard = new CDriveBoard(m_config);
}
```

**第三层：解释为什么 `rom.size` 是 0。** 因为该 ROM 区域在 `Games.xml` 里标着 **`required="false"`**，而载入器对可选区域的处理是"**失败就删掉、继续**"：

```cpp
if (error_loading_region && !region->required)
{
    // Failed to load the region but it wasn't required anyway, so remove it
    rom_erase(region->region_name);
}
```

**于是完整的因果链是**：

```
ROM 区域标为 optional
  → 文件缺失，加载失败
  → 载入器静默丢弃该区域（只打一条 info 级别的提示）
  → rom.size == 0
  → && 判断为假
  → 退化到"未挂载"的空实现
  → 游戏被告知"没有这块板"，但它自己的自检期望有
  → 卡在自检画面
```

**每一环都是"看起来正常"的**：没有致命错误、没有崩溃、日志里那条 info 提示淹没在几百行输出里、而且**离真正的失败点很远**。

**影响面（实测）**：一个缺失的 ROM 文件（CRC `0x0CA70F80`，一块 Billboard 驱动板程序）被 **6 个游戏家族共 18 个集合**引用 —— 全部会静默退化。而另一类驱动板（Wheel，13 个集合）的 ROM 齐全，所以**全部正常** —— 这正是"为什么只有部分游戏有问题"的答案。

**修法（两层）**：

1. **诊断**：在退化发生的地方**明确报因**，把"游戏要什么"和"实际缺什么"放在同一句话里：

   ```
   No 'driveboard_program' ROM for 'von2', which declares a drive board. Falling back to an
   unconnected one - the game will most likely stop at its hardware self-test. Check that the
   ROM set (or its parent set) contains the drive board program.
   ```

2. **用户侧**：补齐那个 ROM 文件到相关的 zip 里。

**教训**：
- **"可选资源"+"静默兜底"是一个危险组合**：它把"资源缺失"从一个错误变成了一种**运行模式**，而这个模式与游戏期望不符时，症状出现在**完全不相干的地方**（自检画面）。
- **`&&` 里的"资源存在性检查"（本例 `rom.size`）是一个隐藏的分支**。读代码时要问：这个条件为假时会走哪里？那条路会告诉用户原因吗？
- 排查这类问题时，**先把"设备实际挂载了没有"变成可观测的**（本例中把 `Extra Hardware` 写进日志，它列出的是**真正实例化的板卡**，而不是游戏期望的），比继续猜"哪一步坏了"有效得多。
- 症状是 `ROM CHECK OK` 但进不去 —— 这类"局部通过、整体失败"几乎总是指向**某个组件的存在性**问题，而不是数据损坏。

> 项目内详见 `TECHLOG.md` 第二十二节。

## 案例 15：诊断输出的去向，决定你能得出什么结论

这一条是**方法论**，因为它在同一个项目里连续造成了**两次相反的误判**。

**症状**：某个子系统看起来"完全没有输出、也没有报错"，于是判定它**正常**。

**根因**：那些诊断走的是 **`printf` / `std::cout`**，而**日志文件是另一条通路**。两者互不相干：

| 输出方式 | 去哪 | 进日志文件吗 |
|---|---|---|
| `printf` / `std::cout` | **stdout** → 控制台窗口 | ❌ **不进** |
| `InfoLog` / `ErrorLog` | 日志文件（+ 视配置进控制台） | ✅ |
| `DebugLog` | 日志文件，但**受日志级别过滤** | 视级别而定 |

**于是"日志里没有"被错误地当成了"没有发生"** —— 而实际上那个模块一直在打印，只是**打到了你看不到的地方**。

**两次具体的误判**：
1. 网络板用 `printf` 打印连接过程 → 日志里一片空白 → 我判定"网络板没问题"，**实际是它的输出根本不进日志**
2. 游戏的硬件清单用 `std::cout` → 日志里查不到"挂了哪些板卡" → 我绕了一大圈才想到去读源码，而**这一行正是答案所在**（它显示 `Drive Board` 不在列表里）

**修法**：
- 把**真正有诊断价值**的输出改为 `InfoLog`；
- **逐次/高频**的输出留给 `DebugLog`（否则会刷爆日志）；
- 注意循环里的 `printf` —— 有一个原本在 `while (!connect())` 循环里，**每轮都打印**。改成日志前先**移到循环外**，否则转过去就是把控制台的噪音变成日志的噪音。

**教训**：
- **在断言"日志里没有错误"之前，先确认那个模块的错误到底往哪里输出。** 否则结论可能完全反向。
- 判断"某功能是否运行"时，**优先把它变成日志里可见的事实**，而不是依赖"没看到异常"。
- 反过来：**转换输出方式时要注意频率**。一次性事件用 `InfoLog`，逐帧/逐字节的用 `DebugLog`。

> 项目内详见 `TECHLOG.md` 第二十二节。

## 案例 16：审计工具连续三次"答对了问题、给出了错的结论"

为一个 ROM 目录写审计工具（`Scripts/RomAudit/`），目的是回答"这些游戏哪些能玩"。工具编译通过、逻辑自洽、输出漂亮，**但它连续三次给出可信的错答案**，每一次都是**问错了问题**。

**为什么用 C# 而不是脚本**：第一版是 PowerShell 脚本，它把一套**完整的 39 文件 ROM 集**报告为"全部缺失"。原因是一个字符串在管道里**丢了格式占位符**，所有 CRC 塌缩到同一个 key 上，而脚本**不报错**。一个"能悄悄出错"的检查工具比没有工具更糟。

### 错误一：按文件名匹配（而模拟器按内容匹配）

**症状**：`scud.zip` 被判为"缺 4 个必需 CROM 文件"。

**实测**：模拟器**成功加载**了它，日志写的是：

```
Title: Scud Race (Australia, Twin/DX)     ← 是 scudau，不是 scud
Extra Hardware: Digital Sound Board (Type DSB1), Drive Board, Net Board
（无任何错误）
```

**根因**：**Supermodel 按 zip 内文件的 CRC-32 识别游戏，完全忽略文件名。** 所以"叫 `scud.zip` 就必须满足 `scud`"这个前提根本不成立 —— 那个 zip 装的是澳洲版。

**修法**：把问题**反过来问**：

| 错的问法 | 对的问法 |
|---|---|
| 名叫 X 的 zip 里有 X 集合的文件吗？ | **这些 zip 能满足哪些集合？** |

### 错误二：把"合并"当成并集，后来又矫枉过正成"整区域替换"

**症状**：首先几乎所有**子集**（有 parent 的集合）都被判为不可满足。

**根因**：我不该猜，应该读源码。`GameLoader::MergeChildrenWithParents()` 写得很清楚：

> *"...with the child set loading in different files to **overwrite** the parent set."*

**合并既不是并集，也不是整区域替换，而是「按 offset 替换」**：

```cpp
// 先整体拷贝父集的 regions
new_regions[region_name] = std::make_shared<Region>(*v2.second);
// 再把子集的文件合并进来：同 offset 覆盖，新 offset 追加
if (new_region->FindFileIndexByOffset(&idx, child_region->files[i]->offset))
    new_region->files[idx] = child_region->files[i];       // 同 offset -> 替换
else
    new_region->files.push_back(child_region->files[i]);   // 新 offset -> 追加
```

- **只求并集**：要求子集和父集两套文件同时存在 → 永远匹配不上。
- **整区域替换**（我第一次的"修法"）：子集若只声明了该区域的**部分** offset，父集剩下的 offset 会被丢掉 → 把仍然必需的文件当成"多余"。**这个错误更隐蔽，因为它只在子集声明 offset 数少于父集时才暴露。**

**真实案例**：`mgtrkbad` 只声明了 `crom` 4 颗芯片中的 2 颗，并在注释里明说另外两颗**继承自父集**：

```xml
<!-- file offset="2" name="epr-21436.19" ... - same data as EPR-21436 in MAGTRUCK -->
```

按"整区域替换"算，该集合是 27 个文件、有 2 个"多余文件"；按**正确的按 offset 合并**算是 **29 个**、零多余 —— **与模拟器日志逐字吻合**。前者还会在缺少那 2 颗芯片时错误地判定"可玩"。

**修法**：合并键用 `(区域名, offset)`：

```csharp
foreach (var def in chain)              // 父集在前，子集在后
    foreach (var region in def.Regions)
        foreach (var f in region.Files)
            merged[region.Name].ByOffset[f.Offset] = f;   // 同 offset 后者覆盖前者
```

**教训**：**合并语义要去读加载器，不要从注释的字面意思推断**。"overwrite the parent set" 听起来像"整个区域覆盖"，实际是"按 offset 覆盖"。**注释概括意图，代码才是契约。**

**第三个变体**：**路由 B**（子集 zip + 按名字取父集 zip）也犯过两次错：
1. 把父集文件**无条件并进每个候选**，结果"1 个 35 文件的 zip 满足了 8 个不相关的游戏"（父集在偷偷提供一切）；
2. 又改成要求"每个贡献者各自 zip 里齐全"，比加载器更严。

**加载器的实际判定**（`ChooseGameInZipArchive`）：候选必须能被识别（**该 zip 里至少有子集自己的 1 个文件**），随后按**名字**打开 `<parent>.zip`，**在两个归档的并集里**查找所有文件：

```csharp
bool identified = own.Any(f => zip.Crcs.Contains(f.Crc));
bool complete = required.All(f => zip.Crcs.Contains(f.Crc) || parentZip.Crcs.Contains(f.Crc));
```

### 错误三：问"集合能否满足"，而用户问的是"游戏能否玩"

**症状**：`scudplus`、`harley`、`vf3`、`magtruck` 被判为不可玩。

**实测**：四个**全部能跑**，日志显示它们加载的是**同名的另一个修订**：

```
scudplus  → 加载为 Scud Race Plus (Export, Twin/DX, Revision A)   = scudplusa
harley    → 加载为 Harley-Davidson and L.A. Riders (Export, Rev A) = harleya
vf3       → 加载为 Virtua Fighter 3 (Japan, Revision C)            = vf3c
magtruck  → 加载为 Magical Truck Adventure (Japan)                 = mgtrkbad
```

`magtruck` 最典型：它的 CROM 是 **2022 年重新 dump** 的版本，用户手上是旧 dump —— 但 `mgtrkbad`（旧 dump，**标题和版本与它完全相同**）能跑，所以游戏**照常可玩**。

**修法**：按**标题分组**汇总，"该游戏可玩"= **任一修订可满足**。

### 验证方式（这条最关键）

工具写完后**没有直接用它下结论**，而是拿**已知答案**对照：

| 集合 | 工具 | 模拟器实测 | 一致 |
|---|---|---|---|
| `skichamp` | 39/39 全在 | 日志显示 39 个文件全加载成功 | ✅ |
| `scud.zip` | 满足 `scudau` | 加载为 scudau | ✅ |
| `bassdx` | ❌ 不可玩 | ❌ 缺 `mpr-20259.4` 硬失败 | ✅ |
| `ecap` | ❌ 不可玩 | ❌ 缺 `qq.ic15` 硬失败 | ✅ |
| `scudplus`/`harley`/`vf3`/`magtruck` | ❌ → 修正后 ✅ | ✅ 全部能跑 | ✅ |

**教训**：

- **先确认你问的是不是用户真正想问的。** "集合能否满足"和"游戏能否玩"只差一个词，结论完全不同。
- **检查工具本身必须先被检查。** 用**已知答案**（这里是模拟器日志）验证，而不是看它"跑通了、输出很整齐"。
- **一个"能悄悄出错"的脚本比没有工具更危险。** 这也是改用编译型语言 + 类型系统的理由：PowerShell 那次丢占位符**静默**产生错误答案，而 C# 在编译期就会拦下这类问题。
- **别把"名字"当身份。** 文件名、区域名、集合名都可能与实际内容不符；**能验证内容时就验证内容**。
- **合并语义要看源码注释，不要凭直觉。** "子集覆盖父集"和"子集补充父集"在多数系统里都说得通，但只有一种是对的。

**最终审计结果**（`Scripts/RomAudit/`）：

- **26 / 27 个游戏家族可玩**；
- 唯一真正打不开的是 `bassdx`（缺 `mpr-20259.4` 等），**模拟器实测同样失败**；
- **24 个集合**声明了驱动板却缺其 ROM（`epr-18022.ic2` 等）→ 驱动板退化为"未连接桩"，游戏会**卡在硬件自检**，而日志里**没有对应错误**。这是本次审计最有实用价值的发现。

## 案例 17：两个"上限"各写各的，漂移出 45 万顶点的缺口

这是**移植**类项目最典型的一类 bug：**同一件事的两个限制条件写在两个地方，而且从来没被放在一起校验过。**

**症状**：Vulkan 模式下，玩到约 **2 分 40 秒**时，画面突然出现**大片黑块**（远景、路面、隧道内），并且**持续存在**。而 **New3D 完全正常**。载入存档后**恢复正常**。

**排查过程（走了不少弯路，值得记）**：

1. 先怀疑**纹理**。加了脏区块漏检器（每区块校验和），跑满 200 秒 —— **零发现**，说明标记机制完整。
2. 又怀疑**脏区块增量上传**本身。做了个粗暴实验：**每帧全量重传纹理页**（8MB/帧）。**问题依旧** —— 纹理上传被彻底洗清。
3. 转向 **VROM 几何**。在 `UploadGeometry` 里看到：

```cpp
m_romGpuVerts += count;                                 // 只增不减
if ((m_romGpuVerts + count) * sizeof(R3DVertex) <= m_rom.size && ...)   // 放不下就静默跳过
    ...
if (rom && (size_t)(mesh.vboOffset + mesh.vertexCount) > m_romGpuVerts)
    continue;                                           // ← 缺失的几何
```

于是加了**填充率日志**，跑 200 秒后直接坐实：

```
ROM geometry - 1048284 of 1048576 vertices used so far (100.0% of the buffer's capacity)
[Error] ROM vertex buffer is FULL - 1048576 vertices fit in the 64 MB buffer (64 bytes each).
        294 new vertex/vertices dropped; every mesh beyond them will not be drawn.
```

**填充曲线在约 2 分 40 秒撞顶 —— 与症状出现的时机完全吻合。**

**根因**：

```cpp
// R3DSceneBuilder.cpp —— CPU 侧：攒到多少就清空重建
#define MAX_ROM_VERTS 1500000

// Vulkan3D.cpp —— GPU 侧：缓冲区大小
CreateBuffer(64ull * 1024ull * 1024ull, ...)     // 64MB ÷ 64字节/顶点 = 1,048,576
```

| | 值 |
|---|---|
| CPU 允许累积 | **1,500,000** 顶点 |
| GPU 实际能装 | **1,048,576** 顶点 |
| **缺口** | **451,424 顶点（30%）** |

一旦 CPU 侧超过 104.8 万，GPU 缓冲就**拒绝上传**，且**静默**丢弃几何。New3D 之所以没事，是因为它按上限分配：

```cpp
// New3D.cpp:86 —— 按 MAX_RAM_VERTS + MAX_ROM_VERTS 分配，从不会不够
m_vbo.Create(GL_ARRAY_BUFFER, GL_DYNAMIC_DRAW, sizeof(FVertex) * (MAX_RAM_VERTS + MAX_ROM_VERTS));
```

**为什么"黑块"而不是"几何消失"**：丢失的是**远景/建筑等静态模型**，暴露出来的是黑色清屏色，所以看起来像贴图错误 —— 这正是它难查的原因。

**修法**：

1. **把常量移到 `VulkanCommon.h` 的单一来源** `kMaxRomVerts`，**两处共用**（这是防复发的关键）；
2. 缓冲区改为 **`kMaxRomVerts * sizeof(R3DVertex)`**，不再写死 64MB；
3. 补上**静默失败**的日志（缓冲区满、清空事件）；
4. 按实测速率把上限提到 **600 万**（约 16 分钟余量，正常赛道永不触发清空）。

**实测**：越过旧上限 104.8 万后**不再报错**，填到 21% 无异常，全程无清空。

**教训**：

- **同一个量的两个约束必须来自同一个定义。** 一个魔数出现在两个文件里，就是在等一次漂移。发现这类 bug 后，**修法不只是改数字，而是消除重复定义**。
- **"静默失败"会伪装成别的问题。** 几何上传失败 → 缺失模型 → 看起来像贴图错误。**任何"放不下就跳过"的分支都该有日志**，否则排查方向会被症状带偏。
- **量化比推理快。** 加一行填充率日志，5 分钟定位；靠读代码推理，前面白跑了两轮（纹理漏检、全量重传）。
- **移植时，"分配大小"是最容易搞错的地方。** 原版按 `上限 × 元素大小` 分配，移植时写成了字面量 —— 这类错误不会崩，只会悄悄丢数据。
- **"上限够不够"要用曲线回答，不要外推。** 修完之后有人问"600 万够吗、长时间游玩会不会又爆"，当时的依据是累积速率外推（6000/秒 → 16 分钟）。但那**默认了线性增长**，而缓存按地址去重、本应饱和。跑 13 分钟实测后曲线是：

  ```
  2.5% → 8.1% → 16.7% → 24.0% → 26.8% → 26.8% → …（57 个采样点全平）
  ```

  饱和在 **1.609M**，即容量的 **26.8%**，之后 9.5 分钟纹丝不动。**外推会得出"16 分钟就满"的悲观结论，而真实答案是"永远不会满"。** 一条有平台期的曲线，胜过任何线性假设。

- **移植时最容易丢的不是算法，是"条件分支"。** 一个宽屏选项"完全没效果"，而 3D 渲染器**确实按宽屏在渲染**：视锥展宽、视口全宽，诊断日志也报 ACTIVE。问题在**另一层** —— Vulkan 的 2D 合成器有自己的裁剪矩形（`PictureRect()`，同时供 scissor 与背景图几何使用），而它**漏了 WideScreen 这一路**（OpenGL 的 `glScissor` 有这个分支）。于是 3D 渲染出全宽画面后，**合成器又裁回 4:3**。

  这个 bug 之所以极难发现，是因为 **Hor+ 的数学性质本身就是"中央区域与窄视角逐像素相同"** —— 裁掉两侧之后，画面和没开宽屏**一模一样**。"渲染正确"和"显示正确"中间隔着一层裁剪，只验证前者会得出"功能正常"的结论。

  验证靠的是**已有的背景图诊断**（它打印画面矩形）：

  | WideScreen | game 矩形 | 黑边 |
  |---|---|---|
  | 0 | `(468,160 984x760)` | 4 条（含左右）|
  | 1 | `(0,4 1920x1072)` **全宽** | 2 条（只剩上下）|

## 案例 18：上报"配置意图"而非"实际生效状态"

**症状**：游戏内的状态读数显示 `Sync: G-SYNC/VRR`，用户据此认为自己享受到了可变刷新率。但这台机器**并没有走那条路** —— 驱动拒绝了独占全屏、或配置要的显示模式不存在，代码已**静默回退**到 borderless，而在 borderless 下 VRR 根本无法生效。

**根因**：读数从**配置**推导，而不是从**解析后的结果**取：

```cpp
// 错：读用户想要什么
const bool exclusive  = config["ExclusiveFullscreen"].ValueAsDefault<bool>(false);
const bool fixedRate  = config["ExclusiveRefreshRate"].ValueAsDefault<float>(0.0f) > 0.0f;
const char* mode = fixedRate ? "fixed arcade" : (exclusive ? "G-SYNC/VRR" : "windowed");
```

而已有代码里**本来就存在**"实际结果"这个变量 —— 回退时会被更新：

```cpp
if (s_fullScreenMode != FullScreenMode::Borderless)
{
    // 独占切换被驱动拒绝
    InfoLog("Exclusive fullscreen: refused by the display driver, falling back to borderless fullscreen.");
    s_fullScreenMode = FullScreenMode::Borderless;   // ← 事实在这里
}
```

实测复现（配置要固定 57.524，该分辨率下无此模式）：

```
[Info] Exclusive fullscreen: no 57/58 Hz display mode at 1600x1200 (rates there: 144, 120, 119, 100, 75, 60, 59).
[Info] Exclusive fullscreen: no usable 57/58 Hz display mode; falling back to G-SYNC/VRR at the desktop mode.

旧读数 → Sync: fixed arcade          ← 与事实相反
新读数 → Sync: exclusive VRR (preconditions met)
```

**修法**：把"实际状态"作为接口参数每帧传入，而不是让读数模块自己去读配置：

```cpp
enum class StatsSyncMode { Windowed, Borderless, ExclusiveVrr, ExclusiveFixedRate };

// Main.cpp：每帧，不是启动一次 —— 会话中途切全屏或显示配置变化都可能触发回退
StatsOsdSetSyncMode(StatsSyncModeForCurrentSession());
```

**为什么这类缺陷特别坏**：

- **回退路径的存在，恰恰意味着"配置 ≠ 实际"是常态而非异常。** 代码之所以要写回退，就是因为请求的东西**会失败**。所以"读数撒谎"发生的场景，正好是用户**最需要知道实情**的那些场景。
- 一个在成功时不撒谎、在失败时撒谎的读数，**比没有读数更糟** —— 它给的是虚假的安心（同案例 12 的"假通过"）。
- 用户从**其它数字的落差**能推断出不对（`Rate 57.5` vs `Panel 60`），但那要求用户比作者更懂这个系统。**读数不该要求读者自己纠错。**

**能带走的教训**：

1. **凡是带回退/降级的代码路径，就存在"两个真相"：请求的和发生的。** 状态显示必须读**后者**。
2. **报告状态时，先找"哪个变量在降级时被更新了"** —— 那才是事实来源。若没有这样的变量，说明降级是静默的，而那就是另一个 bug（见案例 14）。
3. **"不可验证的部分"要显式标注，而不是含糊过去。** 本例最终标签为 `exclusive VRR (preconditions met)`：它**声明验证了哪三个前提**（独占全屏、VSync `FIFO`、面板上限 ≥ 播放速率），而不是笼统地说 `unverified`（含糊 —— 没说清哪一半没验证），更不是写一个读起来像保证的 `G-SYNC/VRR`。

**为什么第四项天生不可观测**（不只是"API 没暴露"）：程序**刻意低于面板上限运行**，生产慢于消费 → swapchain 永远有空闲图像 → 呈现调用从不阻塞。应用唯一能测的是**自己的 sleep 时长**，而该值在变频与否两种情况下完全相同。**除非程序跑得比面板快，否则面板永远不会掐住它，也就没有可观测信号。** 想确证只能靠显示器 OSD 或厂商叠加层。

## 案例 19：抓屏"看起来成功"，但少了被测的那一层

**症状**：要验证一个**画进游戏 swapchain 的叠加层**（ImGui 读数面板）是否绘制到了正确位置。抓屏返回的**不是黑屏** —— 是一帧**完全正常、内容合理的游戏画面**，只是里面没有那个面板。于是判定"功能没生效"。

**这条和案例 9 的关键区别**：

| | 抓屏结果 | 误判风险 |
|---|---|---|
| 案例 9 | **全黑** | 低 —— 一看就知道抓取方式有问题 |
| 本例 | **内容正常，但缺被测的那一层** | **高** —— 像是目标功能自己没画出来 |

**失败的三种尝试**（都返回"可信但不对"的结果）：

- `CopyFromScreen` 抓客户区 → 拿到游戏画面，**不含叠加层**；
- 同一方法再试两次 → 拿到的是**同一块游戏内 logo**，被误读为"面板画在这里了"；
- 改用程序自带截图（`Alt+S`，复制 swapchain 于叠加层**之后**，理论上最准）→ **按键送不进程序**（`SetForegroundWindow` 返回 `True`，按键仍不生效，见案例 10）。

**真正有效的**：**不截图，改看日志**。把"算出来的值"和"要放的位置"一起写进日志：

```
Stats OSD: viewport 1600x1200 at (0,0) -> panel 24x24 at (12,12);
           sync G-SYNC/VRR, rate 57.5000 Hz (arcade 57.5242), panel mode 3840x2160@120 Hz.
```

`(0,0) → (12,12)` 直接证明锚点在左上角；`Rate` 的值与标题栏帧率交叉验证（`60.0000 Hz / 60.000 FPS`、`57.5000 Hz / 57.500 FPS`）—— **配置 → 读数 → 实际帧率三点一致**。

**能带走的教训**：

1. **抓屏失败有两种，第二种才是陷阱。** 全黑会让你换方法；"内容合理但少了被测的一层"会让你去查被测功能。**当截图看着对、功能却像没生效时，先怀疑抓取路径。**
2. **问一句：我的抓取读的缓冲区，和被测功能写的缓冲区，是同一个吗？** 注入到 swapchain / 叠加层的绘制，**不在合成器交给窗口的那份拷贝里**。
3. **人眼看到的和自动化抓屏拿到的，可以不是同一回事。** 本例中用户手动截图**能看到面板**，而脚本抓不到 —— 这不是"用户看错了"，是两条路径不同。**"我抓到的不含它" ≠ "它不存在"。**
4. **把日志从"我执行了"升级为"我算出的值是多少"。** 只记录"已到达此处"无法验证正确性；把**计算出的位置和数值**写进日志，日志就能**替代截图**做数值验证 —— 而且不受焦点、合成器、全屏模式的干扰。
5. **验证手段失效时，要能识别"这是验证工具的问题"。** 本例中三次抓屏失败都被误读为渲染 bug，浪费的都是查错方向的时间。

## 案例 20：两份"脏状态"由两个不同条件的路径消费

**症状**：`magtruck` 在独占全屏下，切到别的程序（独占全屏被系统强制最小化）、切回来再进全屏，**人物和部分场景出现黑块**。**改成 borderless 就不出现。**

**根因**：同一个写入触发**两套独立的"变了"机制**，而两者的**消费条件不同**：

| 机制 | 写入方 | 消费方（在条件内？） | 作用 |
|---|---|---|---|
| `textureRAMDirty` 位图 | `UploadTexture()` | `SyncSnapshots()` → **条件外**，每帧跑 | 把实时 RAM 拷进快照 `textureRAMRO` |
| `queuedUploadTextures` 队列 | `UploadTexture()` | `BeginFrame()` → **条件内**，窗口有表面才跑 | 告诉渲染器"这些 tile 变了" |

```cpp
if (BeginFrameVideo() && gpusReady)   // ← 最小化时为假
{
    GPU.BeginFrame();                  // ← 排空队列：被跳过
    ...
}
// 而 SyncGPUs() 在这个条件之外：
queuedUploadTexturesRO = queuedUploadTextures;   // ← 覆盖，丢弃上一帧未排空的条目
queuedUploadTextures.clear();
```

**丢数据时序**：最小化 → 队列不排空、条目滞留 → 下一帧的覆盖把它们丢掉 → 但脏位**已被消费**（快照数据已更新）→ **数据变了、通知没了** → GPU 保留旧数据且永不复知。

**修法**：把覆盖改为**追加**，让未排空的条目留存到下一次。

```cpp
queuedUploadTexturesRO.insert(queuedUploadTexturesRO.end(),
  queuedUploadTextures.begin(), queuedUploadTextures.end());
```

**能带走的教训**：

1. **一个写入 → 两条"变了"通道，是这类缺陷的温床。** 只要两条通道的**消费条件不同**（一个在 `if` 内、一个在 `if` 外），就会出现"一侧推进、另一侧没跟上"的脱节。看到"同一事件触发两套状态更新"就要问：**它们的消费条件一样吗？**
2. **检索"覆盖"语义的赋值。** `A = B` 在生产者/消费者模型里意味着"丢弃 A 之中尚未被消费的一切"。改成 `A += B` 往往是正确的最小修法。**凡是跨帧/跨线程的待处理队列，赋值前先问"旧的还在等着被处理吗"。**
3. **"只有某个特定动作才触发"是宝贵的定位信息。** 本例中"borderless 不出现"直接指向了被跳过的那条路径 —— 因为 borderless 不会被强制最小化。**把用户描述的触发条件当作约束去筛代码，比从症状反推快得多。**
4. **散布的坐标 vs 连续的坐标。** 诊断输出 11 个 tile 的坐标，它们**散布**而非连成一片 → 排除"寻址整体偏移"，指向"通知零星丢失"。**一个既有守卫的坐标输出，把范围从"纹理寻址"缩到了"上传请求"，这是整个排查的转折点。**
5. **不要轻易把既有诊断判为"误报"。** 我一度认为那个 `stale tile` 指标过于严格而忽略它，绕了三圈才回来 —— 它方向是对的。**过严的指标值得调准刻度（本例拆成 fully/partly/never 三档），而不是关掉。**
6. **复刻用户的运行环境是前提。** 用户指出"你窗口化测试、我全屏 4K G-SYNC"，而**差异不在配置本身，在于"只有独占全屏会被强制最小化"**。若继续在窗口化下测试，永远复现不出。

## 案例 21：功能与某一个后端绑定，另一个后端下静默消失

**症状**：用户在设置里勾了「统计面板」，进游戏**什么都不显示**，日志里也**没有任何报错**。而他选择了 Vulkan —— 只是启动时被静默回退到了 OpenGL：

```
[Error] Vulkan: no device offers Vulkan 1.3, ... Falling back to OpenGL for this session
[Info]  Vulkan: retrying with the OpenGL renderer (New 3D).
```

**根因**：功能与"有没有 Vulkan 上下文"绑定，而**整个初始化块被跳过**：

```cpp
if (s_vkContext)          // ← 回退后为 null
{
    OverlayInit(...);                   // ImGui 后端
    StatsOsdSetWindow(s_window);        // 面板与读数
    StatsOsdApplyConfig(...);
}
```

配置里 `ShowStatsOsd=1` **确实存在** —— 说明功能正常、用户操作正确、只是这条路径**从来没人告诉过他走不通**。

**为什么这类缺陷特别坏**：

1. **不报错、不崩溃、配置项状态还是"开"的** —— 从用户视角看，就是"功能坏了"
2. **它触发在用户最需要它的时候**：老硬件、集显、驱动受限的机器 —— 恰恰是最需要看帧率和瓶颈的人
3. **没有任何提示 = 用户不会去试另一条路**。他会以为是自己没配对，反复折腾设置

**修法（两条都要）**：

1. **让功能不依赖后端**：给 OpenGL 路径也做一份实现。本例中面板/读数/输入/快照逻辑**全部共用**，只分叉三处（每帧开始、绘制、重建时机）—— 用 `enum class Backend { None, Vulkan, OpenGL }` 做标签。
2. **如果实在做不到，就必须显式说明**：在设置项旁边写清"仅 XX 下有效"，而不是静默失效。

**能带走的教训**：

1. **凡是 `if (某个能力) { ...功能... }` 的写法，都要问：条件为假时用户看到什么？** 如果答案是"什么都没有"，那就是这个案例。
2. **"共用一个实现 + 少数分叉点"优先于"复制两份"。** 本例中两个后端的差异只有 3 处，而复制会让面板以后每次改动都要改两处 —— 而**本项目的第 31 节恰好就是"两个消费者由不同条件保护"导致的缺陷**，是同一个教训的另一面。
3. **配置项的状态必须反映真实可用性。** 勾选状态为"开"、实际却不工作，是最容易让人误判的组合。
4. **能力回退要同时通知用户**。日志写了没用 —— 用户在设置界面里，不在日志里。弹一条提示，并指向能改回来的那个开关。

## 案例 22：恢复被移除的兼容路径前，先读清当初为何移除

**症状**：想让渲染器支持更老的设备（Vulkan 1.2），而代码里**原来就有**这条路，注释说"已移除"。照原样加回来，**会在同一个地方以同样方式失败**。

**根因**：移除的原因**不在被删的那几行代码上**，而在旁边的注释里，而且涉及**另一个文件**：

```cpp
/*
 * There used to be four wrappers here ... They existed only for the Vulkan 1.2 path and are gone
 * with it: 1.3 is now a hard requirement ...
 *
 * ... It is a correctness one: the 1.2 path could not actually work as written. The shaders are
 * compiled to SPIR-V 1.6, which requires Vulkan 1.3 or VK_KHR_maintenance4, and that extension
 * was never in the required list - so the path would have failed at shader-module creation on any
 * device that reached it.
 */
```

**失败链条**：恢复分派逻辑 → 编译通过 → 运行时在 **1.2 设备上**走到 `vkCreateShaderModule` 才失败 → 报错指向**着色器**，而不是"版本要求没配对"。而手边没有 1.2 设备的话，**这个失败永远看不到**。

**修法**：两件事一起做 ——

1. 恢复运行时选路（按设备能力选核心名 / 扩展名，**一次决定、所有调用点复用**）
2. **同时修掉真正的原因**：把着色器目标从 `vulkan1.3`（SPIR-V 1.6）降到 `vulkan1.2`（SPIR-V 1.5）—— 两个版本都能加载，于是 1.2 路径没有遗留障碍

**验证手法**（值得记）：在 1.3 设备上正常**永远走不到** 1.2 分支，所以临时加钩子强制它，验证后撤除：

```
[Info] Vulkan: using ... (API 1.4, Vulkan 1.2 extension path).   ← 强制后
[Info] Vulkan: of 147987 textured draw(s): 147404 fully uploaded ← 不只是没崩
```

**能带走的教训**：

1. **注释里写着"已移除 / 已废弃"的地方，先读完整段再动手。** 移除的理由往往涉及别的模块，而"照原样恢复"会精确复现当初的 bug。
2. **被移除的路径通常不是"写得不对"，而是"依赖的前提没满足"。** 本例是版本要求没配对 —— 恢复它就要**把前提补齐**，而不是只恢复代码。
3. **无法在本地复现的设备能力分支，要主动造假条件去测。** 否则你交付的是一段"编译通过但从未执行"的代码 —— 它只会在用户的机器上第一次运行。
4. **兼容性门槛要看"实际用了什么"。** 本例中 1.3 相对 1.2 只多了两个**有扩展等价物**的特性 + SPIR-V 版本，而代码清单只有 **14 个调用点** —— 门槛是虚高的。**先清点真实依赖，再决定要不要为它放弃一整代硬件。**
5. **用运行时选路而非分叉两套代码。** 差异只有 14 个调用点时，分叉就是给自己造两份要同步维护的东西。选路写成"优先核心名、回退扩展名"的薄封装，1.3 设备**行为零变化**。
6. **包装函数静默无操作时，必须加一次校验。** `if (ptrA) A(); else if (ptrB) B();` 在两个指针都空时什么都不做 —— 对绘制命令是安全的，但应该**在设备创建时查一次并明确报错**，否则表现为"一块空屏"。

## 案例 23："支持某特性"与"该特性在此参数下可用"是两件事

**症状**：用户开了 G-SYNC，游戏稳定跑 57.5 fps，**画面还是轻微不均**。文档只写着"需要支持 G-SYNC/FreeSync 的显示器和 V-Sync"。用户只能怀疑是自己配错了、或者模拟器没做对。

**根因**：**"显示器支持 VRR"和"显示器能在 57.5 Hz 下 VRR"是两个独立条件**，而文档（和代码逻辑）只覆盖了前者。

可变刷新只在显示器**自身的最小值与最大值之间**工作。区间下限常见是 48 Hz，但**可能是 60** —— 那么 57.5 Hz **根本不在范围内**。此时驱动要么：

- 走**低帧率补偿**（面板扫 ~115 Hz、每帧重复显示两次）—— 运动均匀，但**不再是"1 帧对一次扫描"**
- 或者干脆退到最低速率 —— 表现与"未同步"的抖动一致

**而应用两样都看不到**：没有可移植接口能查询 VRR 范围，也没有接口能问"此刻驱动是否在变频"。

**修法**：**文档说清楚，并把"能确认什么"和"不能确认什么"分开陈述** ——

1. 明确写出 range 与 feature 的区别，以及低于下限的两种后果
2. 告诉用户**去哪里查**（显示器内置 OSD 的实时刷新率、显卡控制面板里列出的范围）
3. 状态读数里写 `exclusive VRR (preconditions met)` 而**不是** `G-SYNC 已启用` —— 前者说明"我验证了这三项"，后者读起来像保证

**配套的一个更一般的改进**：把**两个已知数值之间的关系算出来**。

本例中面板速率与仿真速率**都在屏幕上**（`Panel: 120 Hz` / `Rate: 57.5 Hz`），但"不整除 → 帧重复不均"这步算术没人替用户做。加一行结论就成了可解释、可行动的：

```
Cadence: uneven (2.09 panel scans per frame) - frames repeat
         unevenly; an exclusive sync mode removes this
```

**注意反向条件**：整除时显示 `Cadence: even (2 frames shown per panel scan)` 且**不提建议** —— 没问题就不该建议改设置。

**能带走的教训**：

1. **"支持 X"后面总要跟一句"在什么条件下可用"。** 硬件特性几乎都带参数范围（VRR 范围、分辨率上限、时序限制），只写"支持"等于把最容易踩的坑留给用户。
2. **能力检查要覆盖"范围"而不只是"有无"。** 本例的代码检查列不出 VRR 范围 —— 那就**必须在文档和 UI 措辞上说清"我能确认到哪一步"**，而不是含糊过去。
3. **两个已知数值的关系值得算成一句结论。** 屏幕上一堆数字，用户要自己做除法才能发现问题 —— 那就别指望他自己做。**把派生结论直接给出来**（"不整除，所以会抖，改用独占模式"），比多显示一个数字有用得多。
4. **给出建议判定时要有反向条件与判定力测试。** 只在"有问题"时报，在"没问题"时**明确说没问题且不给建议** —— 否则用户会把"永远出现的提示"当背景噪音。本例用整数倍 + 1% 容差做判据，并用"60 ÷ 120 = 2"这个必然通过的场景验证它确实会沉默。
5. **顺带**：注释里**引用符号名是有代价的**。本例中一条注释引用了两个不存在的标识符（`SpeedMode`、`ComputeTimings`），都是写注释时的臆造 —— 参照 `CModel3::RunMainBoardFrame` 才对。**引用就核实**，否则留下的是误导后人的线索。

## 案例 24：帮助文本引用了未分发的文件

**症状**：用户问"发布的版本里一直没有 `ArcadeDisplay.ps1` 啊？" —— 而界面和 README **共 5 处**让用户去运行它。发布包只含 exe + 数据 + 文档，**整个 `Scripts\` 目录不打包**。

**这不是笔误，而是一类结构性疏漏**：帮助文本、README、打包脚本**分属三个地方**，三者之间没有任何机制保证一致。改帮助文本的人**不会去看 `build.bat`**；改打包脚本的人也不知道哪句提示引用了什么。

**修法（选择"分发"而不是"删掉引用"）**：

1. **把文件真正打包**，并保留文档里已经写着的目录层级（`Scripts\`），这样**路径直接变成正确的**，不需要改 5 处文案：
   ```bat
   if not exist "%DIST%\Scripts" mkdir "%DIST%\Scripts"
   copy /y "%ROOT%\Scripts\ArcadeDisplay.ps1" "%DIST%\Scripts\" >nul
   ```
2. **修掉被分发暴露出的第二个问题**：脚本原来只认源码检出布局（`$PSScriptRoot\..\MSVC\x64\Release\Supermodel.exe`），在发布布局下找不到 exe。改为**优先找同级目录、再回退检出路径**。
3. **补上运行前提**：`.ps1` 随下载分发会被执行策略拦下，所以文档里给出
   `powershell -ExecutionPolicy Bypass -File ...`，并说明**这是让文件能跑，不是建议改系统设置**。

**能带走的教训**：

1. **"引用别人的东西"要跟着一次"它会被打包吗"。** 任何写进用户可见文案的**路径**（脚本、文档、图片、模板），都是对打包脚本的**隐含依赖**。
2. **发布一个可执行/脚本时，它的路径假设就是它的接口。** 本例中脚本硬编码了开发布局的 exe 位置 —— 打包后必然失效。**让工具在两种布局下都能找到自己的同伴**，比在文档里额外解释一遍便宜。
3. **分发会暴露只在开发环境成立的前提。** 脚本在本仓库里跑得好好的，打包后立刻坏 —— 而**这类问题只有真的打包一次才会出现**。所以"从发布目录跑一遍"是必要的验证，不是可选的。
4. **补齐引用比删除引用更值得。** 直接删掉那 5 处引用成本更低，但那个工具本身是有用的（列模式、切换、退出后恢复桌面）。**先问"这功能还该存在吗"，再决定是补分发还是删引用。**

## 案例 25：两个选项在某种配置下等价 —— 应禁用其一，而非静默等价

**症状**：用户问"如果显示器不支持，独占 G-SYNC 这个选项应该变成灰色不可选吧？"

查下来，**"固定街机刷新率"在任何情况下都可选**，只是选中后警告"会回落到 G-SYNC"。而它回落到的是——**上面那个选项**：

```cpp
if (FindArcadeDisplayMode(refreshRateHz, mode) && SDL_SetWindowDisplayMode(...) == 0)
    return FullScreenMode::ExclusiveArcade;
// 找不到 → 返回 ExclusiveDesktop，也就是 G-SYNC 那个模式
```

**没有 57/58 Hz 模式时，两个选项产生的结果完全相同。** 两个选项做同一件事、其中一个还描述了别的东西 —— 比一个"不可用且说明原因"的选项更糟。

**修法**：**真正禁用**（`ImGui::BeginDisabled`）并保留说明：

```
未检测到 57/58 Hz 模式，因此此项不可选：选了也只会回落到上面的 G-SYNC。
```

**同时修掉一个陈旧缓存**：原来是 `static const bool`（**进程内只算一次**）。而设置窗口的存活时间长于"用户去驱动控制面板建自定义分辨率"这个动作 —— **自然的顺序正是"看到提示 → 去建 → 回来"**，缓存会一直说"不可用"，读起来像 bug。改为**按帧节流**复查（约 2 秒一次），于是提示可以写"**创建后自动生效**"，不需要重启。

**同一个原则，另一项故意不禁用**：用户同时建议"G-SYNC 不支持也置灰"，但 **VRR 可用性在当时的判断里无法检测**（见案例 26 —— 这个判断后来被证明是错的，VRR 范围确实能从 EDID 读到）。**基于猜测去禁用比说明"什么是未知的"更糟** —— 所以那一项只是把要求写出来并指出去哪查。

**能带走的教训**：

1. **核对"选项 A 的回退目标"与"选项 B"是不是同一个。** 只要有回退链，就可能存在**两个选项等价**的配置。等价时应该禁用其一，否则用户以为自己在做选择。
2. **"选了会回落到 X"这种提示，说明选项本身就不该可选。** 提示是补救，禁用才是正确表达。**能检测的条件就检测并禁用；不能检测的就说清楚并指出去哪查** —— 两者判据是同一条，但形式不同。
3. **可用性检查不要缓存到进程级。** 被检查的对象（显示器配置、驱动设置、外接设备）**可能在进程存活期间变化**，而用户的操作顺序常常正是"看到提示 → 去改 → 回来"。**缓存要有时限**（或按事件失效），否则"改了没用"会被读成 bug。
4. **禁用时要给出原因和出路。** 一个灰掉的控件没有解释就是死路；附上一行"为什么 + 怎么做"才让它可操作。

> 项目内详见 `TECHLOG.md` 第 35.2 节。

## 案例 26：把"我用的这条解析路径没有"当成"数据不存在"

**症状**：为回答"能不能检测显示器是否支持 VRR"，我解析了显示器 EDID，得出"EDID 里没有任何 VRR 声明"，并把这个结论写进了 README、代码注释和两份文档。**结论是错的。**

**错在哪**：我只遍历了 CTA-861 扩展块里的**扩展标签**（顶层 `tag == 7`），去找扩展标签 `0x01`(VSVDB) 与 `0x2A`。而自适应同步声明在**顶层 `tag == 3` 的 VSDB** 里 —— 同一个字节域里的**另一类**标签，我根本没查。

补上后的原始字节：

```
offset 24: 标签字节 0x74 → tag 3 (VSDB) len 20
      载荷: 1A 00 00 03 0F 30 90 00 00 60 08 5B 36 90 00 00 00 00 00 00
      → OUI = 00-00-1A   （AMD / VESA Adaptive-Sync）
         byte[5] = 0x30 = 48
         byte[6] = 0x90 = 144
```

**VRR 范围一直都在那里。**

**为什么会犯这个错**：CTA 块的数据标签是**两级结构** —— 顶层 3 位标签（1=Audio、2=Video、**3=VSDB**、7=扩展标签），其中 `tag 7` 之下还有**第二级扩展标签**。我第一次解析选择了 `tag 7` 这条支路，还拿到了一个看似相关的结果（OUI `90-84-8B` 的 VSVDB），**于是以为覆盖全了**。**"查到了一些"比"什么都没查到"更危险** —— 它让人停止继续查。

**修法**：遍历时**穷举所有顶层标签**，不只走自己想到的那一条；注释里写明两类标签并存、以及"只看 tag 7 会漏掉"这个具体的坑。

**并保留最有价值的一点 —— 不对称**：

| 情形 | 结论 |
|---|---|
| **声明了范围** | 报为**事实**：支持 VRR，范围如此 |
| **没有声明** | **什么都不报**，绝不写"不支持" —— 支持 VRR 可以不在 EDID 里声明（旧版 AMD HDMI FreeSync 正是如此） |

**能带走的教训**：

1. **"我在这个位置没找到" ≠ "它不存在"。** 二进制格式、协议、注册表这类**多支路/多层级**结构里，"没找到"首先应怀疑**自己走错了支路**。
2. **多级标签结构要穷举，不要只走想到的那一条。** 本例顶层标签有 8 种、扩展标签又几十种；只查一支就下结论是结构性错误。**先列一张"总共有哪些支路"的清单。**
3. **"查到了一些东西"会让人停止怀疑。** 我第一次拿到过一个看似相关的 VSVDB，于是认为已覆盖 —— **部分成功比完全失败更容易掩盖遗漏**。
4. **否定性结论要标注置信度，或干脆不给。** 那句"EDID 里没有 VRR 声明"进了用户文档，而它是错的。**凡"X 不存在"的断言，先问"我用了几条路径去找"。**
5. **同一个错误常被复制到多处 —— 更正时必须一并处理。** 该结论当时出现在代码注释、README、`TECHLOG.md`、`FIXES.md` 四处，漏改一处就留下自相矛盾的文档。
6. **更正后要重新检查"基于这个错误结论做出的设计决定"。** 本例中"G-SYNC 项不禁用"的部分理由是"无法检测" —— 更正后理由只剩下一半（真正的理由是**基于猜测禁用更糟**、且**无声明不等于不支持**），所以那段代码注释也一并重写了。

> 项目内详见 `TECHLOG.md` 第 35.11 节。

## 案例 27：在批处理文件里混用"代码页切换"与"非 ASCII 文本"

**症状**：给一个 `.bat` 加了中文注释，运行时出现一串莫名其妙的报错：

```
'??关闭，以便看清??' is not recognized as an internal or external command
'?异常，请先检查这一行是否还在最前面??' is not recognized as an internal or external command
```

**报错的文本正是我写的 `rem` 注释内容** —— 注释被当成命令执行了。

**最小复现**（4 行文件）确认了规律：

```bat
@echo off
chcp 65001 >nul 2>nul
rem 中文注释测试          ← 这一行报错
echo   [提示] 中文输出测试  ← 这一行正常
```

输出：
```
'中文' is not recognized as an internal or external command
```

**根因**：`cmd.exe` 执行 `.bat` 时**按字节偏移重新定位文件读取位置**，而该偏移是在**解析该行时生效的代码页**下算出来的。文件中间一句 `chcp 65001` 改变了代码页，于是后续每行的偏移都不再对齐，**行首的 `rem` 被吞掉，剩余文本当命令执行**。

这解释了为什么 `echo` 的中文能正常输出（那是**运行时**的字节），而 `rem` 的中文会炸（那是**解析时**的关键字定位）—— **同一份文件里两种中文的成因完全不同**。

**试过的三条路**：

| 方案 | 结果 |
|---|---|
| `.bat` 里写中文注释 | ✗ 被当命令执行 |
| `.bat` 里输出中文 | ✓ 字节正确，但同文件有中文注释时会连带损坏 |
| `.ps1` 里写中文（无 BOM） | ✗ **连读取都失败**：字符串未闭合、语法报错 |
| `.ps1` 里写中文（**有 UTF-8 BOM**） | ✓ 逐字节正确 |

**修法：把所有非 ASCII 文本集中到一个带 BOM 的 `.ps1`，`.bat` 保持纯 ASCII。**

| 文件 | 编码 | 内容 |
|---|---|---|
| `X.bat` / `X-zh.bat` | **纯 ASCII（0 个非 ASCII 字节）** | 只做启动，传语言参数 |
| `X.ps1` | **UTF-8 带 BOM** | 全部本地化文本 |

两种语言的前言**并排放在同一个哈希表里**，不会各自漂移；而**给维护者看的注释是英文、给用户看的输出才分语言**，本来也更合理。

**能带走的教训**：

1. **批处理文件不是普通文本文件 —— 它的解析依赖字节偏移与代码页。** 在同一份 `.bat` 里既切代码页又放非 ASCII 文本，会触发这类**只在解析期**出现的问题。
2. **"同一份文件里两种用法结果不同"是重要线索。** 本例 `echo` 中文正常、`rem` 中文报错 —— 顺着这个差异才发现根因在**解析时机**而非编码本身。
3. **`.ps1` 里的非 ASCII 需要 UTF-8 BOM。** 无 BOM 时 Windows PowerShell 按系统代码页读取脚本内容，中文会被读坏（症状是"字符串未闭合"这类语法错误，而不是"显示乱码" —— **很容易误判为代码写错**）。
4. **写进注释，防止后人"顺手改回去"。** 我在 `.bat` 和 `-Lang` 参数处都写明了"为什么必须纯 ASCII、为什么 PS1 必须有 BOM"，否则后来者很可能把中文加回 `.bat`、或去"清理"那个看起来多余的 BOM。
5. **宁可架构上规避，不要依赖特定环境的宽容。** 即使某个代码页组合下能跑，也不该让正确性取决于用户的系统语言设置。

> 项目内详见 `TECHLOG.md` 第 35.12 节。

## 案例 28：把"必要条件"当成"充分条件"来陈述

**症状**：用户在 60Hz 笔记本屏上运行，预期"应该会被测出**不支持**非标准刷新率"。实测是 **恰好相反**：被判为"在范围内"。

**根因**：被检查的量（EDID `0xFD` 时序范围）只能证明**必要条件**，而措辞写成了结论。

原始文案是「57.5Hz 在时序范围内，**自定义分辨率可创建**」。但检查实际只说明**面板电子部分声明的同步范围包含该值**，并不说明：

- 显卡驱动是否**开放**自定义分辨率（**笔记本 eDP 面板常常根本不开放**）
- 端口带宽是否够（如 HDMI 1.4 的像素时钟上限）
- 面板 scaler 是否真的 1:1 透传

**而实测数据揭示了一个反直觉的事实**：57.5Hz 只比 60 低 4%，所以**它几乎总落在任何现代面板的垂直范围内**。本机 S24F350（75Hz 屏）报 `50-75 Hz`，60Hz 笔记本屏通常报 `48-60` 或 `50-60` —— **全都包含 57.5**。

**所以"60Hz 屏会被测出不支持"这个预期是错的，检查很少给出否定结论。**

**修法：区分两种结论的强度，并照实陈述。**

| 情形 | 可靠性 |
|---|---|
| **不在范围内** | ✓ **可证** —— 面板不会锁定到它未列出的时序 |
| **在范围内** | ✗ **只是必要条件** |

```
57.5Hz 在面板时序范围内——这只是必要条件；能否真正创建还取决于显卡驱动是否开放自定义分辨率
57.5Hz 不在面板时序范围内，该显示器无法接受此时序，创建自定义分辨率无用
```

**能带走的教训**：

1. **写结论前先问：这条数据能证明到哪一步？** "在范围内"和"能做到"之间隔着驱动、端口带宽、scaler 三道关。**能证明必要条件的措辞，不要写成能证明结论的措辞。**
2. **过度承诺在用户最没辙的地方伤害最大。** 本例中受影响的是**笔记本用户** —— 他们既无法创建自定义分辨率，也没有别的替代选项。承诺落空时，他们无从补救。
3. **反直觉处最值得实测。** 用户的预期（60Hz 屏 → 不支持）直觉上很合理，但没有数据支持。**一测就发现方向完全相反** —— "57.5 只比 60 低 4%"这个简单事实，决定了这个检查几乎从不给出否定结论。
4. **区分"可证"与"只是必要条件"，并让它体现在措辞里。** 这与案例 23（VRR 声明：有则可信、无则未知）是同一原则的**反向**应用 —— 那里否定无意义，这里肯定不充分。**共同点是都不给超出数据支撑的结论。**
5. **顺带记下"为什么不做某事"**：本例中水平频率不显示、更低垂直频率不支持，两者都记录了**理由**（派生量且部分面板报退化值；Model 3 只有 57.524160 一个硬编码速率）。否则同样的建议会被反复提出。

> 项目内详见 `TECHLOG.md` 第 35·补三 节。

## 案例 29：全屏画面上下被裁 —— 渲染分辨率被当成了窗口尺寸

**症状**：把模拟器输出到副屏全屏时，画面最上面少了一截，上下各被切掉一块。同一份配置在主屏上完全正常。

**定位过程**（每一步都留下证据，因为最容易停在第一个说得通的解释上）：

1. 打印窗口尺寸与显示器尺寸对比 —— 窗口 **2976x2304**，副屏 **1920x1080**。第一层解释成立：窗口比屏幕大。
2. 查来源：`XResolution/YResolution`（用户设的 6x 超采样 = 496×6, 384×6）**同时被用作窗口尺寸**。
3. 但**同一份配置在主屏上是 2976→3840 之类的正确结果**。说明"分辨率太大"不是完整答案 —— 主屏能自动纠正，副屏不能。
4. 于是查全屏到底把我们放在多大一个窗口里：打印 `SDL_GetWindowSize` → 副屏上**仍是 2976x2304**，4K 上被改成了 **3840x2160**（= 屏幕尺寸）。**差异就在这一步**。
5. 查为什么副屏没被纠正：全屏走 `SDL_SetWindowDisplayMode`，参数取自 `SDL_GetDesktopDisplayMode` → 副屏报 **2880x1620**。
6. 算一下：2880x1620 = 1920x1080 × **1.5**，而 **1.5 正是主屏的缩放**。副屏自己没开缩放。
7. 成因确认：进程只声明 **system DPI aware**（`SDL_HINT_WINDOWS_DPI_AWARENESS=system`），Windows 于是把**与系统 DPI 不一致**的显示器几何换算进系统 DPI 空间。副屏 100%、主屏 150% → 副屏被换算。
8. SDL 不补偿：`dpi_scaling_enabled` 只在 `SDL_HINT_WINDOWS_DPI_SCALING` 为真时开启（默认关，本项目没设），所以 SDL **原样透传**虚拟化后的值。
9. 结论链闭合：`SDL_SetWindowDisplayMode(2880x1620)` 失败（**面板上没有这个模式**）→ 进入全屏时**窗口尺寸不变** → 保留创建时的 2976x2304 → 超出屏幕 → 窗口居中 → **上下各裁掉 (2304-1080)/2 ≈ 612 px**。

**根因是两条，彼此独立，但必须一起才能解释症状**：

| | 根因 | 后果 |
|---|---|---|
| **A** | 请求的**渲染分辨率**被当作全屏**窗口尺寸**使用 | 窗口比屏幕大 |
| **B** | 全屏切换用的"桌面模式"取的是 SDL 的 **DPI 虚拟化尺寸**，而非面板真实模式 | 切换失败，A 的后果没被纠正 |

只有 A 时（主屏的情形）全屏会顺手把窗口缩到屏幕大小，所以看不出来；只有 B 时窗口尺寸本来就合适，也看不出来。**两个条件同时成立才暴露。**

**修复**：

1. `ApplyWindowSize()`：全屏用**显示器尺寸**，窗口模式才用请求分辨率 —— 窗口模式下它确实就是一个窗口尺寸，那时是对的。
2. `ReadPanelMode()`：用 `EnumDisplaySettings(ENUM_CURRENT_SETTINGS)` 取**面板真实模式**，替换 SDL 那个尺寸（保留它的刷新率）。
3. 加两行日志：`window size WxH`（与后端的 `swapchain WxH` 并列，两者不一致就是这个 bug 的签名），以及每显示器一行，虚拟化尺寸与面板尺寸并排。

**验证**（同一份 ini，只换显示器）：

| | 设置的模式 | 全屏窗口 | 交换链 |
|---|---|---|---|
| 副屏（修复前） | 2880x1620（**面板上不存在**） | 2976x2304 ❌ | 2976x2304 |
| 副屏（修复后） | **1920x1080** | **2880x1620** ✅ | 2880x1620 |
| 主屏（回归） | 3840x2160 | 3840x2160 ✅ 未变 | 3840x2160 |

**能带走的教训**：

1. **两个语义不同的量共用一个数字，迟早会在某个条件下分叉。** "渲染多少像素"和"窗口多大"在全屏下不是一回事，只是常常碰巧相等。
2. **不要停在第一个说得通的解释上。** "分辨率设太高了"对副屏成立、对主屏不成立 —— **这个不一致本身就是最好的线索**，它把问题从"数值大小"推到了"机制差异"。用户报告的主屏正常/副屏异常，价值就在于此。
3. **同一 API 的不同入口可能给出不同空间的值。** `SDL_GetDisplayBounds` 与 `EnumDisplaySettings` 在这里不一致，而后者才是驱动认可的、显示器 OSD 也认的那个。
4. **DPI 虚拟化看的是"与系统 DPI 是否一致"，不是"自己有没有开缩放"。** 用户一开始就指正了这一点：副屏没开缩放，但主屏开了 150%，副屏照样被换算。
5. **顺手让日志能自证。** `window size` 与 `swapchain` 并列、虚拟化尺寸与面板尺寸并列 —— 下次同类问题不需要再花一轮实验去构造对比。

## 案例 30：界面在"推测"而不是"测量"—— 显示了一张根本不是它在用的显卡

**症状**：OpenGL（New 3D / Legacy 3D）模式下，设置界面的"显示设备"是一个**置灰、只有一个选项**的下拉框，显示着某块显卡的名字并标注"已锁定独显"。用户问：为什么不让我选？万一我想换卡测试呢？

**两层问题，第二层才是真问题**：

1. **O盘的客观限制**：OpenGL 没有设备枚举 API，应用无法选择适配器 —— 这是事实，所以"不能选"是对的。
2. **但它显示的名字是猜的**：名字来自 **Vulkan** 设备列表，按 `NVIDIA`/`AMD` 关键字匹配。**实际渲染的卡本可以直接测**（`glGetString(GL_RENDERER)`），而且我们**早就在日志里打印它了**。

**为什么猜是错的**：那两个进程级标志（`NvOptimusEnablement` / `AmdPowerXpressRequestHighPerformance`）只是**请求** —— 驱动可以忽略，OS 的按应用显卡设置也能覆盖它。一旦被忽略，界面会**准确地显示一块没有在渲染的显卡**，而用户没有任何途径发现。**把已知事实换成推测，是纯粹的功能退化。**

**验证**（本机双显卡 RTX 5060 Ti + Intel Arc）：

```
OpenGL: settings window context is on "NVIDIA GeForce RTX 5060 Ti/PCIe/SSE2".
```

New 3D 与 Legacy 3D 都落在独显上 —— 标志确实有效。**但这是测出来的，不是猜的**，两者对用户的价值完全不同。

**修复**：设置窗口的 GL 上下文建立后读一次 `GL_RENDERER`，界面显示实测值；换卡指引指向 Windows 图形设置，并**明说该设置是否对 OpenGL 生效由驱动决定、程序无法检测**。

**同一轮里另一个"只报症状不给数值"的地方**：无边框模式报 `Cadence: uneven` 却不说**目标是多少**。而目标是可以算的（57.5 的整数倍），且能直接填进自定义分辨率对话框。补上 `even at Nx = ... Hz`。顺带纠正一个直觉错误：**240Hz 与 480Hz 都不均（4.17x / 8.34x），而 230Hz 均匀（3.998x）** —— 面板越快不等于越接近整数倍。

**能带走的教训**：

1. **能测量的就别推断。** 凡是"程序本来就知道，却显示了一个推导值"的地方，都在制造一种用户无法察觉的错误。**先问"这个值我是测的还是猜的"。**
2. **客观限制要如实说明，但不能用猜测去填补它。** "OpenGL 做不到"是诚实的；"所以显示一块猜出来的卡"不是。
3. **"请求"不等于"结果"。** 一个 hint/flag 的语义是"我希望"，把它呈现成"已生效"就是过度承诺 —— 与案例 23、28 同一原则。
4. **报出症状时，一并报出目标值。** "不均"不是一个可执行的结论；"even at 2x = 115.00 Hz"是。**用户拿着数字才能动手。**
5. **反直觉的地方值得实测。** "更高的刷新率更接近整数倍"听起来合理，实际相反 —— 因为基频不是整数。
6. **顺带记下接口的不对称**（有 `-vulkan3d` 无 `-no-vulkan3d`），否则同样的疑问会被反复提出。

> 项目内详见 `TECHLOG.md` 第 35.14 节、`SYNC.md` 第十、十一节。

## 案例 31："不可能"是相对的 —— 一个被驱动选项推翻的前提

**症状**：用户指着 NVIDIA 控制面板「设置 G-SYNC」页上的一项设置问：*无边框模式到底走 Windows 的 120Hz，还是说 NVIDIA 其实支持桌面下也启用 G-Sync？*

**这条提问推翻了我们 6 处以上的断言**：

```
Main.cpp:241    // general purpose: desktop-sized composited window (VRR cannot engage)
Main.cpp:615    // Borderless fullscreen cannot do either, because Windows DWM keeps composing
                // at the desktop refresh rate and also prevents VRR from engaging.
Main.cpp:2652   * Borderless fullscreen cannot use VRR, so the panel keeps its own rate...
StatsOsd.cpp    * Borderless fullscreen cannot use VRR - the desktop compositor keeps...
StatsOsd.cpp      syncMode = "borderless, VRR off";
ArcadeDisplay.ps1  ...does not engage in windowed or borderless fullscreen because DWM...
```

**错在哪**：NVIDIA 提供把 G-SYNC 应用于**窗口输出**的选项（「为窗口和全屏模式启用」；驱动默认是「仅全屏模式」）。开了它，无边框窗口——在 DWM 看来仍是窗口——就能让显示器跟随应用。**"DWM 阻止 VRR"只在默认设置下成立。**

| 该设置 | 无边框下面板 |
|---|---|
| 仅全屏（默认） | 120Hz，帧被不均匀套接 |
| 窗口和全屏 | **~57.5Hz，1:1，画面可能完美** |

**后果不只是注释不准，而是读数会误报**：`Cadence: uneven (2.09)` 假设面板在自身速率上。若窗口 VRR 已生效，面板跟着应用走、画面没问题 —— **我们却报了一个不存在的问题。**

**为什么修不了逻辑**：两种情况对应用**完全无可观测差异** —— 都以相同速率呈现、都报同样的 FPS。（这正是案例 22、29 之后第三次撞上同一个"没有信号"的边界。）所以只能改措辞：

```
Sync: borderless (panel keeps its own rate)          ← 原为 "borderless, VRR off"
Cadence: uneven if panel @ own rate (2.09 scans per frame)
         (assumes the panel is at its own rate; driver windowed
          VRR would override this - check the display's readout)
```

日志与设置界面的提示也一并加上 —— 并且**明确指出唯一的验证途径是显示器自己的 OSD**（~57-58Hz = 已生效），因为在程序内无从判断。

**同时把这条新知识登记为"未验证"**：该选项确实存在，无边框按 DWM 语义也应当适用，但我**没有实测确认**（读不到显示器 OSD），所以文档写"可能"而非"是"。

**能带走的教训**：

1. **"不可能"通常是"在某个前提之下不可能"，而前提往往不在你的代码里。** 本例的前提是驱动的一项设置。写"cannot"之前先问：**这条依赖什么外部配置？**
2. **被推翻的断言不止出现在一处。** 同一个信念被复制到 6 个位置（注释、日志、界面字符串、脚本头），说明它是**一个前提**而不是一处笔误 —— 修的时候要**全文搜同一个句子**。
3. **错误的前提会让"工具"变成"误报源"。** 注释写错只是难看；读数报错问题会让用户去修一个不存在的问题 —— 这比不报更糟。
4. **无信号时，把断言降级为前提，并给出唯一可执行的自查方式。** 与案例 22、28 同一条原则：不给超出数据支撑的结论，同时告诉用户去哪里能看到答案。
5. **新知识也要标注证据等级。** 用户提供的信息（该选项存在）是可靠的；"它对我们这种窗口生效"是我的推断 —— 所以要写成"可能"并注明未验证。这正是本文档"实测/未验证"分栏的意义。

> 项目内详见 `TECHLOG.md` 第 35.15 节、`SYNC.md` 第 2.1 与 7.2 节。

## 案例 32：把"正确"当成"该显示"—— 界面被诊断信息淹没

**症状**：用户反馈设置页里长段说明文字太多、界面显得乱；同时指出 `输出显示器` 把主屏显示成"5 号"（"我的 Primary 是 G70D，为什么显示成第 5 号选项?"）。

**第一条的成因是一个累积过程，不是单次错误**：为了把诊断做准，每确认一个新结论就补一段说明 —— 输出显示器说明、怎么选、无边框例外、G-SYNC 要求、固定率不可用说明、OpenGL 换卡指引。**每一段都正确**，但界面上因此有 6 处多行散文。**正确不等于该常驻显示。**

**第二条是"内部标识当成了用户语言"**：`\\.\DISPLAYn` 的编号会跳号（本机主屏是 DISPLAY5），所以最重要的那台显示器看起来最反常。

**修法**：

| 界面只留 | 收进 `(?)` 提示 |
|---|---|
| 用户硬件的读数 + 一行结论 + 控件 | 背景、例外、为什么、怎么办 |

角色标签取代编号：

```
自动 · 跟随系统主显示器
主显示器 · Odyssey G70D  3840x2160 @120Hz  · #5      ← 原为 "5: Odyssey G70D ..."
副显示器 · S24F350  1920x1080 @60Hz  · #1
```

`MONITORINFOF_PRIMARY` 为权威来源（原先靠 SDL 顺序推断）；编号以 `#n` 保留在末尾供脚本使用；**"副显示器"仅在恰好一台非主屏时使用**（3 台以上没有唯一副屏，编造序号更糟）。

**验证**：截屏放大读字 —— `主显示器 · Odyssey G70D  3840x2160 @120Hz  · #5`。

**过程中发现并修掉自己引入的一个缺陷**：显示器日志写在缓存重建路径里，而缓存每 2 秒过期 → **每 2 秒重复一遍**。改为按内容签名比对，仅在列表真正变化时打印（实测 14 秒内仅 1 次）。

**能带走的教训**：

1. **"正确"和"该显示"是两件事。** 诊断越做越准的副作用就是界面越写越长。需要一个分流判据 —— 本例用的是**"这是数据还是解释"**，够用且不易争议。
2. **但判据要有例外，且例外要能识别。** 用户先前**明确要求**高亮显示硬件型号和 Hz，所以硬件读数必须留在界面上 —— 若照"一并收进提示"处理，就会推翻一个已经被采纳的需求。**分流时先查"这条是不是用户点名要的"。**
3. **内部标识不要当标签主语。** 编号 / ID / 端口名对程序必需、对用户无用，而且**跳号的编号会让最常见的那一项看起来最反常** —— 这正是用户觉得别扭的原因。
4. **保留标识的可及性，而不是保留它的显著性。** 编号仍然要能拿到（存配置、传脚本、对接「标识」），所以放在末尾 `#n` 并写进提示，而不是删掉或提到最前。
5. **修界面时顺带查自己刚加的东西。** 这一轮改的是界面，却在同一次验证里发现并修掉了自己上一轮引入的日志刷屏 —— **每次重测都是复查已有改动的机会。**

> 项目内详见 `TECHLOG.md` 第 35.16 节、`SYNC.md` 第 9.2 节。

## 案例 33：不要用低分辨率截图去"核对"一个字符串

**背景**：为验证新加的一行读数，用 `PrintWindow` 截取游戏窗口，再做琥珀色分离、放大读取。在 `Sync:` 那一行读到了 `Sync: windowed, VRR off`。

**由此可能得出的错误结论**："界面显示的文案和源码不一致" —— 而当时源码里根本没有 `VRR off` 这个串，所以看上去像个真 bug（甚至是旧二进制没更新的问题）。

**真正解决它的是查二进制，不是看图**：

```
含 'VRR off' : False
含 'windowed': True   → 独立字符串 "windowed"
```

**exe 里没有那个串，就说明它不在屏幕上。** 于是回头复查：琥珀色分离用的阈值太宽（`R-B>60 && R>120`），把游戏画面里色调相近的内容一起变成了黑字，读起来像是同一行的后续文字。收紧阈值后重截，得到的是干净的 `Sync: windowed`。

**教训**：

1. **核对字符串要查二进制或源码，不要查截图。** 前者是二值事实，后者要经过缩放、插值、阈值、人眼四道有损环节。**一个问题"看上去像 bug"和"是 bug"之间，隔着一次廉价的机械核对。**
2. **怀疑旧二进制时要查哈希和时间戳，不要靠外观推断。** 本例真正排除"exe 没更新"的，是对比两个 exe 的 MD5 与 mtime，以及直接在二进制里搜新旧串。
3. **图像阈值处理是"有损的证据"，用它可以发现，不足以确证。** 宽松阈值会造出**不存在的文字**；收紧后才可信。凡是靠阈值/插值得到的读数，只能当线索。
4. **顺序上先做最便宜、最确定的检查。** 这次浪费的几轮，都花在反复裁图放大上；而 `IndexOf("VRR off")` 一行就能给出答案。**先问"哪个检查最接近无歧义"，再动手。**
5. **顺带记下源文件 mtime 与 exe mtime 的先后** —— 本例中两者顺序一度看起来矛盾，追查后确认是重构建顺序造成的噪声，而不是真的漏编译。**时间戳能帮你排除一类假设，但也可能引入虚假的因果。**

> 项目内详见 `TECHLOG.md` 第 35.17 节。同一轮里 `Render:` 行本身是**屏幕与日志双向核对**通过的。

## 案例 34：只在"恰好一台显示器"的机器上失败的脚本

**症状**：用户在自己的**笔记本**上双击 `Scripts\ArcadeDisplay-zh.bat`，得到

```
The property 'Count' cannot be found on this object. Verify that the property exists.
    + FullyQualifiedErrorId : PropertyNotFoundStrict
```

而同一个脚本在**两台显示器的台式机**上一分钟前还跑得好好的。

**根因**：PowerShell 在函数返回时会**展开集合**。

```powershell
# ArcadeDisplay.ps1（修复前）
$monitors = Get-Monitors | Sort-Object Number    # Get-Monitors 返回 List[object]
if ($monitors.Count -gt 1)
```

| 显示器数 | `$monitors` 实际类型 | `.Count` |
|---|---|---|
| **1** | **标量 PSCustomObject**（被展开） | ✗ `PropertyNotFoundStrict` |
| 2 | `Object[]` | ✓ = 2 |
| 0 | `$null` | ✗ 同样抛错 |

脚本开头有 `Set-StrictMode -Version Latest`，访问不存在的属性直接抛错，整个脚本中止在列模式之前。

**修复与验证**：`@(Get-Monitors | Sort-Object Number)` —— 已复现原失败（1 台抛错 / 2 台正常），并验证 `@()` 后 0/1/2 台全部正常；真实脚本退出码 0。同时把"返回单元素时会被展开、需要 `.Count` 的调用方要包 `@()`"写进 `Get-Monitors` 的注释。

**能带走的教训**：

1. **"在我机器上是好的"这句话，要问"我的机器和对方差在哪一个维度"。** 本例差的不是版本、不是架构、不是驱动 —— 是**显示器数量**。而那个维度恰好是这段代码刚加的新功能所依赖的，所以它从未在单显示器下被走到过。
2. **缺陷会集中出现在"最少见的那台机器"上。** 单显示器笔记本是最没条件绕过问题的环境：用户既不能换个显示器试，也不容易想到"这是机器相关"。
3. **PowerShell 的集合展开是静默的。** `return $list` 与 `return @($list)` 在调用方看来类型不同，而类型不同只在`.Count`/索引这类操作上才暴露。凡是"数量"参与判断的地方，一律 `@()`。（这一点与案例 27 的 `NullString` 同源：**PowerShell 的参数/返回值转换会在你不注意的地方改变语义。**）
4. **修完顺手写进被调用方的注释。** 同一个 helper 会被再次调用，而陷阱不在调用点、在返回值的契约上。

## 案例 35：`exclusive VRR (preconditions met)` 在一个不能变频的面板上

**症状**：用户笔记本人报告 —— 屏幕显然不支持 57.5Hz，但读数里同时出现两行看起来矛盾的内容：

```
Sync:  exclusive VRR (preconditions met)
Rate:  57.50 Hz  arcade 57.52  (-0.04%)
Panel: 1920x1080  60 Hz mode
```

**先分清两件事**：

- **`Rate:` 不是面板刷新率**，是模拟器自己的**配速目标**（来自 `RefreshRate` 设置）。面板的真实速率在 `Panel:` 行（60Hz，正确）。
- 所以"显示 57.5Hz"本身不是错误，是**两行在说不同的事**。这属于可读性问题，不是缺陷。

**真正的缺陷在后面**：`Cadence:` 那一行**只对无边框模式绘制**（`StatsOsd.cpp`），设计理由是"独占模式要么让面板按模拟器速率扫描、要么让 VRR 跟随它"。但在**不支持 VRR 的面板上 `ExclusiveDesktop` 两者都不是** —— 面板仍钉在 60Hz，57.5 帧被套接上去。**这正是无边框的帧节奏问题**，可读数在这里既不报警也不给 `Cadence:`。

该用户日志里两种模式恰好都出现过，对照极其清楚：

```
独占 VRR ：（无 Cadence 行）
无边框   ：Stats OSD: cadence uneven - 1.0435 panel scans per frame.
```

`1.0435` = 60 ÷ 57.5 ✓ —— **同一台机器、同一个面板、同一份内容，只因为换了个同步模式，问题就从"不显示"变成"显示"。**

**修法（保持诚实，不假装能检测）**：把 `ExclusiveVrr` 纳入帧节奏判断，措辞按模式区分：

| 模式 | 措辞 |
|---|---|
| 无边框 | `uneven if panel @ own rate` + 窗口 VRR 可能覆盖 + 显示器 OSD 自查 |
| **独占 VRR** | `uneven if VRR is not engaging` + "VRR 只在显示器真的变频时才是 1:1" + 固定率模式可消除 |

**一个顺带的重要结论**：`Even` 这一档在独占 VRR 下**不需要任何限定语** —— 若面板自身速率是模拟速率的整数倍，那么 VRR 变频与否都是均匀的。这反而是个更强的陈述，所以 `Even` 在独占 VRR 下不写"如果"。

另外**独占固定率被显式排除**：那种模式下 `SetWindowDisplayMode` 已把面板切到 57/58Hz，`SDL_GetDesktopDisplayMode` 会读到 57 —— 与 57.5242 相除得 0.991，会**把 1:1 的整数取整误报成"不均"**。这个 guard 是代码级保证，但**没能在现有硬件上实测**（两台机器都没有 57/58Hz 模式）。

还补了一条实用提示（用户要求）：**多数笔记本内屏不支持 VRR**，这类机器上"独占 VRR"与"无边框"等价，可以留在无边框。

**能带走的教训**：

1. **"只在 A 模式适用"的规则，要问"A 模式的边界之外会退化成什么"。** 这里退化的结果是**恰好等于 B 模式**，而 B 模式有诊断、A 模式没有 —— 于是诊断能力最强的那个模式反而最安静。
2. **同一台机器出现两种相反解释时，先找出能区分它们的那个变量。** 本例是同步模式，而用户日志里两种模式都有，对照比任何推理都硬。
3. **可读性缺陷与逻辑缺陷要分开处理。** "显示 57.5Hz"是前者（两行说不同的事），"独占模式不提帧节奏"是后者。混在一起会让人以为要改 `Rate:` 的含义。
4. **诚实不等于含糊。** 不能检测 VRR 是否生效，但可以说清"若不生效会怎样"，并指出唯一能确证的途径（显示器 OSD）。加限定语比沉默好，比假装检测更好。
5. **顺手记下没能实测的部分**（独占固定率的 guard）—— 不写清楚的话，下一个人会以为它验证过。

## 案例 36：升级驱动后反而崩溃 —— 被"宽容的驱动"掩盖的规格违规

**症状**：用户升级了 Intel UHD 620 的显卡驱动（2026-09 版），之后在这台笔记本上**三个渲染器全部闪退，连游戏画面都看不到**。而升级前用 OpenGL 是能跑的。

**起点**：驱动升级让 Vulkan 首次启动成功（此前日志是 `no device offers a usable API version`），于是走了一条**在这台机器上从未执行过的路径**：

```
Vulkan: using Intel(R) UHD Graphics 620 (API 1.3, Vulkan 1.3 core path).
Vulkan: window size 1920x1080.
[Error] Vulkan2D: failed to create the composite pipeline.
```

**根因（第一层）**：描述符池比它要服务的 layout 小。

```cpp
constexpr uint32_t kCompositeLayerCount = 4;   // 4 个采样图层（含 bezel）
bindings[1].descriptorCount   = kCompositeLayerCount;   // 布局要 4
sizes[1].descriptorCount      = 3;                      // 池只给 3   ← 规格不允许
```

而 `VkDescriptorPoolSize` 必须覆盖 layout 的需求，否则 `vkAllocateDescriptorSets` 失败 → `CreatePipeline()` 的一个**无日志** `return false` → 上层只报一句 `failed to create the composite pipeline`，看不到是哪一步。

**其中最刺眼的一点**：那个常量的注释**自己列出了"必须一致的三个地方"** —— 布局的 binding 数、descriptor write、shader 里的 `uLayers[]` —— **却漏了第四个：描述符池**。注释写对了"容易忘"，但忘了把它自己数进去。

**为什么以前没发现**：台式机的 NVIDIA 驱动**容忍**了这个短缺，所以这个违规一直存在却从未暴露。`kCompositeLayerCount` 从 3 改成 4 时（加 bezel 那一步）池没跟着改，而"在我机器上是好的"字面成立。

**第二层根因（放大效应）**：见案例 37 —— 错误路径没有关闭音频设备，于是第一次失败之后**每次尝试都死于另一个错误**，看起来像"三个渲染器都坏了"。

**修复与验证**：

| 改动 | 位置 |
|---|---|
| 池计数改为 `kCompositeLayerCount`，并在注释里把"三处"改成"四处" | `Vulkan2D.cpp:342` |
| **给 `CreatePipeline()` 的 5 个静默失败点各加一条 VkResult 日志** —— 下次同类问题一行日志就能定位，不必在别人的硬件上做实验 | `Vulkan2D.cpp` |
| 排查了同类模式（其他 layout/pool 配对：后处理 1/1、纹理缓存 16/1/1/2）—— **只有这一处不符** | 全树扫描 |

台式机回归无损（无错误、渲染与音频正常）。

**能带走的教训**：

1. **"在我机器上是好的"可能字面为真，而代码仍然是错的。** 驱动对规格的执行力度不同：违规代码在一张卡上跑得好好的，在另一张上必崩。**这不是"环境问题"，是被掩盖的缺陷。**
2. **凡是"多处必须一致"的常量，要在注释里把每一处都列出来 —— 包括不显眼的那几处。** 本例的注释列了三处却漏了池，而**漏掉的恰恰是唯一出错的那一处**。
3. **升级驱动会改变"哪段代码被执行"。** 用户升级后不是"新驱动有问题"，而是**长期潜伏的缺陷第一次被走到**了。症状出现在升级之后，不代表原因也在升级里。
4. **静默的 `return false` 是债务。** 一个函数有好几个失败原因却都不打日志时，调用方那句笼统的错误信息就等于没有信息。**每个失败点写清 VkResult，成本一行，收益是下次不用猜。**
5. **顺手做同类扫描。** 找到一处"计数不一致"之后，全树搜一遍同样的模式 —— 这次是干净的，但只有扫过才敢这么说。

## 案例 37：一个失败变成"全盘崩溃"—— 错误路径没有归还资源

**症状**（与案例 36 同一事件）：第一次尝试闪退后，用户切换渲染器再试，**三个模式全部闪退**。日志显示后面的尝试**根本没到渲染阶段**：

```
[Error] Unable to open 44.1KHz 4-channel audio with SDL: Audio device is already opened
```

而第一次会话的音频是**成功打开**的。

**根因**：`OpenAudio()` 之后的所有错误出口都走 `goto QuitError`，而 `QuitError` **没有调用 `CloseAudio()`**：

```cpp
if (Result::OKAY != OpenAudio(s_runtime_config)) return 1;   // 音频在这里打开
...
if (Result::OKAY != Render2D->Init(...)) goto QuitError;     // 渲染失败 → 音频未关闭
...
QuitError:
  SetModalLoopHook(nullptr);
  StatsOsdShutdown();
  OverlayShutdown();
  delete Render2D;        // ← 渲染器被清理了
  ...                     // ← 音频设备没有
```

于是设备一直开着，而**设置窗口仍然在跑** —— 用户切换渲染器、换游戏，每次都开新会话，每次都在 `OpenAudio` 处失败。**一个渲染器的问题被放大成"所有渲染器都不能用"。**

**修复**：`CloseAudio()` 加 `s_audioOpened` 守卫（可安全重复调用 / 未开启时调用），并在 `QuitError` 中调用它。

**能带走的教训**：

1. **错误路径必须和正常路径归还同样的资源。** 正常退出路径调了 `CloseAudio()`，错误路径没调 —— 这类不对称是资源泄漏的常见来源，而且**它在正常使用下完全看不出来**。
2. **一个失败的初始化会伪装成别的问题。** 症状（"所有渲染器都崩"）指向的方向（渲染器）与原因（音频设备未释放）完全相反。**当"所有选项都失败"时，优先怀疑共用的东西**，而不是逐个排查选项。
3. **残留资源造成的次生错误会盖住原始错误。** 第一次的 `Vulkan2D: failed to create the composite pipeline` 才是根因，却被后面五次 `already opened` 淹没。**"第一次错误"通常比后面的都重要。**
4. **让清理函数可以被无条件调用。** 错误路径上的代码**无法知道**资源是否真的被创建了；要求它去查清，正是它当初没做的原因。守卫写在清理函数内部，而不是每个调用点。

## 案例 38：去重只记住"上一个"，在振荡状态下等于没去重

**症状**：一次 15 秒的会话说生产了 **12014 行日志**，其中 **11830 行（98%）是同一条消息在两种状态间反复**：

```
6045 次: Vulkan: viewport ... - widescreen ACTIVE (...)
5785 次: Vulkan: viewport ... - widescreen NOT active (...)
```

真实信息被埋在 2% 里 —— 而这个日志正是排查本次故障要读的东西。

**根因**：代码的**意图**写得很清楚 ——

```cpp
// ...the viewport dimensions and whether the branch applied are reported once per distinct
// viewport rather than per frame.
static uint32_t s_lastKey = 0xFFFFFFFFu;
if (key != s_lastKey) { s_lastKey = key; InfoLog(...); }
```

**"once per distinct viewport"要靠"记住全部见过的"才能实现，而它只记住了最近一个。** 场景构建器**一帧内会走多个不同视口**（游戏在全屏视图与较小视图之间切换），于是"和上一个不同"在**两个状态间振荡时每帧都成立** → 每帧打印。

**顺带一个同类的隐患**：键是把四个坐标用移位+异或压进一个 `uint32_t`，**会碰撞**（例如 `495x0` 与 `0x495` 得到同一个键）。碰撞会导致**漏报**而非多报 —— 所以不是本次洪水的原因，但属于同一类错误，一并改掉。

**修复**：改用 `std::set<std::tuple<int,int,int,int>>`（精确、无碰撞），`insert().second` 判断首次出现。

**验证**：viewport 行 **11830 → 2**，总行数 **12014 → 382**；而那 2 条正是诊断所需（一个全屏视口激活 widescreen、一个零视口不激活），**信息价值零损失**。

**过程中踩的一个坑**：第一次改用了 `const auto key` + `std::set<decltype(key)>`，`decltype` 推出的是 `const std::tuple<...>`，而 `std::allocator<const T>` 非法 → **编译失败**。而当时我没看退出码就去跑测试，得到的是**上一版 exe** 的结果（数字看起来也"变小了"，纯属同游戏状态的巧合）。**先查构建是否成功，再看测试结果** —— 否则会把旧二进制的行为当成修复效果。

**能带走的教训**：

1. **"去重"要问清"记住几次"。** 记住上一个 ≠ 记住全部见过的，而两者只在**状态会来回振荡**时才有差别 —— 恰好是最难自查的情形。
2. **振荡比持续更毒。** 若状态单调变化，"记住上一个"能省下大部分行；正是**来回切换**让它退化成每帧一条。到日志里看"最多的那行"，一秒就能确认。
3. **压缩多个字段进一个整数时，先问会不会碰撞。** 碰撞的后果是**静默漏报**，比多报更难发现。
4. **诊断信息也要有预算意识。** 加日志时想的通常是"有没有足够信息"，而忘了问"**会写多少行**"—— 一条每帧执行、无条件打印的日志，在 15 秒内就能淹没整个文件。
5. **构建失败后跑"验证"，会验证错的东西。** 这次的假数据恰好长得像成功（行数确实变小了）。**退出码和产物时间戳要一起看。**

## 案例 39：排除条件把"最好的情形"排除了

**症状**：笔记本上 60Hz 面板 + 60Hz 配速（即完美的 1:1）时，读数报

```
Cadence: uneven (borderless, panel at own rate) - 1.0000 panel scans per frame
         ↑ 说不均                          ↑ 但 1.00 表示每帧正好显示一次
```

**自相矛盾，而且附带建议** —— 界面接着显示"frames repeat unevenly; an exclusive sync mode removes this"，也就是**让用户去修一个本来没问题的东西**。

**根因**：

```cpp
ratio = 面板Hz / 配速Hz;                        // 60/60 = 1.0
if (ratio < 1.0) return Uneven;                 // 未命中
const double nearest = floor(ratio + 0.5);      // = 1
if (nearest >= 2.0 && |ratio - nearest| <= nearest * 0.01)
    return Even;
return Uneven;                                  // ← 1.0 落到这里
```

`nearest >= 2.0` 把 **1x 排除在外**，而 1x 正是最理想的情形：面板速率恰好等于模拟速率，每帧显示一次。**排除它是为了防"略低于 1 的比率四舍五入成 1 被误判为 even"—— 而那个情况已由上面那行 `ratio < 1.0` 提前拦下了。**

**修复**：`nearest >= 1.0`，并为 1x 单独措辞（`1:1 - one panel scan per frame`，因为 "1 frames per scan" 读起来像舍入误差）。

**验证**（60Hz 副屏 + `RefreshRate=60`）：`cadence even (borderless, panel at own rate) - 1.0000 panel scans per frame` ✓

**能带走的教训**：

1. **写排除条件时，要问"被排除的是不是正好是理想情形"。** `>= 2` 看起来只是"要求至少两倍"，但它同时排除了 1x —— 而 1x 是完美对齐。
2. **保护性条件要核对它防的那个情况是否已被别处拦住。** 这里防的是"略低于 1 误判"，但那个分支早已 `return Uneven`。**重复的防护会顺手删掉合法输入。**
3. **自相矛盾的输出最值得追。** "uneven" 与 "1.0000 scans per frame" 同时在屏幕上，谁都看得出不对 —— **只要有人看到**。而它藏在一个默认关闭的读数里，所以需要读源码才发现。
4. **附带建议的错误判据危害更大。** 如果只是数字难看，影响有限；但它接着建议用户改同步模式，那就是**引着人去做无用功**。

## 案例 40：从一个正在被写入的文件里得出结论

**症状**（我在本案例排查中自己犯的错）：读到笔记本日志尾部是

```
Session: overlay and statistics shut down; destroying the renderers.
Session: 2D renderer destroyed.
```

于是判定"崩溃在 `~CVulkan3D` 里"。**一分钟后再读同一个文件**，尾部却是：

```
Session: 2D renderer destroyed.
Vulkan3D: teardown - textures and targets released.
Vulkan3D: teardown - buffers released.
Vulkan3D: teardown - pipelines and shaders released.
Session: 3D renderer destroyed.
Session: released. Returning to the settings window.
Session: returned with code 0; back to the settings window.
```

**5 个会话全部正常退出，根本没有崩溃。** 差别只是**第一次拷贝时进程还在写**。

**危害在于形状相同**：截断的尾部**与"崩在清理中途"的尾部完全一样**，所以它不只是"数据不全"，而是**一个会主动引导出错误结论的形态**。而且它比空文件更危险 —— 空文件你知道没有数据，截断的文件看起来有结论。

**修复（工具层面）**：`Get-LaptopLog.ps1` 现在检查最后一个会话是否有结束标记（`back to the settings window` / `Program terminated normally` / `... due to an error`）。三者都没有就明确警告：

```
!! The last session has no end marker.
   Either the process is still running, or this copy was taken mid-write. A truncated
   tail looks exactly like a crash during teardown, so do not conclude anything from it.
```

**验证**：完整日志 → 无警告；人工截断版 → 正确报警。

**能带走的教训**：

1. **从"正在增长的文件"里读结论前，先确认它写完了。** 日志、构建输出、还在跑的测试结果 —— 都属于这一类。**问一句"这个文件还会变吗"。**
2. **截断的危险在于它伪装成有结论。** 空文件让人知道没数据；截断文件让人以为看到了结尾。工具应当把这层区分显式说出来。
3. **"最后一行"是最有诱惑力的证据，也最脆弱。** 它常被当作因果链的终点，但它的位置取决于**何时拷贝**，而不只取决于程序行为。
4. **自我怀疑要能落到检查上。** 我当时的反应是"再读一次"，那有效但偶然。**把它写成工具里的一个断言**（有结束标记吗），下次就不必依赖灵光一现。

## 案例 41：实时面板里写着散文

**症状**（用户反馈）：笔记本全屏时左上角的统计面板"出现一堆文字"，与该面板"简洁实时数据"的风格不符。具体是 `Cadence:` 一处占了 **5 行**：

```
Cadence: uneven (1.00x)
         frames repeat unevenly; an exclusive sync mode removes this
         even at 2x = 115.00 Hz
         (assumes the panel is at its own rate; driver windowed
          VRR would override this - check the display's readout)
```

（这条还叠加了案例 39 的判定错误 —— `1.00x` 本该是 `even`。）

**根因是语气错位**：这段措辞是在**解释**（为什么、怎么办、前提是什么），而面板需要的是**读数**。它逐帧绘制、被反复扫视，每多一行都是持续的干扰。

**修复**：压成一行，只留"判定 + 倍数 + 可执行数值"：

| 情形 | 改前 | 改后 |
|---|---|---|
| 60Hz + 60Hz | `uneven (1.00x)` + 4 行 | `even (1:1)` |
| 120Hz 无边框 | `uneven if panel @ own rate (2.09 scans per frame)` + 4 行 | `uneven (2.09x)  even at 115.00 Hz` |
| 120Hz 独占 VRR | `uneven if VRR is not engaging (2.09 scans/frame)` + 2 行 | `uneven (2.09x)  unless VRR is engaging` |

**5 行 → 1 行**，判定 / 倍数 / 目标值三个关键信息一个没少。**日志里保留完整措辞** —— 日志可以啰嗦，逐帧面板不行。

**能带走的教训**：

1. **同一个结论，在"实时读数"和"设置界面"里应当有不同详略。** 设置界面是**决策现场**（用户正在读、正在选），可以也应该给出理由；实时面板是**状态显示**，只承担"当前是什么"。**把解释放在两处，等于在错的地方多说一遍。**
2. **判据：这一行在每秒被看 60 次时还值得存在吗？** 逐帧绘制的文字，成本不是"多占几行"，而是**每次扫视都消耗注意力**。
3. **先查是不是重复。** `(assumes the panel is at its own rate...)` 这行之所以该删，最硬的理由不是"太长"，而是**`Sync:` 行已经写了 `borderless (panel keeps its own rate)`** —— 同一事实在同一屏上说了两遍。
4. **数字要读得像结论。** `1.0000 panel scans per frame` 看起来像舍入误差，`1:1` 一眼就是理想情形。**同一个数字，写法决定它被理解成"正常"还是"可疑"。**
5. **两种详略要同时维护，而日志是第三处。** 面板精简后，**信息并没有消失** —— 它去了设置界面的 `(?)` 提示和日志。删减的前提是**别处真的还在**，否则就是把信息删掉了而不是搬走了。

## 案例 42：部署脚本谎报成功

**症状**：`Deploy-ToLaptop.ps1` 打印

```
  backed up the previous executable
  scp.exe: failed to upload file ... to C:/EMU/Supermodel-VK/Supermodel-VK.exe
  done.
```

**scp 明明报了失败，脚本却报 `done.`** —— 而下一步就是**去测试一个根本没送到的构建**。

**根因**：目标机器上 `Supermodel-VK.exe` 正在运行 → 文件被锁 → `dest open ... Failure`。而脚本那句 `if ($LASTEXITCODE -ne 0 -or -not $?) { throw }` **没有触发**（实测 scp 在命令行手工调用时确实返回 1，所以问题出在脚本内的取值时机上 —— 而**我没有去追这个 PowerShell 细节**，理由见下）。

**修法：改看"结果"而不是"退出码"。**

```powershell
# 拷完把远端文件读回来比对 SHA256 —— 这是地面真相，不依赖 scp 如何报告失败
function Assert-RemoteFileMatches { ... 比对 local/remote 哈希，不一致就 throw ... }
```

这个办法的价值在于：**它不关心失败是怎么发生的**（文件被锁、路径错、网络断、scp 返回值不可靠），只要结果不对就立刻报错。脚本现在 4 个文件逐一校验后才打印成功。

**同时加了一道前置检查**：部署前先用 `tasklist` 查远端是否有同名进程在跑，有就**明确报出是哪个进程锁住了文件**，并说明"退出游戏只回到设置窗口，要关掉窗口进程才结束"。

> **诚实标注**：这道守卫**我未能实测触发** —— 尝试远程启动一个进程来复现锁定状态没有成功（ssh 会话里 `start /B` 没真正拉起进程）。但哈希校验是主防线且已证明有效（4/4 通过），所以守卫是否触发并不影响脚本的正确性。

**能带走的教训**：

1. **错误处理要检查"结果"，而不是"别人怎么报告失败"。** 退出码、返回对象、日志文本都是**间接证据**，而"目标文件内容对不对"是**直接证据**。当间接证据不可靠时，**换成直接证据**比追查间接证据便宜得多。
2. **工具谎报成功比工具报错更危险。** 报错会让人去查；谎报会让人去测一个不存在的东西，然后得出"修复无效"的错误结论 —— 那会浪费一整轮排查。
3. **"我修好了"和"它真的送过去了"是两件事。** 部署脚本的职责不只是传输，还要**证明传输发生了**。
4. **对"未验证的改动"要标注清楚。** 守卫没被触发过，就写明白没被触发过 —— 否则下一个人会以为它经过验证。

## 案例 43：视锥按窗口算，画面按可见区画

**症状**（用户反馈）：`WideScreen = 1` 与 `IntegerScale = 1` 同时打开时，画面横向被拉宽 —— 4:3 的游戏被展成 16:9 没问题，但**多拉了 12.5%**。`Virtua Fighter 3` 尤其明显：人物横向偏胖，左右两侧的 HUD 被推得更靠边。单开 `WideScreen = 1`（不整数缩放）时反而正常。

**根因**：宽屏分支里，视锥的展宽量 `correction` 用的是**窗口**宽高比，而 3D 图层实际画进的是一个**更小的矩形**。两个量描述的不是同一块区域：

```cpp
// 展宽量：按窗口算
const float correction = ((float)m_totalXRes / (float)m_totalYRes) / ((float)m_xRes / (float)m_yRes);
// 但下面画的是 496 宽的贴图放大到 m_totalXRes、高 vpHeight * m_yRatio 的矩形
vp->width  = (int)m_totalXRes;
vp->height = (int)(vp->vpHeight * m_yRatio);
```

3840×2160 面板上取 5 倍整数缩放时：

| 量 | 值 |
|---|---|
| 窗口高度 | 2160 |
| 3D 图层实际高 | 384 × 5 = **1920** |
| 旧 `correction`（除 2160） | 3840/2160 ÷ (2480/1920) = **1.3763** |
| 正确 `correction`（除 1920） | 3840/1920 ÷ (2480/1920) = **1.5484** |
| 比值 | **1.125** ← 这就是那个 12.5% |

**为什么只在整数缩放下暴露**：`m_yRatio = yRes / 384`，所以非整数缩放的全屏视口满足 `vpHeight * m_yRatio == m_yRes`，两种写法**逐位相同**。整数缩放是唯一让两者分岔的配置 —— 也正是唯一会暴露这个缺陷的配置。

**修复**：把分母换成图层真正被画进去的高度。

```cpp
const float outHeight = (vp->vpHeight > 0.0f && m_yRatio > 0.0f)
    ? vp->vpHeight * m_yRatio       // 图层实际占据的高度
    : (float)m_totalYRes;           // 退化为窗口高度
const float correction = ((float)m_totalXRes / outHeight) / ((float)m_xRes / (float)m_yRes);
```

两个渲染器都有同一段代码，一起改：Vulkan 3D 在 [`R3DSceneBuilder.cpp`](../Src/Graphics/Vulkan3D/R3DSceneBuilder.cpp:750)，OpenGL New 3D 在 [`New3D.cpp`](../Src/Graphics/New3D/New3D.cpp:1627)。

**验证方式（这次没有做视觉 A/B，靠的是可证明的等价性）**：上面的 `m_yRatio = yRes/384` 推导保证了改动在**所有非整数缩放配置下逐位不变**，因此不存在"修好一处、改坏一片"的风险；唯一行为变化恰好就是用户报告的那个组合。

**能带走的教训**：

1. **两个相乘/相除的物理量，先确认它们描述的是同一个矩形。** 这段代码的原意是"展宽量要抵消窗口比与游戏比之差"，但窗口不是 3D 图层的输出面。**一旦分母和实际绘制目标不是同一个东西，比值就是错的 —— 而且错得符合直觉，所以没人怀疑。**
2. **"只在某一个配置下出错"往往不是边缘情况，而是某个等式被打破。** 这里被打破的是 `vpHeight * m_yRatio == m_yRes`。找这种等式，比按配置穷举快得多。
3. **能找到"改动是无操作"的证明，就优先用它代替视觉验证。** 视觉 A/B 只能覆盖测过的配置；代数等价性覆盖全部。**先证明不变量，再动代码。**
4. **同一个算式写了两遍（Vulkan 与 OpenGL），就必须同时改。** 双后端项目里，"另一条路径没这个 bug"经常是错的 —— 它可能只是没被测到。
5. **用户描述的是"多拉了 12.5%"，这个数字精确到能反推出根因。** 不要把它当成主观印象放过：**能量化的症状描述是最高价值的线索。**

## 案例 44：界面上看不见的推导值，被用户当成了设置项

**症状**（用户提问）："整数缩放 5× 才是真正的 4K？是不是跟我设的 3840×2160 @150% DPI 有关？DPI 比例是不是也得提前加入判断？如果 100% DPI 才用 6× 吗？"

三个问号里，**每一个都建立在同一个误解上**：用户相信"4K 就该是 6 倍"。

**根因不是代码，是界面**：

1. **倍率是推导出来的，不是设置的。** 代码里只有 `IntegerScale` 这个布尔开关，倍率由 `trunc(min(面板宽/496, 面板高/384))` 现算。**它不存在于任何配置文件、任何控件里** —— 用户无处可查，只能猜。
2. **界面主动给了错误暗示。** 预设表里有一条 `2976 x 2304`，标签写着 `"6x 分辨率 (2976 x 2304 - 4K级)"`。**"4K级"三个字直接制造了"4K = 6×"的印象**，而 2160 行面板根本取不到 6×（384 × 6 = 2304 > 2160）。
3. **DPI 与此无关，加进去反而会引入 bug。** 面板尺寸来自 `EnumDisplaySettingsW(ENUM_CURRENT_SETTINGS)` 的 `dmPelsWidth/dmPelsHeight`，**不受 DPI 虚拟化影响**；而本项目的 `SDL_HINT_WINDOWS_DPI_AWARENESS = "system"` 会让非系统 DPI 显示器拿到虚拟化尺寸（1080p 显示成 2880×1620）。**如果再用 DPI 去折算，等于把一个已经正确的物理值改错。** DPI 唯一正当的用途是 ImGui 的 UI 缩放。

高度决定倍率（宽度在 16:9 下不构成约束）：

| 面板高 | 倍率 | 可见区 |
|---|---|---|
| 1080 | 2× | 992 × 768 |
| 1440 | 3× | 1488 × 1152 |
| 2160 | **5×** | 2480 × 1920 |
| 2400 | 6× | 2976 × 2304 |
| 2880 | 7× | 3472 × 2688 |

**修复（三处，缺一不可）**：

1. **改掉误导标签**：`"6x 分辨率 (2976 x 2304 - 4K级)"` → `"6x 分辨率 (2976 x 2304)"`，同时把标记只留给真正能落到的两档 —— `3x ... 2K 屏推荐` 与 `5x ... 4K 屏推荐`。**中途试过在不可达档位写 `需 2304 行面板`，是错的**：下拉框被扫视时只回答一个问题"我该选哪个"，写门槛等于把说明塞进了选择项（详见下面"能带走的教训"第 2 条）。
2. **加实时读数**：新增 [`GetIntegerScaleInfo()`](../Src/OSD/SDL/Main.cpp:1134)，输出实际倍率、可见区、面板尺寸、下一档所需行数。它**刻意复用 `CalcScreenGeometry` 的取值顺序**（先查面板、查不到回退到全屏尺寸），所以**读数不可能与几何代码打架** —— 否则又是一个"两个来源说不同话"的坑。
3. **两处都显示**：`常用` 页给普通用户（"实际生效 5×，可见区 2480×1920"），`画面` 页的 `(?)` 提示给调参的人。**同一个事实在决策现场和状态读数里各出现一次，不是重复。**

额外加了一条防空转提示：当 `XResolution/YResolution` 与可见区不一致时，明确写出"会被覆盖为 2480 × 1920" —— 因为整数缩放打开后，用户在"分辨率"里填什么都不会生效（[`Main.cpp`](../Src/OSD/SDL/Main.cpp:558)）。**这是两个互相覆盖的旋钮，不说明就一定有人以为自己的输入生效了。**

**能带走的教训**：

1. **凡是"推导出来的值"，要么显示出来，要么别让用户猜。** 用户不会读代码，他们读界面。界面上没有的数值，就会变成某种民间传说 —— 而传说通常是错的。
2. **"补充说明"和"选项标签"是两种不同的载体。** 下拉框里每一项都在被**扫视**（用来做一次选择），所以只该回答"选哪个"；"为什么选不到"属于解释，归 `(?)` 提示与实时读数。第一版我把 `需 2304 行面板` 写进了标签，等于把说明放进了选择项 —— **信息正确，位置错了**。判据：这一段文字是在帮用户**挑**，还是在帮用户**懂**？
3. **推荐标记只能给"真的能选到"的档位。** 3x/5x 各对应一种真实面板，所以标"推荐"有意义；给 4x/6x/8x 加任何修饰都只是噪音，因为它们在 16:9 上根本落不到。**能标注的前提是它可达。**
4. **同一个词在不同语境下会误导。** `4K级` 在营销语境里是"档次"，在几何语境里是"3840×2160 刚好 5 倍"。**当标签同时具备"评价"和"参数"两种读法时，用户会选错的那个。** 4x 上那个 `2K级` 更糟 —— 它不只是歧义，而是**事实错误**：2K 屏只有 1440 行，进不了需要 1536 行的 4x。
5. **"要不要把 DPI 加进判断"这类问题，先问数据从哪来。** 如果上游已经是物理像素，再加一层缩放就是**制造** bug。**判断依据是数据来源的语义，不是"多加一层更保险"。**
6. **新增的读数必须复用原计算的取值路径，不能另写一份。** 两份取值逻辑迟早会分叉，而分叉时的症状是"界面说 5×，实际画 4×" —— 比不显示更糟。**读数是计算的镜像，不是计算的复述。**
7. **两个旋钮互相覆盖，就必须显式说明谁赢。** 静默覆盖是配置类 bug 的常见来源。

> 项目内详见 `TECHLOG.md` 第 26.3 节。

## 案例 45：先怀疑帧率不匹配，但症状描述已经排除了它

**症状**（用户反馈）：`Daytona USA 2 - Power Edition` 在 Vulkan 模式下，第三人称跟车视角里"每次我稍微往左或往右移动，整个画面跟着移动，感觉挺头晕的"。用户的猜测是**帧率与主屏刷新率不匹配**。

**第一步不是查代码，是拆症状。** 这两个词描述的是完全不同的物理量：

| 用户说的 | 实际是什么 | 属于哪一层 |
|---|---|---|
| "整个画面跟着动" | **整幅画面一致平移** | 游戏自己的镜头运动 |
| "帧率不匹配" | **周期性顿挫**（judder） | 呈现节奏 |

帧率不匹配的表现是：**一段匀速直线也应该一顿一顿，且与是否转向无关**。而用户的描述里，运动量**与转向强相关** —— 所以横移本身不是节奏问题。

**真正的坑在基线**：仓库根的 [`Config/Supermodel.ini`](../Config/Supermodel.ini) 是 **2026-10-09 的旧快照**（`Vulkan3DEngine = 0`、`RefreshRate = 60`、`FullScreen = 0`），**根本不是用户实际跑的那套**。如果按它排查，会去查一个不存在的 4.3% 超速、一个不存在的窗口模式，**整轮方向全错**。

真实基线只能从 `dist/Supermodel-VK/Data/Supermodel.log` 读：

```
RefreshRate    = 57.5         ; 已经是街机原速，超速 4.3% 已排除
ExclusiveRefreshRate = 0      ; 0 = G-SYNC/VRR 独占，不是固定 57Hz
WideScreen     = 0            ; Hor+ 分支不触发，FOV 变形排除
IntegerScale   = 1
Video: integer scaling 5x - visible area 2480x1920 in a 3840x2160 window.
Stats OSD: cadence uneven (exclusive VRR, only if VRR is not engaging) - 2.0870 panel scans per frame.
```

**两个旧疑虑当场消失**（57.5Hz、独占全屏都已经做过了），**一个新问题浮出**：`2.0870 scans per frame` 是按**模式刷新率 120Hz** 算的，程序看不到瞬时扫描率 —— 日志那句 `only if VRR is not engaging` 就是这个意思。所以 G-SYNC 到底咬住没有，**必须用显示器自身 OSD 去量，程序内的数字不能当证据**。

于是把排查改成四步、每步只动一个变量，而不是直接改代码。

**能带走的教训**：

1. **用户的因果假设可以错，症状描述通常是对的。** 他说"帧率不匹配"，判据却是"跟着转向动"。**用症状去检验假设，而不是接受假设当框架。** 一个假设若与症状的**相关性结构**矛盾（此例：横移与转向强相关、与时间无关），就可以先放下。
2. **"我读的配置文件"和"程序读的配置文件"可能是两份。** 仓库根、`dist/`、用户目录都可能有 ini。**先确认程序加载的是哪一个，再看内容。** 这一步不花时间，却能省掉整轮误判。
3. **日志里的数字要看清它是在什么前提下算出来的。** `2.0870` 是"假设面板跑自己的 120Hz"得出的，而不是观测值。**把一个条件值当成实测值，会引出一个不存在的问题。**
4. **程序无法观测的量，就去程序外面测。** 瞬时扫描率在进程内不可见 —— 显示器 OSD 和驱动控制面板才是地面真相。**别在观测不到的地方加日志。**
5. **诊断的第一产出应该是"排除清单"，不是修复。** 这一轮最有价值的成果是三个被排除的方向（超速、FOV、窗口模式）和一个被精确化的未知量（VRR 是否生效）。**排除比猜测便宜，也比猜测可靠。**
6. **同一个缩写在不同语境下是两件事。** 这里的 `VR3` 指游戏内的 **第三号视角**（`VRDefaultView = 2`），与渲染器编号（Vulkan 3D / New 3D / Legacy 3D）**毫无关系**。我一度按渲染器去理解，导致建议"切换到 VR1"时指的是错误的东西。**遇到缩写先问"这是谁的命名空间"。**

## 案例 47：“读档后没声音”——变哑的是输出，不是存档

**症状**：游戏内面板里存了档，退出到设置界面，再从「管理存档」Load 进去，
画面正常、震动正常，**完全没有声音**。日志里没有任何音频错误，under-run 只有
2–3 次。

**先把“哪里静了”拆开。** 音频链路上有三个可能变哑的点：

| 环节 | 变哑时的日志特征 |
|---|---|
| 游戏没发声（SCSP / DSB / 存档状态） | 缓冲区照常消耗，`source peak` 为 0 |
| 混音后为 0（音量 / 平衡） | `source peak` 有值、`mix peak` 为 0 |
| 输出被静音（OSD 开关） | 两者都有值，`enabled == false` |

为此加了 `SM3D_AUDIO_LEVEL=1`：每秒打印 `source peak` / `mix peak` /
`output on|MUTED`。全新进程载入**用户那份存档**，`mix peak ≈ 0.59` 满量程、
连续 6 秒稳定 → 存档和 DSB 路由都没问题。**排除掉两个最花时间的方向，
只用了 10 秒。**

**根因不在音频子系统，而在它的生命周期。** `enabled` 是文件级 `static bool`：
面板打开会自动暂停并 `SetAudioEnabled(false)`，在面板里存档后直接退出，配对的
`SetAudioEnabled(true)` 不会执行；而设置界面在同一个进程里跑下一局，于是新会话
从“静音”开始。缓冲区健康、混音正常、只有 `MixOut()` 走 `out.Silence()` ——
这正是“日志一切正常但没声音”。

**能带走的教训**：

1. **“静音”和“无声”是两件事，先分清楚。** 前者是输出端开关，后者是信号本身。
   两者的日志表现完全不同：静音时缓冲区健康、under-run 不涨。
2. **进程级的静态量不会随会话结束而复位。** 凡是 `static` 的运行状态，都要问
   一句“下一个会话继承它合理吗”。本项目的会话边界是 `OpenAudio()` /
   `CloseAudio()`，所以复位放在这两处；`FlushAudioBuffer()` 这种只清数据的
   函数不能代替它。
3. **用户的“退出再进”要问清是退出到哪一层。** 退出到设置界面（同一进程）和
   退出整个程序（新进程）会走不同的状态继承路径，症状相似、根因不同。本例只
   在前者复现，恰好是用户描述的操作。
4. **诊断日志要能区分“输入为 0”和“输出被关”。** 只打最终电平，两种情况都是 0；
   同时打源电平和 `enabled`，一行就能定位到层。

> 全程没有声音」一节。

## 案例 48：“换了后端后，同一套校准/输入突然不准”——先拆“数据丢了”还是“坐标空间变了”

**症状**：一个跨后端的功能（光枪准星、触屏、摇杆死区……）在旧后端下校准得好好的，
换到新后端后突然对不齐。用户第一反应是“校准代码是不是被替换/丢了”。

**先分层的定位思路**：把问题拆成两个彼此独立的环节，分别验证：

1. **数据还在吗？** 校准常量/配置/映射表是不是被整块删掉或覆盖了。这一步用 `grep`
   定位到具体文件和行，确认 `SetRange(...)`、`ApplyGameSpecificInputRanges(...)`
   这类调用还在、分支还命中（本例要确认游戏解析出的 set 名正确，看
   `resolves to set` 日志，而不是 zip 文件名）。
2. **坐标换算还对吗？** 同一份数据，从“输入坐标”到“最终像素”的换算路径变没变。
   本例 SDL3 把鼠标从整数像素换成浮点子像素、按设备 ID 的 RawInput —— 校准常量
   没变，但“鼠标坐标 → 轴值”的链路整个重写了。

**关键工具：探针，把“校准后的值”和“最终像素”打印在同一行。** 本例 `SM3D_GUN_PROBE=1`
打的是 `axis X/Y + ValueAsFraction + viewport + 最终 crosshair 像素`；`RefreshPointer`
再补一行“鼠标原始坐标 + display 几何”。两个数对得上，问题在数据/常量；对不上，
问题在坐标空间（DPI 逻辑/物理、窗口内缩、视口偏移）。

**根因**：跨后端迁移只搬了“校准结果”（那 4 个常量），没搬“输入坐标的语义”。
校准常量本身正确且没丢；真正变的是喂给它的坐标从“整数像素”变成了“浮点子像素 +
每设备坐标”，以及 DPI 缩放下逻辑/物理坐标是否一致。

**修法（本例）**：无需改校准常量。确认 `ApplyGameSpecificInputRanges` 的
15/119/222、250/144/38 和 `Model3.cpp` 的 Y 轴反转 `255 - value` 都还在、且命中
`lostwsga`；再在 150% DPI 下分别验证 3x 窗口 / 5x 全屏，确认坐标空间一致即可。

**能带走的教训**：

1. **“校准不准”先别改校准，先确认校准还在。** 一条 `grep` 比重新测量便宜得多。
2. **跨后端迁移，危险的不是数据，是“数据含义”。** 整数→浮点、逻辑→物理、
   全局→每设备，任何一处坐标语义变化都会让“同一套常量”失效。
3. **探针要同时打“输入”和“输出”两端。** 只打最终结果，两个环节的故障表现一模一样；
   两端都打，一行就能定位。
4. **先问“游戏解析成哪个 set”再下结论。** 分支命中判断（`lostwsga`）依赖运行时
   解析出的 set 名，不是 zip 文件名。

## 附：从这些案例中抽象出的通用清单

排查渲染/图形类问题时，按顺序自问：

1. **它执行了吗？** —— 用一次性追踪日志点亮链条，别靠推测。
2. **它能执行吗？** —— 资源是否已创建（`nullptr` 句柄在图形 API 里常是**静默**失败）。
3. **它执行的结果对吗？** —— 需要**独立的数据**验证，不是"看着像"。
4. **这个数字/字符串/长度写了几遍？** —— 多于一遍就有漏改风险。
5. **这个状态是"成功后才清"还是"先清后做"？** —— 后者中途失败会永久丢失。
6. **失败路径收拾干净了吗？** —— 布局、锁、计数器都要无条件回到一致状态。
7. **这个矩形是"裁剪"还是"几何"？** —— 改错的症状完全不同。
8. **这个函数只在条件满足时才被调用吗？** —— 那就不能由它来改变条件。
9. **我的验证有判定力吗？** —— 没见过它失败的测试不算测试。
10. **我复现的是用户的真实场景吗？** —— 启动方式、窗口模式、输入方式。
11. **"可选资源 + 静默兜底"的地方在哪？** —— 资源缺失会退化成一个**运行模式**，症状出现在别处。
12. **这个模块的错误输出到哪？** —— `printf`/`cout` 不进日志，别看错地方就下结论。
13. **我上报的是"请求的"还是"发生的"？** —— 检索这段代码有无回退/降级路径；若有，事实就在那个被降级时更新的变量里，读配置等于撒谎。
14. **抓屏"看着正常"就等于抓对了吗？** —— 全黑会让你换方法，"内容合理但少了被测那一层"会让你去查被测功能。**当截图看着对、功能却像没生效时，先怀疑抓取路径**，并问：我抓的是不是被测功能写入的那个缓冲区？
15. **分子和分母描述的是同一块矩形吗？** —— 宽高比、缩放比、视口尺寸这类比值，**一旦分母取错来源，结果就会以"差一点点"的形式出现**（本例是 12.5%），而且符合直觉，极难怀疑。
16. **这个"看起来不生效"的数值，界面上有地方能读到吗？** —— 若是代码推导出来的，就必须显示出来；否则用户会自己编一个解释，而那个解释通常是错的。
17. **我读的配置，是程序读的那一份吗？** —— 仓库根、`dist/`、用户目录都可能各有一份；**先确认加载路径，再看内容**。
18. **这个数字是在什么前提下算出来的？** —— 带条件的推导值（"假设备份面板跑 120Hz"）不是观测值。**程序观测不到的量，去程序外面测。**
19. **这个缩写是谁的命名空间？** —— `VR3` 可以是"第三号视角"，也可以是"渲染器编号"。**歧义缩写必须先消歧再讨论。**

排查"偶发"问题时：

1. **先确认是不是自己改出来的** —— 查文件时间戳，一步就能排除方向。
2. **找"什么时候会集中发生"** —— 偶发问题的触发条件往往是某个时序（暂停恢复、重建、切换）。
3. **查共享配额** —— 内存池、环缓冲、描述符池耗尽会表现为完全不相干的症状。

排查"设备/组件没反应"的问题时：

1. **先把"它到底挂载了没有"变成可观测的** —— 打印**实际实例化的组件清单**，而不是猜测。
2. **检查条件表达式里的资源存在性判断**（`&& res.ok()`）—— 它为假时走哪条路？
3. **"局部自检通过、整体失败"** → 怀疑某个组件**根本不存在**，而不是数据损坏。

排查"两个上限/约束不一致"这一类问题时：

1. **凡是"分配大小"出现字面量的地方，都问一句：它对应哪个上限？** 两者必须来自**同一个定义**。
2. **凡是"放不下就跳过/丢弃"的分支，都必须有日志。** 静默丢弃会把症状伪装成完全不同的问题（丢几何 → 看着像贴图错误）。
3. **优先加"用量/填充率"日志，而不是继续读代码。** 一条 `已用 X / 上限 Y` 的周期日志，往往比几小时的静态阅读更快定位。
4. **移植时逐项核对原版的分配表达式** —— `size = limit * sizeof(T)` 被写成字面量，是一类不会崩、只丢数据的错误。
5. **排查卡住时，换一个"证伪"实验比继续推理有效。** 本例中"每帧全量重传"这个粗暴实验，一举洗清了整条纹理链路，把方向扭转过来。

排查"检查工具本身"时：

1. **先问：它验证的命题，和我真正关心的那件事，是同一个吗？** 一个"翻译审计"一直报全部已翻译，而用户切英文仍看到中文 —— 它检查的是"表里有没有条目"，不是"代码有没有查表"。**答案正确、问题问错的检查比没有检查更危险**，它给的是虚假的安心。
2. **手工维护的清单是负债。** 列"哪些函数会翻译"这种清单，既会漏（121 条误报），又可能把错的项列进去 —— 而**方向偏宽松的清单会藏住它本该抓的 bug**。能推导就别列举。
3. **解析型工具同样要有判定力测试。** 自动推导的第一版要求 `{` 独占一行，结果漏掉所有单行定义的辅助函数，误报 68 条。**只有把它拿去跑、并确认"注入已知错误后会报"，才知道它是否在工作。**
4. **"取最后一个匹配"要确认最后一个是对的。** 从 `Version.h` 提版本号时，同文件里的拼接宏也含该标识符，最后一次匹配覆盖了正确值，版本号静默变成 `v--20261013`。加行首锚定才对。

排查"设置项出现在错误的页/位置"时：

1. **先找"谁负责绘制这一项"的两份名单。** 通用渲染器按"组"绘制，手写控件按"白名单"绘制；**一个键若进了白名单却没人画它，它就会从所有页面消失** —— 而代码、翻译、配置全都是对的。本例中网络设置躺在「常用」页底部，正是因为白名单把它标记为"由手写代码绘制"，而那个手写代码不在「网络」页里。
2. **搬运手写控件时，注意它与"快照/回写"机制的相对位置。** 把编辑夹在 `UpdateTempValues(group, true)` 与 `(false)` 之间，改动会被静默回滚 —— 回写恢复的是快照时的值。正确做法是让编辑发生在**快照之前**。
3. **这类缺陷不会报任何错。** 设置项不崩、不丢、翻译也齐全，只是**出现在不该出现的地方**（或干脆不出现）。**只有打开界面实际看，或者核对"哪段代码负责绘制它"，才能发现。**

排查"状态显示/读数类功能"时：

1. **先问：这个数字是从"配置"算的，还是从"实际结果"取的？** 有回退路径的代码存在两个真相。读配置的读数，会在**用户最需要知道实情的时候**（功能降级了）给出错误的安心。
2. **找出"哪个变量在降级时被更新"** —— 那才是事实来源。若找不到，说明降级是静默的，那是另一个更严重的 bug。
3. **把无法验证的部分显式标出来，并说清"验证了什么"。** `exclusive VRR (preconditions met)` 好过 `unverified`（含糊，没说清哪一半没验证），也远好过 `G-SYNC/VRR`（读起来像保证）。含糊的措辞会让用户在出问题时无从判断是自己配置错了还是程序在骗他。
4. **先问"这个信号在被观测时是否真的存在"。** 本例的第四项前提**不是**因为"API 没暴露"而不可观测，而是因为**程序刻意低于面板上限运行** —— 生产慢于消费，面板永远不会掐住它，于是没有可观测的时间差异。**"技术上能读到"与"物理上有信号"是两件事；设计读数前先确认后者。**
5. **差值类数字的精度要配得上它要表达的量。** 真实值 57.524160、可选值 57.5，按一位小数显示成 `-0.0%` —— 看起来像程序算错了，而不是"下拉框只能给到这个精度"。**读者会把格式化缺陷读成逻辑错误。**

排查"功能与某个能力/后端绑定"时：

1. **逐条问：`if (能力) { 功能 }` 里，条件为假时用户看到什么？** 答案是"什么都没有"时，这就是案例 21。**静默消失的功能比明确不可用的功能更让人困惑**，因为用户会以为是自己配错了。
2. **优先让功能不依赖那个能力。** 先数清两个路径的**真实差异点** —— 本例中面板/读数/输入/快照全部可共用，只有 3 处分叉。差异小就别复制。
3. **做不到就显式声明**，写在使用它的那个控件旁边，而不是只写在日志或 README 里 —— 用户在设置界面里，不在日志里。
4. **配置项的勾选状态要反映真实可用性。** "状态为开、实际不工作"是最容易误判的组合。

排查"要恢复一段被移除的代码"时：

1. **先读移除处的注释，读完整段。** 理由常常涉及**别的模块**（本例是着色器目标版本），照原样恢复会精确复现当初的失败，而且**失败点在别处**。
2. **问清"它当初为什么不行"** —— 通常是某个前提没满足（版本、特征、初始化顺序）。恢复代码的同时要**把前提补齐**。
3. **清点真实依赖再决定门槛。** 本例中"要求 1.3"实际只用到两个有扩展等价物的特性 + 着色器版本，代码清单仅 14 个调用点。**门槛是虚高的，代价是放弃一整代硬件。**
4. **本地无法复现的设备分支，造假条件也要测一次。** 否则交付的是"编译通过但从未执行"的代码 —— 它只在用户机器上第一次运行。测完记得撤除钩子。
5. **薄封装 + 运行时选路，好过复制两套代码。** "优先核心名、回退扩展名"，高版本设备行为零变化。
6. **包装函数在两个指针都空时静默无操作 —— 要加一次性校验。** 否则症状是"一块空屏"，而不是"驱动不支持"。

排查"硬件特性/能力"相关的功能时：

1. **"支持 X"后面必须跟"在什么条件下可用"。** 硬件特性几乎都带参数范围（VRR 范围、分辨率上限、时序限制）。只写"支持"等于把最容易踩的坑留给用户 —— 本例中"支持 G-SYNC"并不代表"能在 57.5 Hz 下 G-SYNC"。
2. **能力检查要覆盖"范围"而不只是"有无"。** 若接口查不到范围，就必须在**文档和 UI 措辞上说清"我能确认到哪一步"**，而不是含糊过去。`(preconditions met)` 这种写法比"已启用"诚实得多。
3. **两个已知数值的关系值得算成一句结论。** 屏幕上已经有一堆数字，用户要自己做除法才能发现问题 —— 那就别指望他自己做。**把派生结论直接给出来**（"不整除，会抖，改用独占模式"）比多显示一个数字有用得多。
4. **建议类提示必须有反向条件 + 判定力测试。** 在"没问题"时**明确说没问题且不给建议**，否则"永远出现的提示"会变成背景噪音。本例用整数倍 + 1% 容差，并用 `60 ÷ 120 = 2` 这个必然通过的场景确认它会沉默。
5. **注释里引用符号名是有代价的 —— 引用就核实。** 本例一条注释里两个标识符（`SpeedMode`、`ComputeTimings`）都是臆造的，正确的分别是配置项名和 `CModel3::RunMainBoardFrame`。**留下一个不存在的符号名，就是留下一条误导人的线索。**

排查"打包/分发"相关问题时：

1. **"引用别人的东西"要跟着一次"它会被打包吗"。** 任何写进用户可见文案的**路径**（脚本、文档、图片、模板）都是对打包脚本的**隐含依赖** —— 界面、README、打包脚本分属三处，没有任何机制保证一致。
2. **发布脚本/工具时，它的路径假设就是它的接口。** 让工具在**开发布局和发布布局下都能找到自己的同伴**，比在文档里额外解释一遍便宜。
3. **分发会暴露只在开发环境成立的前提。** 仓库里跑得好好的东西打包后立刻坏 —— **这类问题只有真的打包一次才会出现**，所以"从发布目录跑一遍"是必要验证。
4. **补齐引用比删除引用更值得 —— 但先问"这功能还该存在吗"。** 删文案成本更低，可如果工具本身有用，补分发才是对的。
5. **`.ps1` / `.bat` 随下载分发会被执行策略或标记拦住。** 文档里给出可直接复制的完整命令（含 `-ExecutionPolicy Bypass`），并说明**这是让文件能跑，不是建议改系统设置**。

排查"设置项该不该置灰"时：

1. **核对"选项 A 的回退目标"与"选项 B"是不是同一个。** 有回退链就可能存在**两选等价**的配置 —— 等价时禁用其一，否则用户以为自己在做选择。
2. **"选了会回落到 X"这种提示，说明选项本身就不该可选。** 提示是补救，禁用才是正确表达。
3. **能检测的就检测并禁用；不能检测的就说明"未知"并指出去哪查。** 两者判据同一条，但**不要假装有一个我们没有的检查** —— 基于猜测禁用比说明未知更糟。
4. **可用性检查不要缓存到进程级。** 被检查的对象（显示器配置、驱动设置、外接设备）可能在使用期间变化，而用户的操作顺序常常正是"看到提示 → 去改 → 回来"。**缓存要有时限**。
5. **禁用时要给出原因和出路。** 灰掉的控件没有解释就是死路。

排查"多个选项需要用户选一个"时：

1. **先问：这三个选项里，有没有哪一个回答了"我该选哪个"？** 通常没有 —— 每个都只说"我做什么"，而用户带着的是"**我的硬件适合哪个**"。这个问题的答案往往**不需要任何检测**，只需要写一行。
2. **补一行"怎么选"，并让它跟随检测结果。** "用第 3 项"写在**灰掉的第 3 项旁边**是没用的建议。措辞必须与置灰条件一致 —— 两者读同一个值（本例中把 `arcadeModeAvailable` 上提到段首只读一次，就是为了这个）。
3. **列出所有用户状态的组合，找出"每个选项都不理想"的那一格。** 本例是"无 VRR + 无自定义模式"：一个灰着、另一个选了没用，**而没有任何引导**。这一格就是缺口所在。
4. **区分"可证的失败"与"只是错过"，决定是否禁用。** 可检测且失败可证（会精确做另一选项的事）→ 禁用；不可检测且失败只是错过（会话照常、不比默认更差）→ **不禁用，说明后果**。基于看不见的能力禁用，等于**从最想要它的用户手里拿走这个选项**。
5. **也要说清"选错了会怎样"，而不只是"需要什么条件"。** 用户最怕的是"选了会不会把机器搞坏"。写明"不会报错也不会更差，只是退回默认行为"能消除这个顾虑。

排查"想检测某项硬件能力"时：

1. **先确认这个数据到底在哪个通道上。** 本例中 VRR 范围**不在 EDID**（我拆了完整 EDID 验证：无 Adaptive Sync 块）—— 它走 **DPCD 寄存器 / AUX 通道**，只有内核态显示驱动能读。**"Windows 能显示它"不等于"应用能读到它"** —— 系统组件常常有更高权限的通道。
2. **按能力来源分层排查，并记录每层的否定结果。** 本例依次排除了 EDID、Windows SDK、SDL、Vulkan present mode、NVAPI 按名导出 —— **否定结果本身就是交付物**，它让后来者不必重查一遍。
3. **区分"是否支持"与"参数是否落在范围内"。** 大多数可得路径只能回答前者，而需求往往是后者（"VRR 范围是否含 57.5Hz"）。**拿到一个答非所问的值，比没有更危险。**
4. **厂商 SDK 的可用性要在目标机器上验证，而非假设。** `nvapi64.dll` 存在且 `nvapi_QueryInterface` 已导出（说明可动态加载），但函数**按 ID 取而非按名导出** —— **探测不到就等于无法验证**，不能凭"库在"就认为"能用"。
5. **做不到检测时，把答案的"去处"写清楚，并说明为什么只能是文案。** 只写"请自行查看"是把问题推给用户；写清"在哪看、每个地方回答哪个问题、为什么程序读不到"，才是完整的交付。
6. **信息源按"回答哪个问题"组织，而不是列清单。** 本例三个来源分别回答"是否支持 / 范围是多少 / 此刻是否在变频" —— 用户带着哪个疑问，就知道该看哪个。

排查"第三方给的检测方案能否采纳"时：

1. **逐条实测每个断言，并把否定结果记下来。** 本例资料里 8 条断言有 5 条不成立；**否定结果本身就是交付物**，它免得后来者把同一条路再走一遍。
2. **区分"这个字节存在"与"它表示你以为的那个意思"。** `0xFD` 描述符确实存在、偏移也确实写对了（我先前算错偏移，是我的错），但它是**时序范围而非 VRR 声明** —— 几乎每台显示器都有。**解析正确 ≠ 语义正确。**
3. **最有力的检验：拿"已知为真"的样本去测。** —— 但**也要检查自己有没有走对支路**：本例中我正是拿"已知支持 VRR 的显示器"去测，却因为只解析了 `tag == 7`（扩展标签）而漏掉顶层 `tag == 3` 的 VSDB，于是得出了"EDID 里没有 VRR 声明"的**错误结论**。**"用已知正例检验"是对的，但检验失败时，先怀疑自己的解析路径，而不是先怀疑正例。**

> **本条的更正（重要）**：我先前断言"VRR 范围不在 EDID、无法检测"是**错的**。补上顶层 `tag == 3` 的 VSDB 解析后，显示器 EDID 里确有 `00-00-1A`（AMD/VESA Adaptive-Sync）并带范围（48-144 Hz）。完整教训见**案例 26**。
4. **注意"历史残留"这类数据源污染。** 注册表 EDID 保留了**所有曾连接过**的显示器（本例 7 条，活动仅 2 条）。代码注释声称"跳过残留节点"，但 `except` 只捕获"键不存在"，捕获不到"键在而设备已拔" —— **注释描述的意图与代码行为不符，是要专门核对的一类点**。
5. **能力类判据要问"它究竟在测谁"。** `DXGI_FEATURE_PRESENT_ALLOW_TEARING` 测的是**驱动/合成器**能否无同步呈现（Win10 1803+ 基本都为真），与**显示器**无关；拿它当 VRR 判据会在任何机器上返回真。
6. **层次不同要分开说。** "系统能显示某项信息"说明**数据存在**，但不说明**用户态可达** —— 本例数据在内核驱动的 DPCD 通道里。**顺着这个矛盾去查，往往能找到真正的根因与真正的边界。**
7. **采纳其中站得住的那一块，并明确标注它的语义边界。** 本例最终用 `0xFD` 回答"面板会不会接受 57.5Hz 时序"，并写明"**与 VRR 无关**" —— **把必要条件当必要条件说，不冒充充分条件**。
8. **成本要配得上收益。** 辅助信息若依赖昂贵调用（WMI 数十毫秒），就**只在需要时抓一次并缓存**，不要放进每帧或定时路径。

## 案例 46：范围链漏了一个区间，索引变成 4 GB 偏移

**症状**：音频改造后的第一版构建，两个 exe（SDL2 的 LegacyOG 和 SDL3 的 VK）
一进游戏 1–2 秒就 `0xC0000005`；加 `-no-sound` 跑 12 秒完全正常。日志停在启动阶段，
没有任何异常信息。因为 `-no-sound` 同时会跳过 SCSP 与声音板 68K，第一层判断
"崩溃在声音路径"很容易，难的是定位到哪一行。

**定位过程（可复用）**：

1. Windows 已经为进程写了 WER minidump（`%LOCALAPPDATA%\CrashDumps`）。
2. 用脚本读 `MINIDUMP_HEADER` 的 ExceptionStream：异常码 `0xC0000005`、写操作、
   目标地址 `0x7FF8E4550DAC`、RIP 落在 exe 的 `+0x1AD91A`。
3. 从 ExceptionStream 的 CONTEXT 读寄存器：`rdx = 0x7C0`、`rax = 0x7FFFFFE0`、
   `r8 = SCSPs`。这些值已经把答案写出来了。
4. 为了把 `+0x1AD91A` 变成函数名，临时给 MSVC 链接加 `/MAP` 重新生成 map。
   先 `cmp` 新 exe 与部署 exe：**只有 6 个字节不同**（PE 时间戳/校验和），
   代码布局完全一致，map 的符号地址才可信。得到
   `SCSP_w32 + 0x14A`，调用栈里还有 `SCSP_DoMasterSamples` →
   `SCSP68KRunCallback` → `m68k_op_clr_32_pi`。
5. 反汇编该地址：`mov word ptr [r8 + rax*2 + 0x159C], r10w`，就是
   `SCSP->DSP.MPRO[(addr - 0x800) / 2] = val`。

**根因**：`SCSP_w32()` 的分支链是

```cpp
if (addr < 0x780) COEF;
else if (addr < 0x7C0) MADRS;
// 0x7C0–0x7FF 只是注释，没有分支
else if (addr < 0xC00) MPRO[(addr - 0x800) / 2];
```

`addr = 0x7C0` 落进 `MPRO` 分支，而 `addr - 0x800` 是 **unsigned**：
`0xFFFFFFC0`，右移后 `rax = 0x7FFFFFE0`，字节偏移 ≈ 4 GB，
`SCSPs + 0xFFFFFFC0 + 0x159C` 直接访问违例。`SCSP_w16()` 有显式的
`else if (addr < 0x800) {}`，`w32` 在改的时候只写了注释，漏了分支。

**修法**：补上显式空分支：

```cpp
else if (addr < 0x800)
{
    // Reserved hole: discard. Falling through would compute (addr - 0x800) / 2
    // unsigned, i.e. a ~4 GB offset.
}
```

**能带走的教训**：

1. **地址/范围链要逐段对账，不能只删中间一段。** 删掉 `MADRS` 分支后，
   原来的 `else if` 会自动把空档交给下一段。写“丢弃”逻辑时，
   **空分支必须是代码，不是注释**。
2. **索引表达式里的无符号减法要在分支里保证下界。** `(a - b) / 2` 在 `a < b`
   时不会得到负数，而是巨大的正数；即使没有符号问题，也会越界。
   在 `if` 链里，每个算术分支都应能证明自己的输入范围。
3. **“只有开声音才崩”已经把范围缩到一个子系统；再看寄存器就能到行。**
   崩溃转储里的 `rdx`/`rax` 往往直接是出错的输入值，比读代码快得多。
4. **用 map 前先证明二进制一致。** 重新链接会改变布局，先用 `cmp` 确认
   新 exe 与出问题 exe 的代码段一致（本例仅 6 字节头差异），符号偏移才有效。
5. **修复后要重跑真实会话，而不是只过编译。** 本例如果只构建不运行，
   这个 bug 会直接进发布包；`-no-sound` 存活与完整会话存活是两个都必须过
   的门。

> `DSP.md` 第六节。

## 案例 29：多附件渲染的“附带写入”与 alpha 语义

**症状**：两个看似无关的画面问题同时出现：

1. 半透明海水（低 priority）盖在后来绘制的不透明角色（高 priority）**前面**；
2. 2D 背景层的天空（VF3 的月亮/云、Lost World 的云层）**整块消失**，
   变成雾色或黑色。

**定位**：

- 先用“只画某个 priority”开关确认归属：海水在 priority 1、角色在 priority 2。
- 再做**清深度实验**：在每个 priority 开始前把深度清到近/远平面，画面**不变**。
  这一步很关键——它说明透明层根本不和角色共享深度值，深度比较方向不是原因。
  （清深度后结果变化，才应该继续查 reverse-Z / depthCompareOp。）
- 然后对照原实现：New3D 把三个颜色附件放在**同一个 FBO**，不透明层在
  `WriteOutputs()` 里向 trans1/trans2 写 `vec4(0)`。这是跨 priority 唯一的
  擦除机制，不是优化。

**根因**：

- 移植时把三个附件拆成独立 image、每个 pass 只绑一个，**“写 0 到其他附件”
  这个副作用消失了**。低优先级的透明像素一直留到帧末，合成时盖住角色。
- 合成器又把 3D 场景的 alpha 硬写成 1.0。原实现是用场景 FBO 自己的 alpha
  做 `SRC_ALPHA / ONE_MINUS_SRC_ALPHA`，alpha=0 的地方露出 Render2D 底图；
  写 1 等于永远不透明覆盖，2D 天空自然消失。

**修法**：

- 每个场景 pass 绑定全部三个颜色附件，用 pipeline 的 `colorWriteMask` 选择目标；
  颜色层三个 mask 全开，着色器写 `colour + 0 + 0`，透明层只开自己那个。
- 合成改为保留场景 alpha 的 source-over：
  `a = ta + ba(1-ta)`，`rgb = (trgb*ta + brgb*ba(1-ta)) / a`；两层透明重叠时
  才输出 alpha 1。

**能带走的教训**：

1. **“往别的附件顺手写 0”是渲染语义，不是实现细节。** 拆分渲染目标时，
   要把所有附件当成一个整体检查：谁写谁、谁擦谁。
2. **alpha 是“这一层是否覆盖背景”的信息。** 合成时写死 1 会静默吃掉下层；
   只要原实现用了混合，就要把它的两次混合推导成等价的 source-over，
   而不是“看起来像不透明就写 1”。
3. **先证伪最简单的假设。** 本例若一开始就调 `depthCompareOp`，会改出
   Daytona 2 瀑布那样的新问题；清深度实验只花一次截图就能排除整条方向。
4. **对照原实现时看“副作用”，不只看着色公式。** FBO 多附件、混合状态、
   清屏 alpha 都属于“不在 draw call 参数里”的行为。

## 案例 49：测试脚本改了配置，硬中断后没有还原

**症状**：跑过截图/帧率脚本后，**设置窗口整窗马赛克或闪动**，游戏内渲染正常；
代码和构建都没改过。

**定位**：

- 先看配置：`VulkanDevice` 是否是测试里用的那块显卡，`XResolution` / `FullScreen`
  是否也是测试值。ini 旁边若还有 `<ini>.testbak` / `<ini>.testrun`，基本可以定案。
- 再看进程：脚本被 `Stop-Process`、关终端或调试器强停时，`try/finally` 没有机会运行。
  单纯 Ctrl-C 通常还能走 `finally`，所以“上次是怎么结束的”决定了会不会留残留。

**根因**：测试脚本为了跑一组参数而就地改写配置，备份只存在脚本内存里。
进程被硬杀后没有还原路径，下一次启动就按测试配置初始化。

**修法**：

- 覆盖期间把原始文件字节复制到 `<ini>.testbak`，把补丁文件的 SHA-256 写进
  `<ini>.testrun`；还原时只在“当前文件仍等于补丁指纹”时覆盖，避免抹掉用户
  之后的编辑。冲突时保留现文件，原配置另存 `<ini>.testoriginal`。
- 每个测试脚本启动时先尝试还原一次；另提供手动入口 `Tools\Restore-TestIni.ps1`。
- 补丁与启动放进同一个 `try/finally`；中断时先关闭被测进程再还原，保证文件最后
  一次写入是用户配置。

**能带走的教训**：

1. **“临时改配置”的工具必须有跨进程的撤销信息**（备份 + 指纹），不能只靠
   `finally`；硬杀是常规操作，不是异常。
2. **故障现象可能指向完全不同的子系统。** 跨显卡渲染表现为马赛克，第一反应往往是
   渲染器；先检查输入（配置/环境）再查代码。
3. **还原要保守**：发现文件在中断后被编辑过，就不要覆盖，把原配置留成副本。

> 项目内详见 `devdocs/CHANGELOG.md` 的「工具：测试脚本的临时 ini 覆盖带崩溃恢复」一节。

## 案例 50：同一份存档“卡死 → 无声 → 只剩音乐”——三个独立故障叠在一起

**症状**：从「管理存档」冷启读 `scudplus.zst1`（Scud Race 选车画面）会卡死；
死循环修掉后，选车画面几乎没有声音；进赛道只剩音乐，没有引擎/碰撞/轮胎声。
把 `NbSoundChannels` 从 4 改成 2，三者全部消失。很容易当成“一个音频 bug 修了三次”。

**第一层是死循环，不是静音。** 主线程停在 `EndSimulationFrame()` 等声板，日志最后
一个声板标记是 `DSB begin`。`SM3D_LOAD_DEBUG` 打出存档字段：

`loaded=1 start=2147516416 end=2147516416 loopStart=0 loopEnd=2147516416 offset=712512`

`2147516416` 就是 `0x80008000`：板子固件的“无曲目”哨兵，不是窗口。旧 `SetMemory()`
不校验，`dec.size` 为负 → `EndOfBuffer()` 恒真、`loop` 每轮把 `pos` 清 0、
`frame_bytes` 也是负的，`DecodeAudio()` 永不返回。`isPlaying` 在这里没有判别力，
它只是 `IsLoaded()`（`buffer != nullptr`）。

**第二层是寄存器和真实播放状态分叉。** 存档里 `loaded=1` 且 `offset` 是一只播到
712 KB 的真实位置，说明 `MpegDec` 确实在放；但 Z80 把下一首命令暂存在
`mpegStart/mpegEnd`，影子变量 `usingMPEG*` 被留成了哨兵。**只恢复影子变量就会
丢掉正在放的曲子**。修法：在 DSB 块之后追加可选块 `DSB1 MPEG` / `DSB2 MPEG`
（magic `MPG2`），存解码器真实的活动窗口 + 位置 + loop；读档优先用它，旧存档没有
这个块则回退到校验过的旧字段。老版本读新存档会按名字跳过该块，所以 `isPlaying`
在保存时要按“旧字段是否可用”过滤，免得把哨兵再喂回旧版本。

**第三层才是“没声音”。** 存档已经能读出正确的 `mpeg=1 mpegpos=…`，声音仍不对，
才去看输出：`scudplus` 是 `QuadFrontRear`（音乐 + SCSP0 在前，SCSP1 在后），而这台
机器的默认端点只有 2 声道。`NbSoundChannels=4` 时 SDL 会自己用
`SDL_ConvertQuadToStereo`（0.421/0.359/0.22）折叠后声道，比我们 `MixChannels()` 的
平均小一截；统计浮层还照旧显示 “4 ch”。二声道端点应当由我们自己的混合器折叠。
现在 `OpenAudio()` 先 `SDL_GetAudioDeviceFormat()`，设备不足 4 声道就降为 2，
日志写 `folding the quad mix down to 2`。

**能带走的教训**：

1. **先拆“停住”和“没声音”。** 卡死时不要调音量；线程标志（`sndDone=1`）只说明
   跑完了，不说明发出了什么。看消费端状态（`mpeg=` / `mpegpos=` / `slots=`）。
2. **存档里要保存“消费者正在用的状态”，不是上游影子寄存器。** 影子寄存器会被
   下一条命令覆盖，而解码器窗口不会。新增设备状态时问一句：读档时它从哪里重建？
3. **旧字段是兼容层，必须有白名单校验。** 负数、相等起止、超出 ROM 容量的值
   一律拒绝；能安全降级成静音，就不要冒着死循环的风险去“尽量恢复”。
4. **输出设备的真实能力要主动查询。** 让库去猜声道数，失败形态是“音量不对 +
   界面显示错误”，不会报错。
5. **`usingLoopEnd` 是长度还是终点，这种语义差必须在代码旁写清楚**；两种写法
   都“看起来合理”，错一次就是一个负的窗口。

> 项目内详见 `devdocs/CHANGELOG.md` 的 2026-10-27「存档读档：Scud Race 卡死、
> 无声与四声道折叠」一节。

## 案例 51：“新后端一启动就死在引导 ROM 的自旋里”——返回值寄存器被自己的重载代码覆盖

给 PowerPC 写 x86-64 混合 JIT 时，块出口和每次慢速总线调用之后都要从 `s_pins`
重载四个固定指针（`r12`/`r13`/`r14`/`r15`）。第一版拿 `rax` 当这个重载的基址，而那正是
“刚读到的值 / helper 的返回值”：

```
mov rax, &s_pins      ; 把读到的数据抹掉了
mov r12, [rax+0]
...
```

**症状**：所有游戏都卡在引导阶段，PC 永远停在 `FFF001AC`（`b .` 自旋），日志里
`13 block(s) translated`、`0 helper call(s)`。根因是引导代码用 `lhbrx` 读 PCI 配置寄存器
得到 `0x91E1A86F`（`&s_pins` 的低 32 位）而不是设备 ID `0x1057`，于是 `cmpli` 不匹配、
跳进死循环。

**为什么锁步校验器没抓到**：带设备访问的块会被标记 `busTouched` 并跳过比对（设备寄存器
不能重复读），而 PCI 配置端口正好是设备访问。逐块比对能抓算术/标志位/寄存器的错，
**抓不到“块内所有设备读都返回同一个垃圾值”这类错**。

**能带走的教训**：

1. **写生成代码时给每个寄存器写清楚“这里装着什么”**，特别是跨调用边界。
   `rax`/`xmm0` 在几乎每个 ABI 里都是返回值寄存器，天然不适合做常量基址。
2. **“永远卡在同一个 PC + 极少的块数”是死循环的指纹**，而且它把范围缩到很小的
   一段代码；拿 `SM3D_PPC_JIT_DUMP=1` 把活动块反汇编出来，一眼就能看到 `b .`。
3. **验证器有盲区时，要有一个“绕过验证器”的对照**：这里就是同一存档用
   `SM3D_PPC_JIT=0` 跑一遍——解释器能过引导、JIT 不能，立刻把问题限定在 JIT 身上。
4. **同一个类的第二个 Bug 会藏在 `break` 的作用域里**：`case` 块里 `break` 属于
   *最近的* `switch`，在嵌套 switch 的回退分支里写 `if (bad) break;` 会继续执行后面的
   发射代码。要么 `if (!bad) { …; return; }`，要么显式 `goto` 到一个命名标签。

> 项目内详见 `sdl3_reports/2026-10-30-ppc-x64-jit/README.md`。

## 案例 52：“导出的图是坏的”——其实是一个运行时根本不读的通道

把游戏内部资源导出成图片，是做高清包、做对比、投稿反馈时最先用到的功能。导出器通常按
**存储格式**把每一位都解出来，而**渲染器只按材质读其中一部分**。两者的差集就是这类报告。

**症状**：导出的角色脸部贴图被白色点阵 / 竖虚线覆盖，看图软件和 GitHub 上一眼像坏图；
报告里自然问“是不是导出功能不完善”。

**定位顺序**（关键是先把“位置错”和“语义错”分开）：

1. **把可疑通道单独画成一张图**（`Image.fromarray(a[:,:,3], "L")`）。这里立刻看到 2 px
   周期的竖条，而且某些图里能看出摩托车 / 人物剪影——是美术做的掩码，不是内存垃圾。
2. **看直方图**：alpha 只有 `0` / `255` 两档、纯白 RGB 为 0 %，说明白点是**透明**而不是
   白像素；行首像素 `(239,189,132,255)` 与 `(239,189,132,0)` 颜色一致，只有 alpha 翻转。
3. **新旧两版导出逐像素比对**：同一哈希的 **RGB `array_equal` 全为真**——取子图坐标、
   页选择、wrap 掩码、行跨度、位深全部没问题，剩下的只有语义。
4. **回到渲染代码看谁真的读这个通道**：
   `if ((flags & kTextureAlpha) == 0 && !alphaTest) a = 1.0;`——对不用 alpha 的材质，
   导出的 alpha 根本没参与画面。

**修法**：把「材质是否读这个通道」带进导出，让导出文件等于**渲染器真正采样到的像素**；
不用 alpha 的写全不透明，带 alpha 的保留原机掩码。同一个哈希可能先被“不读”的材质遇到，
所以要能**重导一遍**（记录哪些是削平写的），不能靠遇到顺序定稿。

**能带走的教训**：

1. **导出 / 回读类工具的输出应该是“运行时用的值”，不是“存储里的位”。** 两者的差集只会
   制造虚假的 bug 报告；如果确实要保留原始位，那是第二个开关、第二个文件，不能默认。
2. **先用一个不依赖肉眼的读数把“位置错”排除掉**（同哈希旧新导出 RGB 全等），否则会在
   坐标 / 跨度 / 位深上白花一天。
3. **单通道可视化是定位这类问题的第一手段**，比看合成图快一个数量级。
4. **“白点”在合成图里既可能是透明也可能是白像素**，一句话说清颜色空间，方向就唯一了。
5. 顺手把诊断做成工具（`Tools/inspect-texturedump.py`）：下次同类报告一条命令就有结论。

> 项目内详见 `sdl3_reports/2026-11-01-dump-alpha-dither/README.md`。

## 案例 53：“选了 4K 也没用”——同一块屏上“点”和“像素”是两个空间

跨平台图形代码最容易埋的坑之一：**窗口尺寸和 drawable 尺寸在高 DPI 系统上不是一个值**。
把一个当另一个用，往往不报错、不崩，只是“高分辨率设置不生效”，很容易被归到显卡/驱动/游戏。

**症状**（GitHub 评论，Mac 用户）：4K Apple 显示器，系统缩放选「默认字号」，程序里选 3840×2160
没有效果；必须把桌面切到「更多空间」才正常。另外还有人会把它描述成“输出不变成宽屏”。

**先纠正一个模型**：macOS 的「默认字号」**不是**把面板跑成 1080p。面板仍是 4K，系统给应用的是
1920×1080 的**点**加 2 倍后备缓冲；申请了高密度 drawable 的应用拿到的就是 3840×2160。
所以“它以为是 1080p”这个描述方向对，但不能据此去改显示模式。

**定位顺序**：

1. **先列出两类尺寸**：`SDL_GetWindowSize()`（point）、`SDL_GetWindowSizeInPixels()`（drawable）、
   `SDL_DisplayMode::pixel_density`。只用其中一个算几何，就会出现“设置无效”或“1/4 画面”。
2. **找谁在消费几何**：`xOffset/xRes/totalXRes` 同时被渲染器（像素）、2D 合成/bezel/准星
   （像素）、输入系统（窗口坐标）使用。混用是症状的根源，不只是一个函数写错。
3. **搜“写死的 1.0”**：`io.DisplayFramebufferScale = ImVec2(1,1)` 这种带“swapchain 等于窗口
   尺寸”注释的代码，在改成高密度 drawable 后会立刻把面板画进左下四分之一。
4. **看基础设施是否给了比例**：`SDL_DisplayMode.pixel_density` 在 SDL3 里有；SDK 版本旧或后端
   没填时它会退化成 1.0（SDL 会归一化），所以读到 1.0 时要区分“真的 1x”和“没这个字段”。

**修法**：把两个空间分开，而不是把某个函数从左换到右：

- 渲染几何（画框、视口、bezel、准星、整数倍缩放、CRT 预设）**全部用设备像素**，
  入口是一个函数（`GetRenderSize()`），其它地方不再自己读窗口尺寸。
- 输入系统与鼠标仍用**窗口坐标**，在调用点换算（`WindowSpacePictureRect()`）。
- 游戏窗口在 Apple 上加 `SDL_WINDOW_HIGH_PIXEL_DENSITY`；其它平台不加（数值本来相等）。
- 面板/UI 的 `DisplayFramebufferScale` 必须来自真实的 drawable/window 比。
- 窗口尺寸（`SetWindowSize`）仍用点：API 本身要的就是点，改成像素会让全屏窗口比屏幕大一倍。

**能带走的教训**：

1. **“高分辨率设置不生效”先查空间，不查分辨率**。把 point 和像素混用一次，能白白怀疑
   显卡、驱动、显示模式一整天。
2. **一个量只能有一个来源**。几何入口收敛到一个函数，比在每个调用点“记得换成像素”可靠。
3. **同一份坐标既有像素又有 point 需求时，转换要发生在边界上**（输入入口、ImGui 入口），
   不要在数据结构里塞一个 `dpi` 字段让每个消费者自己乘。
4. **改完要检查“写死的 1.0”**：ImGui、镜像、模糊链、截图、bezel 都可能有同类注释假设。
5. **无真机的平台不要声称已验证**。这次的 Windows 值不变（已编译并启动确认），
   macOS 只能列复测清单（日志的 `(2x: ...)`、swapchain extent、面板/准星尺寸）。

> 项目内详见 `devdocs/CHANGELOG.md` 2026-11-01「macOS Retina 屏上 4K 设置无效」与
> `issues_from_users.md` 的 gamerg_ 条目。

## 案例 54：单键切视角把“瞬时按钮”写成了“常驻按死”，静默触发街机隐藏选歌秘技

**症状**：在刚刚修过 MPEG 音乐前奏负偏移（`MpegAudio.cpp`）之后，用户测试《Daytona USA 2》发现：**不管是初级环形赛道、中级海盗船赛道还是高级城市赛道，只要车一发动进入比赛，播放的永远是同一首 BGM**。第一反应极其容易怀疑是前一晚改的 `MpegDec` 负偏移把所有曲目指针算到了同一个地址。

**定位顺序（先分清“是播放器放错了”还是“主程序就点了这首歌”）**：

1. **直接看存档里的硬件命令历史，而不是猜解码器**：解压初级赛道（`dayto2pe.zst12`）与中级赛道（`dayto2pe.zst15`）两个存档，检查 DSB2 68K RAM（`0xF00000`）收到的主板 MIDI 命令缓冲：两份存档在发车时主板发来的字节序列**一模一样**——`ae 10 0a`（选车曲）→ `ae 10 00`（停止）→ **`ae 10 08`**（播放 8 号曲目）。
2. 这一下直接给 MPEG 解码器洗清嫌疑：**是游戏主板的 PowerPC 程序自己点名要放 8 号曲目**。
3. **查 8 号曲目在游戏里代表什么**：反汇编 DSB2 68K 固件 `epr-20886.ic2` 的曲目表（`0x8008`），初级、中级、高级赛道的正常 BGM 是 `AE 10 02`、`03`、`04`；而 `AE 10 08` 是《Daytona USA 2》的**官方隐藏选歌彩蛋——在选完车进入赛道加载时，如果玩家一直按住面板上的某个 `VR` 视角键不放（Hold VR1~VR4），游戏就会强制把该局 BGM 换成对应曲目**，其中按住 `VR3（黄键）` 正好对应 `AE 10 08`！
4. **回到输入代码看谁按住了 `VR3`**：`CInputs::IsVRSelected(int index)` 在 `VRCycle = 1`（单键循环切视角，默认开启，起始视角 `VRDefaultView = 2` 即 `VR3`）时写的是：
   ```cpp
   if (m_vrCycle)
       return index == m_vrCycleIndex;
   ```
   街机上的 VR1~VR4 是**瞬时微动按钮（按一下切视角就松开）**，而这段代码把“当前处于哪个视角”直接当成了“那个按钮一直被死死按着”，导致从开机第 1 帧起 `VR3` 永远为 `1`，100% 触发隐藏选歌秘技！

**修法**：把“状态”与“按键动作”分开。开局及选车期间不按住任何 VR 键；仅当玩家实际按下 `VRNext` 切视角时，推进 `m_vrCycleIndex` 并发出一个 **6 帧（~104 ms）的瞬时脉冲**（`m_vrPulseFrames = 6`），随后自动松开。

**能带走的教训**：

1. **硬件上的瞬时按钮（Momentary Button）绝不能在辅助功能里模拟成常闭锁死开关（Toggle Hold）**。很多街机/主机游戏把“加载画面按住某键”用作隐藏彩蛋、调试菜单或强制覆盖逻辑。
2. **刚改完模块 A 就遇到模块 A 领域的异常时，最容易陷入确认偏误**。先看模块 A 的输入指令对不对（本例中看 68K 收到的 MIDI 命令字），30 秒就能避免在解码器里白查半天。

> 项目内详见 `runbook_sound_fix.md` 第五节案例 A 与 `devdocs/CHANGELOG.md` 2026-11-04。

## 案例 55：文件头元数据正常，但帧同步字少了最高位，播放器静默扫到文件尾

**症状**：手写的内置多声道 FLAC 编码器录出的 `.flac` 文件，用 `ffprobe` 检查完全正常（`Duration: 00:02:35.92, 44100 Hz, 5.1, s32 (24 bit)`），文件大小也有 75 MB；但系统播放器打不开，用 `ffmpeg -i file.flac -f null -` 转码则报 `video:0KiB audio:0KiB, Output file is empty`。

**定位顺序**：

1. **`ffprobe` 能认出时长和格式，说明文件头的 `fLaC` + `STREAMINFO` + `VORBIS_COMMENT` 元数据块完全合法**，且块长度没有错位。
2. **`ffmpeg` 解出 0 字节且不报 CRC 错，说明解码器连第一帧的帧同步字（Sync Code）都没找到**，把后面 75 MB 全部当成未同步流跳过了。
3. **直接 dump 第一个音频帧开头的 8 个字节**（偏移 112 字节处）：看到的是 `7f f0 79 5c ...`，而标准 FLAC 帧开头必须是 **`ff f8`**！
4. **看代码**：FLAC 帧头前 16 位是 `14-bit sync (11111111111110b) + 1-bit reserved (0) + 1-bit blockingStrategy (0) = 0xFFF8 (16 bits)`。写代码时把 16 位的 `0xFFF8` 错拆成了 `PutBits(0x3FF8u, 15)` + `PutBits(0, 1)`，最高位被 `0x3FF8` 吃成了 `0`，整体左移 1 位变成了 `0x7FF0`。

**修法**：改为 `m_frameBw.PutBits(0xFFF8u, 16);`；对已经录下的 75 MB 文件，用脚本遍历每帧将开头 2 字节还原为 `0xFF 0xF8` 并重算帧头 CRC-8 与帧尾 CRC-16，即可原地无损抢救。

**能带走的教训**：

- **位流编码器写完后，不能只看 `ffprobe` 识别出头信息就算过**，必须跑一次 `ffmpeg -v error -i out.flac -f null -` 确认解码出的样本帧数与写入帧数一致。

> 项目内详见 `runbook_sound_fix.md` 第三节。
