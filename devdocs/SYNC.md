# 街机 57.524Hz 同步兼容性诊断

本文汇总 Supermodel-VK 在**显示器与显卡的 VRR 能力、特殊刷新率兼容性**方面的诊断逻辑、
实测数据、以及**做不到的部分及其原因**。

`TECHLOG.md` 与 `FIXES.md` 记录"改了什么"和"这类问题怎么查"；本文是**面向同步问题的一份
独立参考**，把散落在各处的结论集中起来，便于查证和向用户解释。

> **阅读约定**：本文严格区分「**实测**」与「**未验证**」。凡未在本机硬件上验证过的说法，
> 都明确标注 —— 这类断言最容易在转述中被当成事实。

---

## 一、问题的根源：Model 3 不是 60Hz

Model 3 的 Real3D 硬件扫描在 **57.524160 Hz**，不是 60Hz。

`Src/Model3/Model3.cpp:2052` 记着完整时序（沿用 System 24 血统）：

```
25 行  /VSYNC 高 → /BLANK 高   （上部边框）
384 行 /BLANK 高 → /BLANK 低   （活动显示 = 496x384）
11 行  /BLANK 低 → /VSYNC 低   （下部边框）
4 行   /VSYNC 低 → /VSYNC 高   （垂直同步脉冲）
------------------------------------------------
424 行合计：384 活动 + 40 消隐
```

由此派生出两个频率，**都必须理解**：

| 量 | 值 | 用途 |
|---|---|---|
| **垂直频率** | **57.524160 Hz** | 仿真步长、音频每帧样本数、驱动板计时 |
| **水平频率** | 57.524160 × 424 = **24.39 kHz** | 中等分辨率档次（见第五节） |

### 为什么不能就用 60Hz

`RefreshRate` 可选项是 **57.5Hz** 与 **60Hz**（界面标 60 为"推荐"——因为它兼容性最好）。
但要注意一个**关键设计**：

```cpp
// Model3.cpp:2062 —— 仿真步长【硬编码】为街机精确值
unsigned frameCycles = (unsigned)((float)ppcCycles / 57.524160f);
```

**仿真时间步长与 `RefreshRate` 是互相独立的。** 所以选 60Hz 不是"换个帧节奏"，而是让
游戏**跑快 4.30%**。统计读数里那行 `Rate:` 就是把这个差值算给用户看：

```
Rate: 60.00 Hz  arcade 57.52  (+4.30%)
```

## 二、三条同步路线：各自要求什么

代码里是 `enum class FullScreenMode`（`Main.cpp:239`），对应界面三个单选项。

| | 模式 | 要求（显示器） | 要求（显卡/驱动） | 代码可确认性 |
|---|---|---|---|---|
| **1** | **无边框全屏**<br>`Borderless` | 无 | 无 **（例外见 2.1）** | ✗ **面板是否按自身速率无法确认** |
| **2** | **独占 · G-SYNC/VRR**<br>`ExclusiveDesktop` | 支持 VRR，**且 VRR 范围含 57.5Hz** | 支持并在驱动里启用 | ✗ **2026-10-14 更正**：若显示器不能变频，本模式**退化成第 1 项**（见 2.2） |
| **3** | **独占 · 固定街机刷新率**<br>`ExclusiveArcade` | **时序范围含 57.5Hz** | **能在控制面板创建自定义分辨率** | △ 能查模式列表；**建不建得成查不到** |

### 2.1 无边框并非必然用桌面速率

**这是本文最容易搞错的一处，因为它取决于驱动设置而非显示器能力。**

Windows 的 DWM 按桌面速率合成窗口，所以**默认情况下**无边框下 VRR 不介入，面板保持自身速率，仿真帧被"套接"上去 —— 这也是长时间以来的通行说法。**但 NVIDIA 提供把 G-SYNC 应用于窗口输出的选项**：

| NVIDIA 控制面板「设置 G-SYNC」 | 无边框下面的行为 |
|---|---|
| **仅为全屏模式启用**（驱动默认） | DWM 按桌面速率合成，面板保持 **120Hz**（或桌面速率） |
| **为窗口和全屏模式启用** | **面板可以跟随合成窗口**，无边框也能达到 1:1 |

所以"无边框不能 VRR"应改为"**无边框默认不能，除非驱动被配置为对窗口输出也应用 VRR**"。

**而这无法从程序内检测**：两种情况下面板都在被刷新，程序都以相同速率呈现、读数也都是同样的 FPS —— 对应用来说**完全无差别**。**唯一的地面真相是显示器自己的实时刷新率读数**（约 57-58Hz = 已生效；显示 120Hz = 未生效）。

> 因此 `Cadence:` 那行现在明确标注了前提（`if panel @ own rate` / `assumes the panel is at its own rate`），`Sync:` 行也从 `borderless, VRR off` 改为 `borderless (panel keeps its own rate)` —— **把断言换成前提**。

### 2.2 第 2 项并非总是优于第 1 项

**这一点是实测发现的**（用户笔记本：Intel UHD 620 + 1920x1080@60Hz 内屏，读数为 `exclusive VRR (preconditions met)`）。

`ExclusiveDesktop` 的"1:1"**依赖显示器真的变频**。若显示器不支持 VRR，本模式**不报错、也不会更好**，而是退化成"面板按自身速率 + 帧被套接" —— **与第 1 项完全等价**。

而两者**原本的差别是诊断能力，且方向相反**：

| | 帧节奏（`Cadence:`） |
|---|---|
| 无边框 | **会报**（曾设计为仅此模式） |
| 独占 VRR | **不报** ← 退化成无边框的情形反而最安静 |

同一台笔记本、同一面板、同一内容，只换同步模式：

```
独占 VRR ：（无 Cadence 行）
无边框   ：cadence uneven - 1.0435 panel scans per frame.   （60 ÷ 57.5 ✓）
```

**已修**：`ClassifyCadence()` 现在也覆盖 `ExclusiveVrr`，措辞按模式区分：

```
Cadence: uneven if VRR is not engaging (2.09 scans/frame)
         a VRR session is 1:1 only if the display really varies;
         if it cannot, the fixed-rate sync mode removes this
```

（**`Even` 档不加限定语** —— 面板自身速率若为模拟速率的整数倍，VRR 变频与否都均匀。）

> **实用推论**：**笔记本内屏通常不支持 VRR**，这类机器上第 2 项与第 1 项等价，可以留在第 1 项。界面提示里已写明。

### 2.3 回退关系

```
选 3（固定街机）→ 找不到 57/58Hz 模式 → 回退到 2（G-SYNC）
选 2           → 进了独占全屏，但面板是否真在变频 → 查不到
选 1           → 面板按自身速率，与仿真帧"套接"（除非驱动窗口 VRR 生效）
```

> **因此模式 3 在无可用的 57/58Hz 模式时是"空选项"** —— 它与模式 2 结果完全相同。
> 界面已把它**置灰**（`Gui.cpp`），因为**两个选项做同一件事、其中一个还描述了别的
> 东西，比一个不可用但说明原因的选项更糟**。

## 三、模拟器**能**自动检测什么

### 3.1 是否存在 57/58Hz 显示模式 ✓ 可靠

```cpp
// Main.cpp:625 FindArcadeDisplayModeImpl()
if (mode.refresh_rate != 57 && mode.refresh_rate != 58)
    return false;      // SDL 只报整数 Hz，自定义的 57.5242 显示为 57 或 58
```

三趟优先序（`Main.cpp:654` 起）：**渲染分辨率 → 桌面分辨率 → 任意**。这样不必为每种
分辨率都建一个自定义时序。

「能出现在 SDL 的模式列表里」意味着**驱动认它**（来自 EDID 或用户建的自定义时序），
所以这个检查是**可信的**。

### 3.2 面板时序范围 ✓ 可靠（`EDID 0xFD`）

基础块偏移 54/72/90/108 四个 18 字节描述符，`+3 == 0xFD` 即范围描述符。
**每个显示器都有**，`+5`/`+6` 为垂直最小/最大 Hz。

**它能回答"自定义分辨率值不值得建"**：低于面板时序范围的自定义分辨率会被拒收。

**但结论强度不对称**（见第四节）—— 这是本检查最重要的性质。

### 3.3 显示器是否**声明**了 VRR 范围 ✓ 可靠

CTA-861 扩展块（块首字节 `0x02`）里的**顶层 `tag == 3` 的 VSDB**，
OUI 为 `1A 00 00`（**AMD / VESA Adaptive-Sync**，注意小端序），载荷：

```
d[0..2] = OUI (1A 00 00)
d[3]    = 版本
d[4]    = 标志
d[5]    = 最小垂直 Hz
d[6]    = 最大垂直 Hz
```

> **踩过的坑**：第一版只解析了 `tag == 7`（扩展标签）支路，**漏掉顶层 `tag == 3`**，
> 于是得出"EDID 里没有 VRR 信息"的**错误结论**并写进了文档。CTA 块是**两级标签结构**，
> 见 `FIXES.md` 案例 26。

### 3.4 接口类型 ✓ 可靠（两条独立途径）

| 途径 | 实现 | 实测值 |
|---|---|---|
| **WMI** `WmiMonitorConnectionParams.VideoOutputTechnology` | 枚举值，5=HDMI、10=DisplayPort | S24F350=**5**、G70D=**10** |
| **EDID 第 20 字节** | 低 4 位：1=DVI、2=HDMI-a、3=HDMI-b、5=DP | G70D=**0xB5**→DP |

两者**互相印证**。注意 EDID 第 20 字节仅在 **EDID 1.4** 定义；S24F350 是 EDID 1.3，
该字节为 `0x80`（未定义），此时**只有 WMI 那条途径有效**。

### 3.5 硬件编码方式：**用 WMI 而不是直接读注册表**

注册表 `HKLM\SYSTEM\CurrentControlSet\Enum\DISPLAY\...\Device Parameters\EDID`
保留**所有曾连接过**的显示器 —— 本机 **7 条**，而实际只有 **2 台**活动。

`WmiMonitorBasicDisplayParams`（`root\wmi`）只列**活动**的，且 `InstanceName` 可直接
映射到注册表路径（去掉末尾 `_0`）。**这是选择 WMI 的唯一原因，也是必要的。**

## 四、模拟器**不能**检测什么，以及为什么

这一节比上一节重要 —— 它划定了"哪些结论不能给"。

### 4.1 VRR 范围：**有声明才可信，无声明什么都不代表**

| 情形 | 结论 | 依据 |
|---|---|---|
| **声明了范围** | **显示器支持 VRR，范围如此** —— 报为事实 | 显示器主动告知 |
| **没有声明** | **什么都不报**，绝不写"不支持 VRR" | 支持 VRR 可以**不声明** |

**已知的不声明案例：旧版 AMD HDMI FreeSync** —— 能力在**驱动**里而非显示器 EDID 里。
所以"EDID 里没写"与"不支持"是两件完全不同的事。

> 这与 4.2 的方向**相反**，但属同一原则：**不给超出数据支撑的结论**。

### 4.2 面板时序范围：**否定可证，肯定只是必要条件**

| 情形 | 可靠性 |
|---|---|
| **57.5Hz 不在范围内** | ✓ **可证** —— 面板不会锁定到它未列出的时序 |
| **57.5Hz 在范围内** | ✗ **只是必要条件** |

落在范围内**不保证**能建成自定义分辨率，还取决于：

- 显卡驱动是否**开放**自定义分辨率（**笔记本 eDP 面板常常根本不开放**）
- 端口带宽是否够
- 面板 scaler 是否真的 1:1 透传

**界面措辞照此写明**（`Gui.cpp`），不写"可创建"而写"这只是必要条件"。

> **一个反直觉的实测结果**：57.5Hz 只比 60 低 4%，所以它**几乎总落在任何现代面板的
> 垂直范围内**（实测 S24F350 是 75Hz 屏，报 `50-75 Hz`，含 57.5）。**这个检查很少
> 给出否定结论** —— 它的价值在极少数"下限较高"的面板，以及**那些数字本身**。

### 4.3 驱动是否**真的在变频面板** ✗ 原理上不可观测

不是"API 没暴露"，而是**没有可观测信号**：

```
仿真 57.5 Hz  →  生产慢于消费
面板上限 120 Hz →  面板永远有空闲图像可取
                →  呈现调用从不阻塞
```

应用唯一能测的是**自己的 sleep 时长**，而该值在变频与否两种情况下**完全相同**
（固定刷新率下只是同一帧被多扫几次）。差异发生在"提交 → 扫描输出"之间。

> 反过来：若程序**跑得比面板快**，`FIFO` 会掐住它、实测 FPS 掉到面板速率 ——
> 那正是帧率显示暴露 vsync 上限的原理。**刻意压在面板之下，这个信号就不存在了。**
>
> 所以读数写 `exclusive VRR (preconditions met)`：**声明可确认的三个前提**，
> 而非声称结果。

**唯一的地面真相是显示器自己**：多数游戏屏的 OSD 能显示**实时刷新率**。

### 4.4 水平频率 ✗ 不检测（见第五节）

### 4.5 显卡侧的 VRR 能力 ✗ 未实现

无公开 API；NVAPI 可按 ID 动态加载但**未能验证**函数 ID 与结构体（见第七节）。

## 五、水平频率：为什么不是用户参数

**Model 3 是"中等分辨率"档次，不是标准分辨率：**

| 档次 | 水平频率 | 典型平台 |
|---|---|---|
| 标准分辨率 | **15.72 kHz** | Atari / Capcom CPS / Neo Geo / Irem |
| **Model 3** | **24.39 kHz** | 专用中等分辨率监视器 |
| VGA / 现代 LCD 最低档 | 31.5 kHz | 现代显示器起点 |

**推论**：15.72 kHz 的机台监视器**无法**同步 Model 3 的 24.39 kHz —— 这正是当年
Model 3 机台必须配专用监视器的原因。现代 LCD 最低 30 kHz 起步，**更接不了 15.72 kHz**。

**但对我们不是问题**：我们**不让显示器跑 496x384@57.5**（那才是 24.4 kHz），而是让它
在**自己的原生分辨率**下跑 57.5Hz：

```
1600x1200 @ 57.524 Hz → 总行数约 1248 → 水平约 71.8 kHz
                       落在现代 LCD 的 30-81 kHz 内（S24F350 实测范围）
```

**而且这个关系自动成立**：显示器本就在原生分辨率下以 60Hz 左右运行，垂直降到 57.5
只是低 4%，水平也随之降 4%。**垂直范围通过了，水平几乎必然通过。**

**这也是不把水平范围放进界面的理由**：

1. 它是**派生量**，不构成独立判据
2. 部分面板报**退化值**（实测 G70D 报 `69-69 kHz`，显然支撑不了它的 4K@120Hz）

**展示一个可能是错的数据，比不展示更糟。**

## 六、为什么不提供更低的刷新率

各类街机平台速率各不相同 —— 例如 Irem 的 **R-Type 是 384x256 @ 55Hz**。**但对本项目不适用**：

**Supermodel 只模拟 Sega Model 3。** 而 Model 3 的速率在仿真核心里**硬编码**：

```cpp
// Model3.cpp:2062
unsigned frameCycles = (unsigned)((float)ppcCycles / 57.524160f);
// DriveBoard.cpp:160
int frameCycles = (int)(freq / 57.524);
```

`Games.xml` **没有任何刷新率字段**，`RefreshRate` 只提供 57.5 / 60 两档。以下全部由
57.524160 派生：

- PPC 每帧周期预算
- 音频每帧样本数（`44100 / 57.524160 = 766.63`）
- 驱动板计时
- VBlank 与 ping-pong 翻转时机

**加"逐游戏刷新率"是一次深层改动，不是加个配置项。** 因此不提供。

## 七、硬件兼容性：实测数据与**未验证**断言

### 7.1 实测（本机 + 用户机器的 EDID）

| 显示器 | 接口 | 时序范围 `0xFD` | 声明 VRR |
|---|---|---|---|
| **Samsung S24F350** | HDMI（WMI=5） | **50-75 Hz** | **无** |
| **Samsung Odyssey G70D** | DisplayPort（WMI=10） | **48-144 Hz** | **48-144 Hz**（CTA `00-00-1A`） |
| **ASUS ProArt PA248QV** | 未测 | **48-75 Hz** | 未确认 |
| **HP LP2065**（4:3 专业屏） | 未测 | **48-85 Hz**（用户口述） | 未确认 |

**G70D 声明 `48-144`，而 57.5 落在其中** → 它的 G-SYNC 路线确实能在街机速率下变频。
这个结论此前只能靠"看显示器 OSD"，现在有了 EDID 证据。

**另一台实测机器（笔记本，2026-10-14）**：

| 项 | 实测值 |
|---|---|
| 面板 | 1920x1080 **@60Hz**，内屏，**无 VRR** |
| EDID | **读不到**（`Display EDID: none could be read.`）→ 界面显示"无法读取显示器 EDID" |
| GPU | **Intel UHD Graphics 620** |
| Vulkan | **无法启动** —— 既不满足 1.3，也不满足 1.2 + dynamic rendering/synchronization2 → **自动回退 OpenGL New 3D** |
| 帧节奏 | 60 ÷ 57.5 = **1.0435** → 不均；且**无更高倍率可用**（2x 需 115Hz） |
| 结论 | 该机器**无法实现 57.5Hz 对齐**；独占 VRR 与无边框等价（见 2.2） |

> 这条同时说明两件事：**回退机制确实在真实老硬件上被触发过**，以及**EDID 读取在部分内屏上会失败** —— 后者不是错误，界面已如实说明"不能判断 57.5Hz 是否在时序范围内"。

### 7.2 **未验证**的断言（转述时须谨慎）

以下说法来自外部资料或推断，**本机无相应硬件、或途径不可用，故未验证**：

| 断言 | 状态 |
|---|---|
| AMD **GCN 1.0（DCE 6.0）不支持**游戏 FreeSync，**GCN 1.1+ 起支持** | ⚠ **未验证** —— 涉及 Radeon HD 7750 等，本机无该硬件。代际划分听起来合理，但**无实测依据** |
| **NVIDIA 全系不支持** AMD 私有 HDMI 1.4 FreeSync | ⚠ **未验证**，且**极易被误读**：它针对的是 AMD 私有 HDMI 协议；经 **DisplayPort** 的 G-SYNC 完全不受影响（G70D 在 RTX 5060 Ti 上正常） |
| S24F350 的 FreeSync 范围为 **48-72 Hz** | ⚠ **EDID 里查不到**（它没有 Adaptive-Sync 声明）。与"旧 AMD HDMI FreeSync 不写 EDID"一致，但**数值无法用程序核实** |
| `DXGI_FEATURE_PRESENT_ALLOW_TEARING` 可作 VRR 判据 | ✗ **判定为无关**：它测的是**驱动/合成器**能否无同步呈现（Win10 1803+ 基本都为真），与**显示器**无关。**尝试实测但 COM vtable 调用崩溃，故为据文档含义判断** |
| Linux `xrandr ... vrr_capable` | ✓ **是真能力标志**（内核驱动从 DPCD 填的 DRM 属性）—— 但**仅限 Linux** |
| HDMI VSDB 的 `Max_TMDS` 可判 HDMI 1.4 / 2.0 | △ **偏移正确**（payload[6]），**但对部分显示器无效**：实测 S24F350 的 VSDB `len=5`，**根本没有该字段** |
| NVIDIA「为窗口和全屏模式启用 G-SYNC」能让**无边框**下 VRR 生效 | ⚠ **未实测确认** —— 该选项确实存在（驱动默认是"仅全屏模式"），且无边框窗口在 DWM 看来仍是窗口，**按理应当适用**；但本机**无法验证**：程序内没有"面板是否在变频"的信号，而显示器 OSD 的实时刷新率我读不到。**故本文把它写成"可能"，而非结论** |

### 7.3 已**放弃**的两条途径

| 途径 | 为何放弃 |
|---|---|
| **NVAPI**（`nvapi64.dll`） | 库存在且 `nvapi_QueryInterface` 已导出（说明可动态加载），但函数**按 ID 取而非按名导出** → **无法在本机核实** VRR 函数 ID 与结构体，出错概率高 |
| **Windows SDK / SDL 2.30** | 搜全部头文件，`VRR` / `AdaptiveSync` / `FreeSync` **零命中**。DisplayPort 的自适应同步能力在 **DPCD 寄存器**（经 AUX 通道），只有内核态驱动能读 |

> 有趣的是：**DPCD 那条路是对的归纳，但我最初据此错误地推断"EDID 里也没有"** ——
> 实际上现代显示器**通常也在 EDID 的 `00-00-1A` 里声明**。两者并存，见 `FIXES.md` 案例 26。

## 八、用户的验证清单

按顺序做，每步都能独立得出结论：

| # | 目的 | 方法 | 看什么 |
|---|---|---|---|
| **0** | **选定显示器** | 「常用」页 →「输出显示器」；脚本用 `-Monitor <n>` | 两处**填同一个编号**（见第九节） |
| 1 | **看当前实际状态** | 游戏内按 `` ` `` 打开统计读数 | `Sync:` / `Rate:` / `Panel:` / `Cadence:` 四行 |
| 2 | **看显示器时序范围与 VRR 声明** | 「常用」页 →「独占全屏 · 固定街机刷新率」下方（不可用时自动显示） | 型号 + `min-max Hz`，以及是否标「已声明 VRR」 |
| 3 | **查显卡侧 VRR 范围与作用模式** | NVIDIA 控制面板 →「设置 G-SYNC」 | ①列出的**刷新率范围**是否含 57.5；②该页下方的**「仅为全屏模式」/「窗口和全屏模式」**单选 —— 选后者则无边框也能生效（见 2.1） |
| 4 | **确认面板是否真在变频** | 显示器自带 **OSD 的实时刷新率** | 游戏运行时显示 ~57-58Hz = 在变频；钉在范围下限 = 未变频 |
| 5 | **看有哪些 57/58Hz 模式** | `Scripts\ArcadeDisplay-zh.bat -Action List`（双击即默认此动作） | 绿色标记的模式；开头会列出各显示器编号 |
| 6 | **切换并自动恢复** | `Scripts\ArcadeDisplay-zh.bat -Action Run -Game <rom.zip> -Monitor <n>` | 退出后自动还原桌面 |
| 7 | **无边框下看帧节奏** | 游戏内按 `` ` ``，只用无边框模式 | `Cadence:` 行；若不均，读数会给 `even at Nx = ... Hz` |
| 8 | **看实际渲染分辨率与抗锯齿** | 同上，任何模式 | `Render:` 行 —— 注意它与设置值可能不同（见下） |

> 第 5 步会先打印「已连接的显示器」并标出本次操作哪一台 —— **编号要在这里对**，因为 `\\.\DISPLAYn` 会跳号（本机是 1 和 5），靠猜必然错。

**统计读数的各行含义**：

| 行 | 含义 | 能否验证 |
|---|---|---|
| `Renderer:` | 实际在跑的渲染后端（**非配置意图**：Vulkan 启动失败会退回 OpenGL） | ✓ |
| `Sync:` | 实际进入的呈现模式 | ✓ |
| `Rate:` | 仿真速率 + 与街机原生的差值 | ✓ |
| `Panel:` | 面板自身模式（G-SYNC 下是它**上限**，不是当前扫描率） | ✓ |
| `Render:` | **实际渲染分辨率 + 实际生效的抗锯齿** | ✓ |
| `Cadence:` | **无边框与独占 VRR 出现**：面板速率 ÷ 仿真速率，非整数即报"不均"；独占固定率不报（见下） | ✓ 纯本地计算 |

> **`Cadence:` 的适用范围（2026-10-14 更正）**：原先只在无边框出现，理由是"独占模式要么面板跟随模拟器、要么就是面板速率本身"。**但不支持 VRR 的面板上 `ExclusiveDesktop` 两者都不是** —— 面板仍钉在自身速率，正是无边框的帧节奏问题。现已纳入，措辞按模式区分：
>
> ```
> 无边框   ：Cadence: uneven if panel @ own rate (2.09 scans per frame)
> 独占 VRR ：Cadence: uneven if VRR is not engaging (2.09 scans/frame)
> ```
>
> **独占固定率仍不报** —— 那种模式下面板已被切到 57/58Hz，`SDL_GetDesktopDisplayMode` 读到 57，除以 57.5242 得 0.991，会把 1:1 的**整数取整误报成不均**。

> **`Rate:` 不是面板刷新率**，是模拟器的**配速目标**（`RefreshRate` 设置）。面板真实速率在 `Panel:` 行。两者并存时（如 `Rate: 57.50 Hz` + `Panel: 60 Hz mode`）并不矛盾 —— 一个说每秒产出多少帧，一个说面板按什么速率扫描。
| `FPS:` / `CPU:` / `GPU:` / `RAM:` | 帧率与 1% low、CPU（混合架构下只统计大核）、GPU 与显存、内存 | ✓ |

> `Cadence:` 报的是"面板按自身速率"这一前提下的整除关系，**前提不成立时该行是假设而非事实** —— 上方表格与说明已分别列出两种模式的措辞。

**关于 `Render:` 这一行** —— 它报的是**实际值而非设置值**，这两者常常不同：

| 情形 | 读数 |
|---|---|
| Vulkan + `MSAA=4` | `Render: 2976x2304  MSAA 4x` |
| OpenGL + `Supersampling=4`，输出 2976x2304 | `Render: 11904x9216  SSAA 4x`<br>`        scaled to 2976x2304` |
| 两者都关 | `Render: 2976x2304  no AA` |

**为什么值得看**：

- **Vulkan 完全忽略 `Supersampling` 设置**（日志会写 `supersampling is not available in this backend; using 1x`），
  所以同一份 ini 在 Vulkan 下是 MSAA、在 OpenGL 下会变成 **`Supersampling × XResolution` 的乘积**。
  上例中 `XResolution=2976` 与 `Supersampling=4` 叠加 → **实际渲染 11904x9216**（1.1 亿像素/帧）。
  这正是 OpenGL 路径比 Vulkan 慢得多的直接原因，而此前在界面上完全看不出来。
- **MSAA 可能被驱动拒绝**（色深/深度格式都不支持该采样数时降为 1x），读数是**获准值**，不是请求值。
- **全屏下渲染分辨率跟随显示器而非 `XResolution`** —— 与"画面被裁"那个 bug 同源，
  现在在读数里直接可见。

> `SSAA` 与 `MSAA` 是两个不同的东西：**SSAA 平均整幅画面，MSAA 只平滑多边形边缘**。
> 两次会话都写着 "4x"，做的事并不一样，所以读数明确区分名称。

同一组数字也会写入日志（面板速率从截图读不出来，远程排查需要）：

```
Stats OSD: render 11904x9216, anti-aliasing SSAA 4x, scaled to 2976x2304.
Stats OSD: render 2976x2304, anti-aliasing MSAA 4x at 2976x2304.
```

### 常见结论对照

| 读数 | 含义 | 建议 |
|---|---|---|
| `Rate 57.50` + `Panel 120 Hz mode` + `FPS 57.5` | G-SYNC 正常跟随 | 保持 |
| `Rate 57.50` + `Panel 60 Hz mode` + `FPS 57.5` | **G-SYNC 未生效**，面板仍按 60Hz 扫 | 检查驱动 G-SYNC 开关与 VRR 范围 |
| `Cadence: uneven (2.09 ...)` | 无边框模式，120÷57.5 非整数（**前提：面板按自身速率**） | 先看显示器实时刷新率：若是 ~57-58Hz 则已由窗口 G-SYNC 解决、可忽略；否则改用独占模式，或按读数给出的 `even at 2x = 115.00 Hz` 建自定义分辨率 |
| `Rate 60.00 ... (+4.30%)` | 选了 60Hz 档，**游戏跑快 4.3%** | 想原生就改成 57.5Hz |

## 九、多显示器：编号、选择，以及一个裁切陷阱

### 9.1 两套编号之间必须搭桥

| | 谁在用 | 编号 |
|---|---|---|
| **SDL display index** | 模拟器内部所有 SDL 调用 | 从 **0** 起，按枚举顺序 |
| **`\\.\DISPLAYn`** | Windows、"标识"、脚本、设置界面 | 从 **1** 起，**且会跳号** |

**两者无法互相推导。** 本机实测：4K 主屏是 `\\.\DISPLAY5`，而 SDL 把它排在 **index 0**。所以"第 2 个显示器"在两套体系里指的不是同一台。

搭桥办法：拿 SDL 的 `SDL_GetDisplayBounds` 矩形去匹配 `GetMonitorInfo` 的 `rcMonitor`。**几何是两边唯一共有的字段**，而且匹配是精确的 —— 即便数值是 DPI 虚拟化后的，**两边被同样地虚拟化**，所以配准依然成立（详见 9.3）。

> `SDL_GetDisplayName()` 给出的是显示器友好名（`DISPLAYCONFIG_TARGET_DEVICE_NAME`），不是 `\\.\DISPLAYn`；后者 SDL 内部持有但不公开。所以名字能显示，编号只能自己配对。

### 9.2 怎么选

| 场合 | 参数 |
|---|---|
| 设置界面 | 「常用」页 →「输出显示器」下拉（**多于一屏时才出现**） |
| 命令行 | `-display=<n>` |
| 配置文件 | `DisplayNumber=<n>` |
| 脚本 | `ArcadeDisplay-zh.bat -Monitor <n>` |

下拉里按**角色**标注，而不是 Windows 编号：

```
自动 · 跟随系统主显示器
主显示器 · Odyssey G70D  3840x2160 @120Hz  · #5
副显示器 · S24F350  1920x1080 @60Hz  · #1
```

**`#n` 才是 `-Monitor` 要填的值**（即「显示设置 → 标识」里的编号）。它被放在末尾而不是开头，因为 `\\.\DISPLAYn` **会跳号** —— 本机主屏就是 `DISPLAY5`，把编号放前面会让最重要的那台看起来最反常。持久化的仍是编号本身（它是唯一在"切换主屏"后仍稳定的名字）。

**两边必须填同一个编号。** 在 A 屏全屏、而 57.524Hz 自定义分辨率建在 B 屏上，结果是**静默退回桌面刷新率** —— 不报错、不提示，正是最难自查的一类问题。

`自动` = 主显示器，也是默认值，同时是**回退值**：配置里存着副屏、但只带笔记本出门时，仍要能正常启动。

### 9.3 陷阱：全屏窗口尺寸不能取渲染分辨率

**症状**：副屏全屏时画面上下被裁掉一条；主屏正常。

**两条独立根因同时成立才会暴露**（完整定位过程见 `FIXES.md` 案例 29）：

| | 根因 | 何时被掩盖 |
|---|---|---|
| **A** | 请求的**渲染分辨率**被当作全屏**窗口尺寸** | 主屏上全屏切换会顺手把窗口缩到屏幕大小 |
| **B** | 全屏用的"桌面模式"取的是 **DPI 虚拟化尺寸**而非面板真实模式 | 若渲染分辨率本来就小于屏幕，看不出 |

**关键机制**：进程只声明 **system DPI aware**，Windows 于是把**与系统 DPI 不一致**的显示器几何换算进系统 DPI 空间。本机主屏 4K@150% 定义了系统 DPI，副屏 1080p@100% 被换算成 **2880x1620**。副屏**自己开不开缩放无关** —— 决定因素是它与主屏是否一致。

由此 `SDL_SetWindowDisplayMode(2880x1620)` 失败（**面板上没有这个模式**），全屏切换时窗口尺寸不更新，超大的窗口居中后上下各裁 ≈612 px。

**修复**：全屏窗口取显示器尺寸（窗口模式仍取请求分辨率，那时它确实就是一个窗口尺寸）；面板真实模式用 `EnumDisplaySettings(ENUM_CURRENT_SETTINGS)` 取，替换 SDL 的尺寸但保留其刷新率。

**验证**（同一份 ini，只换显示器）：

| | 设置的模式 | 全屏窗口 | 判断 |
|---|---|---|---|
| 副屏 修复前 | 2880x1620（面板不存在） | 2976x2304 | ✗ 裁切 |
| 副屏 修复后 | **1920x1080** | **2880x1620** | ✓ |
| 主屏 修复后 | 3840x2160 | 3840x2160 | ✓ 未变 |

日志里现在有这两行，专门用来区分这类问题：

```
Display 1: S24F350  1920x1080 @60 Hz  (Windows space 2880x1620)
Vulkan: window size 2880x1620.
Vulkan: swapchain 2880x1620, 3 images, present mode FIFO (vsync on).
```

**`window size` 与 `swapchain` 不一致，就是这个 bug 的签名。** 括号里的两个数字不一致，说明该显示器被 DPI 虚拟化了。

## 十、高刷新率显示器：240Hz / 480Hz 能对齐吗

**先限定范围：这个问题只在「无边框全屏」下存在。** 两种独占模式要么让面板跟随模拟器、要么就是面板本身的速率，不存在"能不能整除"的问题 —— 这也是那两种模式存在的**首要理由**。

### 10.1 判定规则

无边框下，面板速率 ÷ 模拟速率是否为整数（**容差 1%，且倍数需 ≥2**，见 `StatsOsd.cpp` `ClassifyCadence()`）。

### 10.2 逐档实测

| 面板 | ÷ 57.524160 | 比值 | 最近整数 | 判定 |
|---|---|---|---|---|
| 115 | 1.99916 | | 2 | **✔ 均匀** |
| 120 | 2.08608 | | 2 | ✘ |
| 144 | 2.50330 | | 3 | ✘ |
| 165 | 2.86836 | | 3 | ✘ |
| 175 | 3.04220 | | 3 | ✘ |
| 180 | 3.12912 | | 3 | ✘ |
| **230** | **3.99832** | | 4 | **✔ 均匀** |
| **240** | **4.17216** | | 4 | **✘** |
| 300 | 5.21520 | | 5 | ✘ |
| 360 | 6.25824 | | 6 | ✘ |
| **480** | **8.34432** | | 8 | **✘** |

**结论：240 和 480 都不能对齐。** 而且**高刷新率完全不帮忙** —— 因为 57.524160 不是整数，2x/4x/8x 全都不是标准刷新率：

```
2x = 115.04832      4x = 230.09664      8x = 460.19328
3x = 172.57248      5x = 287.62080      6x = 345.14496
```

**两个反直觉的结果值得记住**：

1. **230 Hz 能通过，240 Hz 不能**（230 ÷ 57.524160 = 3.998，误差 0.04%，落在 1% 容差内）。
2. **480 Hz 比 120 Hz 更糟**：4.17 与 8.34 的"小数部分"不同，但两者都是不均 —— **面板越快不等于越接近整数倍**。

### 10.3 高刷屏的正确用法

| 路线 | 结果 |
|---|---|
| **独占 · G-SYNC/VRR** | 面板直接按 57.5Hz 扫描，**只要 VRR 范围含 57.5**（高刷游戏屏下限通常 48Hz）。1:1，最完美 |
| **独占 · 固定街机刷新率** | 建 57/58Hz 自定义分辨率。高刷屏的 `0xFD` 时序范围几乎必然含 57.5，通常能建 |
| 无边框 | **必然不均**，无论面板多快 |

> **一个检测不到的细节**：若面板 VRR 下限 > 57.5（如 60Hz），驱动会用 **LFC（低帧率补偿）** 把每帧重复 2 次 → 有效 115.05Hz，**仍为整数倍、仍然均匀**。但这是驱动内部行为，我们既读不到也检测不了 —— 所以独占 VRR 模式下只报 `preconditions met`，不声称结果。

### 10.4 读数怎么帮上忙

无边框下报不均时，读数会**给出目标数值**（因为读了 `57.5` 而不是 `57.524160`，2x 是整数）：

```
Cadence: uneven (2.09 panel scans per frame) - frames repeat
         unevenly; an exclusive sync mode removes this
         even at 2x = 115.00 Hz
```

这个数值可以直接填进显卡控制面板的自定义分辨率对话框。**只报"不均"而不给目标，用户无从下手。**

日志里同样有一行，便于远程排查（面板速率从截图读不出来）：

```
Stats OSD: cadence uneven - 2.0870 panel scans per frame; even at 2x = 115.0000 Hz.
```

### 10.5 2026-10-23 更新：高刷插值让这一节成为历史

本节上面的结论是「无边框下必然不均，只能靠独占/VRR 解决」。从 v0.9.5.5a 起有
第三条路，**它不需要面板对齐任何频率**：

- 逻辑仍然固定 57.524160 Hz 步进，画面按面板自己的刷新率输出；
- 两次逻辑步之间的画面由相机与实例矩阵插值生成（四元数 slerp），
  所以 120Hz 下 2.09 帧、240Hz 下 4.17 帧里每一帧都是新画面；
- 倍数不是整数不再产生“重复间隔在 2/3 帧之间跳”，因为**没有帧是重复的**。

对应设置是「常用 → 呈现节奏 → 跟随显示器」，也是新安装的默认值。
原来的三条路仍然保留：

| 路线 | 现在还需要吗 |
|---|---|
| 无边框 + 插值 | **默认，任何刷新率都可用** |
| **整数倍频（VRR 2x/3x/4x/8x）** | **面板够快时最准：115.05/172.57/230.10/460.19Hz，每个仿真帧正好 N 次扫描** |
| 独占 · G-SYNC/VRR | 仍有用：输入延迟最低，且 57.5Hz 在面板范围时最接近真机 |
| 独占 · 57.5Hz 自定义分辨率 | 仍有用：与真机逐帧一致的“博物馆模式” |
| 「原始 57.5Hz」呈现模式 | 上述两种硬同步场景下的配套选项 |

因此第 10.2 节的表格仍然正确，但它已经不是“能不能用”的问题，只是“要不要用
硬同步”。如果不想动显示器任何设置，选「跟随显示器」即可。

如果面板足够快，还有更彻底的一档：**VRR 整数倍频**（v0.9.5.6a 起）。
2x = 115.05Hz、3x = 172.57Hz、4x = 230.10Hz、8x = 460.19Hz，每个仿真帧
正好扫描 N 次，节奏与面板自身的频率彻底脱离关系，alpha 也是固定常数。
120Hz 面板只能用 2x；更高的档位需要 176 / 235 / 470Hz 的面板，不满足时
自动回退并记日志。详见 `sdl3_reports/2026-10-23-11-vrr-multiples.md`。

实测（120Hz 面板，Fixed 120）：`logic 57.50 Hz, present 119.96 Hz`，
呈现路径 0.97–1.20 ms/frame；VRR 2x 下为 `logic 57.53 / present 115.05`，
亚帧路径 0.27–0.35 ms/frame。详见
`sdl3_reports/2026-10-23-10-high-refresh-interpolation.md` 与
`sdl3_reports/2026-10-23-11-vrr-multiples.md`。

## 十一、显卡选择：为什么 OpenGL 下没有下拉框

### 11.1 原因：OpenGL 没有设备枚举接口

| | Vulkan | OpenGL |
|---|---|---|
| 枚举 / 选择 GPU | `SDL_Vulkan_*` + 物理设备选择，**应用真正决定用哪块** | **无对应 API** —— GL 上下文属于窗口，由**驱动**决定哪块适配器服务它 |
| 本项目的做法 | 按名字挑 `VkPhysicalDevice` | 两个**进程级导出符号**：`NvOptimusEnablement` / `AmdPowerXpressRequestHighPerformance`（`Main.cpp` 顶部） |

那两个标志由**驱动在进程加载时读取一次**，进程生命周期内不可更改。所以它不是"下拉框能改"的东西 —— 界面上那个置灰 Combo 甚至只有**一个选项**，即便启用也切不动。

### 11.2 实测：请求确实生效，但界面不该靠猜

本机双显卡（RTX 5060 Ti + Intel Arc），关掉 Vulkan 跑 OpenGL：

```
New 3D    → OpenGL Video Card: NVIDIA GeForce RTX 5060 Ti/PCIe/SSE2  (GL 4.1)
Legacy 3D → OpenGL Video Card: NVIDIA GeForce RTX 5060 Ti/PCIe/SSE2  (GL 4.6)
```

两个 OpenGL 路径**都落在独显**上，说明标志有效。

**但界面原先显示的是推测值**：从 **Vulkan** 设备列表里按 `NVIDIA`/`AMD` 关键字匹配出来的名字，并标注"已锁定独显"。而实际渲染的卡我们**本来就测量过** —— 就是 `glGetString(GL_RENDERER)`。**把已知事实换成推测**，一旦哪台机器上标志被忽略（驱动可以无视，OS 的按应用指定也能覆盖它），界面会显示错误的卡而用户无从察觉。

**现已改为显示实测值**：

```
实际渲染卡：NVIDIA GeForce RTX 5060 Ti/PCIe/SSE2
```

取自设置窗口自己的 GL 上下文（同一进程、同样的默认属性，因此与游戏会话落在同一块卡上）。日志同步记录：

```
OpenGL: settings window context is on "NVIDIA GeForce RTX 5060 Ti/PCIe/SSE2".
```

### 11.3 想换显卡测试，三条路

| 途径 | 可行性 |
|---|---|
| **Windows 设置 → 系统 → 显示 → 显卡**（按应用指定"高性能"） | 可以做。OS 级、需重启进程。**但是否对 OpenGL 生效由驱动决定 —— 未验证**，所以界面以 GL_RENDERER 那行为准 |
| `WGL_NV_gpu_affinity` 扩展 | 能真正按卡创建 GL 上下文，但**仅 NVIDIA**、代码量大、需每卡建 dummy window |
| 运行时切换 | **做不到**：进程级标志 + GL 上下文绑定窗口 |

### 11.4 顺带发现的不对称

有 `-vulkan3d`，但**没有 `-no-vulkan3d`** —— 命令行无法切回 OpenGL（只能改 ini 或在界面切换）。

`-Action List` 列出各显示器编号与全部模式，并标绿可用的；`-Action Save` / `Restore` 保存与还原显示设置（记录设备名，故还原时能回到同一台）；`-Action Run -Game <rom.zip> -Monitor <n>` 切换后启动、退出时还原，并把 `-display=<n>` 一并发给模拟器。

> **`-Monitor` 与模拟器的 `-display` 必须填同一个编号** —— `Run` 会自动转发，但只填一边时不会报错，只会静默按面板自身刷新率输出。
>
> **编码不是随意选的**：cmd 按"当时代码页"下的**字节偏移**重读 `.bat`，中途 `chcp 65001` 会让后续行偏移错位、`rem` 注释被当命令执行。所以启动器保持纯 ASCII，非 ASCII 全部放进带 BOM 的 `.ps1`（无 BOM 时 PowerShell 按系统代码页读取，中文必坏）。详见 `FIXES.md` 案例 27。
>
> 另有一个 PowerShell 特有的坑：`[NullString]::Value` 一旦经过 `[string]` 类型的参数或函数返回值就会被转成空字符串，而 `EnumDisplaySettings("")` 会被拒绝。所以脚本里统一用**空字符串**表示"当前显示器"，只在 P/Invoke 调用前那一刻换成 `NullString`。

## 十三、一句话总结

**能确定的**：是否有 57/58Hz 显示模式、面板时序范围、显示器是否声明 VRR 范围、接口类型、
**若面板按自身速率则无边框帧节奏是否整除（以及目标赫兹）**、**OpenGL 实际渲染在哪块卡上**。

**不能确定的**：驱动是否真在变频（原理上无信号）、自定义分辨率是否建得成（驱动侧）、
未声明 VRR 的显示器是否支持、驱动是否用了 LFC、OS 的按应用显卡设置是否被采纳、
**无边框下 VRR 是否因驱动设置而生效**。

**三条容易被忽略的结论**：

- **高刷新率不帮忙。** 240Hz 与 480Hz 在无边框下都不均；反而 **230Hz 是均匀的**（3.998x）。
  因为 57.524160 不是整数，整数倍 115.05 / 172.57 / 230.10 / … 都不是标准刷新率。
- **OpenGL 下没有显卡可选，也不该猜。** 程序只能"请求"独显，实测值以 `GL_RENDERER` 为准。
- **"不可能"是相对的。** "无边框不能 VRR"默认成立 —— 但 NVIDIA 可把 G-SYNC 应用到窗口输出
  （「窗口和全屏模式」），那时无边框也能 1:1，而程序无法检测：**看显示器自己的实时刷新率**。

**判据永远是同一条**：**不给超出数据支撑的结论**。可证的说成可证，必要的说成必要，
未知的标明未知 —— 并把用户该去哪里查写清楚。
