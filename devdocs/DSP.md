# SCSP / DSP 笔记：Fighting Vipers 2 的胜利画面爆音

本文记录这次排查的**现象、证据、推断和建议**。代码改动只有 `Src/Sound/SCSP.cpp`
里的两处，但结论比改动本身重要，所以单独留档。

相关文件：

| 内容 | 位置 |
| --- | --- |
| SCSP 引擎与混音 | `Src/Sound/SCSP.cpp` |
| DSP 核（**两个引擎共用这一份**） | `Src/Sound/SCSPDSP.cpp`、`SCSPDSP.h` |
| 引擎开关（已退休） | `-new-scsp` / `-legacy-scsp`、配置键 `LegacySoundDSP`：仍被解析，不再影响行为 |

---

## 一、现象

上游 issue #321（`shadowflash`）：Fighting Vipers 2 在 Cross River Dam 关卡赢下
比赛后，本该播放 "you win" 和胜利音乐，实际却是：

- "you wi…" 被截断，然后**一个音符开始循环播放，音量在很短时间内快速攀升**；
- 最终变成满幅的高频噪音，音量足以让人担心损坏耳机或音箱；
- 之后游戏才继续加载下一关。

上游维护者的答复是：这是老问题，给这个游戏单独加 `-legacy-scsp`（或 ini 里
`LegacySoundDSP=1`）换用 ElSemi 的旧 DSP 代码。

## 二、代码事实：并不存在"两套 DSP"

从命名看像是两个实现，实际不是：

- `SCSPDSP.cpp` 里只有一份 `SCSPDSP_Step()`，`SCSP.cpp:1608` 不分新旧地调用它。
- `legacySound` 在 `SCSP.cpp` 里只有 5 处引用：声明、`SCSP_Init()` 读取配置、
  `SCSP_w8()`、`SCSP_w16()`、`SCSP_DoMasterSamples()`。

也就是说两个引擎的**全部**差异只有三处：

1. **DSP 内存写入，字节路径**：新引擎把 `0x7C0–0x7FF` 镜像写进 `MADRS`，旧引擎丢弃。
2. **DSP 内存写入，字路径**：同上（但旧引擎原来的写法是越界，见第五节）。
3. **效果声道混音**：
   ```cpp
   // 新引擎（也是 MAME 的写法）
   UINT16 Enc = (EFPAN << 8) | (EFSDL << 13);
   // 旧引擎（原来的样子）
   UINT16 Enc = (EFPAN << 8) | (EFSDL << 14);
   ```
   音量表 `LPANTABLE[65536]` 的布局是 `TL` 占 0–7 位、`PAN` 占 8–12 位、`SDL` 占
   **13–15** 位（`SCSP_Init()` 里 `iSDL = (i >> 13) & 7`）。左移 14 位会把 3 位的
   `EFSDL` 顶到第 14–16 位，最高位溢出 `UINT16` 被截掉，实际读到的下标等价于
   `(EFSDL & 3) << 1`，即音量档位只剩 `{0, 2, 4, 6}`，`EFSDL >= 4` 直接静音。

## 三、关键实验：把电平对齐后，问题仍然存在

第一步只改了一处：把旧引擎的 `<< 14` 改成 `<< 13`，让两个引擎的**混音完全一致**。
理论上这会让旧引擎的效果声道变响（更接近硬件），如果爆音是电平失控导致的，
应该会变得更糟。

实际结果（用户实测 FV2，Cross River Dam 胜利画面）：**爆音消失，声音正常。**

由此推断：**爆音与效果声道的电平无关**。既然混音已相同，两个引擎剩下的唯一
差异就是 `0x7C0–0x7FF` 这三个字节段/地址段的处理方式。

## 四、证据：FV2 往 `0x7C0–0x7FF` 写入什么

在 `SCSP_w8()` / `SCSP_w16()` 里加临时探针（已删除），跑 FV2 到开机画面，日志
里 DSP 内存写入的顺序是：

```
#1..#20   w8  0x700..0x77F      COEF，真实系数
#21..#72  w8  0x780..0x7B9      MADRS，真实偏移值（如 0x33, 0x37, 0xE8 …）
          w16 0x7BA..0x7BF      0x0000   ← 注意：从 MADRS 的尾部开始
          w16 0x7C0..0x7FF      0x0000   ← 整段清零
          w16 0x800..0xBF8      微程序（在 0x7C0 之后约 30 行才出现）
          w16 0xBF0             触发 SCSPDSP_Start()
```

结论：FV2 是**按地址顺序把一整块 DSP 映像上传**，`0x7B9` 之后的部分是填充的 0。

由此推出爆音机制：

- **新引擎**把 `0x7C0–0x7FF` 的 0 镜像进 `MADRS[0..31]`，而这张表刚刚在
  `0x780–0x7B9` 填好了真实偏移值。镜像写入把整张偏移表清零 → DSP 读采样时
  地址全变成 0 → 读到的是同一小段数据 → 叠加放大，正是"一个音符循环、音量
  快速攀升"的自激形态。
- 硬件上这段地址**不应镜像**：如果真镜像，这个游戏在真机上也会自毁 MADRS，
  而它在真机上是正常的。

- **旧引擎**不写这段（字节路径丢弃），所以 MADRS 保持完整 → 没有问题。

也就是说：上游那句"给 FV2 加 `-legacy-scsp`"能起作用，真正的原因是旧引擎**不**
镜像这段地址；而旧引擎顺带把效果电平压低的那个 bug，又把这个差异掩盖了。

## 五、顺带修掉的越界写（真 bug）

旧引擎的字写路径原本是：

```cpp
else if (addr < 0x800)                                  // 0x780..0x7FF 全收
    MADRS[(addr - 0x780) / 2] = val;
```

`MADRS` 只有 32 个 `UINT16`（`SCSPDSP.h`）。`addr = 0x7C0–0x7FF` 算出的下标是
**32–63**，越界 32 个字，而 `MADRS` 后面紧跟着 `MPRO[512]` —— 等于**把 DSP 微程序
的前 8 条指令改成写入值**（FV2 这里写的是 0）。

已改成：

```cpp
else if (addr < 0x7C0)
    MADRS[(addr - 0x780) / 2] = val;
else if (addr >= 0x800 && addr < 0xC00)
    MPRO[(addr - 0x800) / 2] = val;
```

行为上对 FV2 无影响，因为日志顺序显示微程序是在这些清零之后才上传的
（`0x800–0xBF8` 在 `0x7C0` 之后出现，`0xBF0` 最后触发 `Start()`），被越界踩到的
那 32 个字马上就被真正的程序覆盖。但这属于未定义行为，任何游戏只要往这段地址
写字就会踩到，所以必须修。

## 六、当前状态

2026-10-22 起只有一条 DSP 写入路径：

- `SCSP_w8()` / `SCSP_w16()` / `SCSP_w32()` 对 `0x7C0–0x7FF` 的写入一律丢弃，
  不再镜像进 `MADRS`。这正是第七节建议 1 的实现。
- `LegacySoundDSP`、`-new-scsp`、`-legacy-scsp` 仍被命令行/ini 接受（外部前端
  不必改），但没有任何代码读取它；值为 true 时日志会说明已忽略。
  `NeedsLegacySoundDSP()` 与 FV2 特判已删除，设置界面也不再提供该开关。
- 旧引擎的字写越界（第五节）随分支一起消失。新的 `SCSP_w32()` 同时补上了
  跨边界保护：`0x77E`、`0x7BE`、`0xBFE` 这类地址不会再写到数组外。
  注意 32 位路径的丢弃分支必须**显式**写成 `else if (addr < 0x800) { }`：只删掉
  MADRS 分支、让 `else if (addr < 0xC00)` 接住 `0x7C0–0x7FF` 时，
  `(addr - 0x800) / 2` 是无符号运算，`addr = 0x7C0` 会算出约 4 GB 的偏移，
  在 `MPRO` 存储时直接访问违例（2026-10-22 首次构建的崩溃就是这么来的）。
- 没有加入输出端 `tanh` 软削波或持续满幅降增益熔断（建议 3）。

FV2 不再需要任何额外参数，效果声道的混音也与硬件布局一致（`EFSDL << 13`）。

## 七、建议（2026-10-22：建议 1 已执行，建议 3 继续遵守）

**执行记录**：新引擎的 `0x7C0–0x7FF` 镜像已删除，两个引擎只剩同一条路径，
`LegacySoundDSP` 因此退休。按建议 2，先把两条分支的行为对齐、确认旧引擎不再
依赖任何差异，最后才删掉分支。下列验证要求仍需在真机上人工试听。

**建议 1：把新引擎的 `0x7C0–0x7FF` 镜像也去掉。**

如果新引擎在这段地址上也丢弃写入，那么两个引擎就只剩下"没有任何实质差异"，
`LegacySoundDSP` 这条分叉可以整体退休，`NeedsLegacySoundDSP()` 也能删掉。

风险与验证要求：

- 这是所有游戏共用的路径，改了会影响每一个用到 DSP 的游戏；
- 必须听一遍 DSP 用得重的作品：Scud Race、Daytona 2、Le Mans 24、Sega Rally 2，
  以及 FV2 本身（切到 `-new-scsp` 听大坝关胜利画面）；
- 判断标准是"混响/效果是否还在、音量是否与现在一致"，不是"有没有杂音"。

**建议 2：如果要做，先只改新引擎这一处，旧引擎保持现状。**

这样出问题时可以直接切回 `-legacy-scsp` 对照，而不需要回滚构建。

**建议 3：不要用"输出端软限幅/熔断"来盖这个问题。**

理由（已核对过音频链路）：

- 出口是 `SDL_AUDIO_S16`，SCSP 侧也有 `ICLIP16` / `ClampINT16`，持续满幅噪音
  本来就已经顶到 DAC 上限；`tanh` 软削波只改变波形，不降低响度，护不住耳朵。
- 常见写法 `if (|x| > 0.85) x = tanh(x)` 在拐点是断开的（0.8501 → 0.6912），
  会让所有游戏的大动态都出现咔哒声。
- 真正能保护设备的只有"持续满幅→降增益"的熔断，而它对正常的大音量段落会误伤。

要加只能作为**默认关闭**的选项，而不是默认行为。

## 八、仍未解释的部分

- `0x7BA–0x7BF` 也被写成 0，即 MADRS 的第 29–31 项被清掉。这三项在这款游戏里
  可能本来就没用到，但如果以后遇到"某个效果的定位不对"，可以从这里查。
- 本次只验证了 FV2 的胜利画面。写入路径统一后所有游戏都使用同一条路径，
  第七节的试听清单（Scud Race、Daytona 2、Le Mans 24、Sega Rally 2、FV2）
  仍需人工确认混响/效果和音量与改动前一致。
